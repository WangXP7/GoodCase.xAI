# WebGL2 原生 GLSL 技术详解

> 配套实例：[极光海洋在线演示](https://wangxp7.github.io/YiQiVibe-WBGL2-GLSL-ocean-ZG5.3F/) · [源码 index.html](./index.html)

---

## 一句话定位

「WebGL2 原生 GLSL」指的是：**不借助任何图形框架（Three.js / Babylon.js 等），直接用浏览器暴露的 WebGL2 API 手写 GPU 着色器（GLSL ES 3.00）来完成渲染**。整个场景没有模型、没有贴图、没有网格数据——画面上的每一个像素都是 fragment shader 用数学公式现场"算"出来的。

配套的极光海洋 demo 就是这种打法的一个典型样本：一个 HTML 文件、一段顶点着色器（7 行）、一段约 180 行的片元着色器，就能渲染出会流动的极光海洋。

---

## 1. 它在技术栈里的位置

浏览器里画东西有几层选择，从高到低：

| 层级 | 代表 | 你操控的东西 |
|---|---|---|
| 应用框架 | Three.js、Babylon.js | 场景图、网格、材质、灯光对象 |
| 底层 API | WebGL2 / WebGPU | 缓冲区、纹理、着色器、绘制命令 |
| 着色器语言 | GLSL ES 3.00 / WGSL | **每个像素的颜色如何计算** |

「原生」的含义就在这里——跳过第一层，直接操作第二层，而创作的核心全部发生在第三层。Three.js 最终也是把你的场景翻译成 WebGL2 调用，原生写法等于自己当这个翻译。

---

## 2. 渲染管线：着色器到底是什么

GPU 渲染一张图要经过一条固定流水线，WebGL2 里你主要写其中两站：

```
顶点数据 → [顶点着色器] → 光栅化 → [片元着色器] → 逐像素输出到画布
```

- **顶点着色器（Vertex Shader）**：对每个顶点跑一次，负责回答"这个点在屏幕的哪里"（输出裁剪空间坐标）。
- **片元着色器（Fragment Shader）**：对每个像素跑一次，负责回答"这个像素是什么颜色"。**极光、海浪、月光全部在这里面计算**——demo 里 `aurora-ocean.html:73` 开始的那段 `FS` 就是整个宇宙。

GLSL 是运行在 GPU 上的 C 方言，天然并行：一帧 960×540 ≈ 52 万个像素，同一份片元程序在几十万个 GPU 线程上同时执行。所以它的思维模式和 CPU 代码完全不同——**没有循环遍历像素的概念，你写的只是一个"给定像素位置，返回颜色"的纯函数**。

---

## 3. WebGL2 相比 WebGL1 升级了什么

WebGL2（2017 年起全平台普及）对应 OpenGL ES 3.0，对 shader demo 来说最关键的几点：

- **GLSL ES 3.00 语法**：`in`/`out` 取代 `varying`/`attribute`；片元输出用自己声明的 `out vec4 outColor`（demo 第 80 行）而不是只能写死 `gl_FragColor`
- **`gl_VertexID`**：可以在顶点着色器里凭顶点序号凭空造出几何体——demo 的全屏三角形（第 67 行）就是靠它**一个顶点缓冲区都不建**，直接 `drawArrays(TRIANGLES, 0, 3)` 画出铺满屏幕的三角形
- **循环和数组放开限制**：GLSL ES 1.00 的 for 循环必须是编译期常量次数，3.00 里可以用变量次数——极光那种"步数由质量档位决定"的光线步进（`auroraMarch(ro, rd, int steps, ...)`，第 148 行）在 WebGL1 里写不了
- 其他还有实例化渲染、Transform Feedback、3D 纹理、整数纹理、多渲染目标等，对这个 demo 类型影响不大，但在粒子系统、GPU 模拟里是主力特性

## 4. 剖析这个 demo 的骨架

### 4.1 JS 侧：一次配置，每帧只传参数

原生 WebGL 的样板代码是固定的三段（`aurora-ocean.html:245-258`）：

```js
gl.compileShader(...)   // 编译两段 GLSL 源码
gl.linkProgram(...)     // 链接成着色器程序
gl.bindVertexArray(...) // 绑定一个空的顶点数组（占位）
```

之后每一帧（`render()`，第 321 行附近）只做一件事——把 5 个 `uniform`（CPU→GPU 的全局变量）更新一下，然后一条绘制命令：

```js
gl.uniform2f(U.uRes, canvas.width, canvas.height); // 画布尺寸
gl.uniform1f(U.uT, simT);                          // 累计时间
gl.uniform1f(U.uAurora, P.aurora);                 // 极光强度滑杆
gl.uniform1f(U.uWave, P.wave);                     // 海浪高度滑杆
gl.uniform2f(U.uLook, P.yaw, P.pitch);             // 鼠标拖动的视角
gl.drawArrays(gl.TRIANGLES, 0, 3);
```

拖滑杆、转视角都**不重新编译着色器**，只是改 uniform 值，所以是零卡顿实时响应。

### 4.2 全屏三角形技巧

```glsl
vec2 p = vec2(float((gl_VertexID << 1) & 2), float(gl_VertexID & 2));
gl_Position = vec4(p * 2.0 - 1.0, 0.0, 1.0);
```

用位运算从顶点序号 0/1/2 生成 (-1,-1)、(3,-1)、(-1,3) 三个点——一个远超屏幕的大三角形，光栅化后恰好覆盖整个画布。这是 Shadertoy 风格 demo 的标准起手式：**几何体不存在，唯一的"场景"就是像素坐标**。

### 4.3 片元着色器：把整个世界写成数学

这是这类技术的灵魂。对每个像素，流程是（`main()` 在第 195 行附近）：

1. **重建视线**：从 `gl_FragCoord.xy`（像素坐标）算出归一化屏幕坐标 `uv`，结合相机朝向（视角 yaw/pitch）生成一条光线 `rd`，起点 `ro` 在海面上方 1.6 米处
2. **分岔**：`rd.y < 0` 往下看 → 是海面（与 y=0 平面求交，算波高、算法线、算反射）；否则是天空（夜空渐变 + 星星 + 月亮 + 极光）
3. **输出颜色**，经 ACES 色调映射 + gamma 校正 + 抖动

其中几个反复出现的"积木"值得单独说：

#### FBM（分形布朗运动）——demo 第 100 行

把多层不同频率的值噪声叠加：

```glsl
float fbm5(vec2 p){
  float v = 0.0, a = 0.5;
  for (int i = 0; i < 5; i++){ v += a * vnoise(p); p = m * p; a *= 0.52; }
  return v;
}
```

低频层给大形状、高频层给细节，一层比一层幅度减半——这一个函数同时供给了极光的光团、海浪的起伏。再配合**域扭曲**（先用一次噪声去偏移采样坐标，第 157 行附近的 `qw = q + (w - 0.5) * 7.0`），噪声图案就会扭曲出流动感，这是做出"像有机物"效果的核心手法。

#### 光线步进（Raymarching）——极光的实现（第 148 行）

极光不是画上去的一个面，而是：沿视线方向每走一小步就在三维空间里采样一次极光密度（密度 = FBM × 垂直包络 × 竖纹系数），把半透明颜色累加起来。天然有体积感和前后层次，海面反射极光时换个步数再步进一遍即可。

#### 程序化法线——海浪的实现（第 183 行）

海浪没有几何形变，只是对波高场做差分（第 183 行）得到法线扰动，再喂给 Fresnel 和镜面反射，几十字节的数据就骗出了粼粼波光。

#### 色彩管理——第 192 行

ACES 色调映射把 HDR 高亮压回 [0,1] 且高光不过曝、颜色渐变自然；最后逐像素加 1/255 随机抖动消除色带（第 240 行）。

## 5. 性能模型与优化手段

片元着色器的成本 ≈ **像素数 × 每像素指令数**。极光每步要算好几层噪声，一步的代价相当于普通 shader 的几十倍——这就是为什么 demo 必须带分辨率自适应：

- 「自动适配」每秒测一次 FPS，低于 45 就把渲染分辨率降 5%，高于 57 就升——GPU 性能差异被自动吸收，弱机掉分辨率而不是掉流畅度
- 反射用的极光步数（12）比主画面（28）少：水面波纹本身会把反射扭曲打碎，低精度根本看不出来
- 法线差分步长随距离放大，远景自动"糊化"，防止高频波纹在远处闪烁成噪点
- `preserveDrawingBuffer` + 定时器兜底：标签页被遮挡、`requestAnimationFrame` 被浏览器暂停时画面不冻结

## 6. 什么时候用「原生」，什么时候用框架

**适合原生的场景**：

- Shadertoy 式的程序化视觉：极光、云海、流体、分形、故障艺术……这些用框架反而绕远路
- 极限性能敏感的小特效（loading 背景、演唱会大屏、视觉效果页面）
- 学习图形学——每一行代码都在逼你理解管线本身

**该用 Three.js 的场景**：加载 glTF 模型、多光源多材质的真实感场景、需要阴影贴图/后处理链的完整 3D 应用。原生写这些等于手搓引擎，性价比极低。

**已知短板**：

- WebGL2 无法多线程提交命令（WebGPU 可以）
- 移动端低端 GPU 跑重步进着色器会吃力（所以分辨率自适应几乎是这类 demo 的标配）
- 着色器编译失败只给一行日志，调试比 CPU 代码痛苦——demo 里那个把 `getShaderInfoLog` 显示到页面上的错误浮层（第 244 行附近）就是为此准备的

## 7. 往下深入的建议路径

1. **The Book of Shaders**（thebookofshaders.com）：噪声与 FBM 最好的入门，交互式逐章演示
2. **Shadertoy**：几千个可直接阅读的 live 着色器，iq（Inigo Quilez）的作品是这个领域的教科书；他的博客文章（iquilezles.org）覆盖 SDF、raymarching、噪声的所有数学细节
3. **WebGL2 Fundamentals**（webgl2fundamentals.org）：把 JS 侧的缓冲区/纹理/VAO 样板讲得最透
4. 改现成的代码是最快的学习方式——比如把 demo 里的极光颜色梯度（`auroraMarch` 里那两行 `mix`）换成粉色系，或者把 `uWave` 的默认值推到 3.0 看风暴效果，每一处参数改动的视觉反馈都是即时的

---

## 总结

**WebGL2 原生 GLSL 就是把 GPU 当一台大规模并行的"数学函数求值器"来编程**——场景不再是数据（模型、贴图），而是一组随时可求值的连续函数；代价是思维要彻底转向数学与信号处理，回报是用几十 KB 的文本换来无限细节、永不重复、完全实时的画面。
