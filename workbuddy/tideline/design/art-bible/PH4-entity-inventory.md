> ### ⚠️ 开宗明义：本文档有一处必须上报的估算错误
>
> 我在美术圣经 §10.4 写过「MVP 约 275 sprite，**可打包进 2 张 1024×1024 图集**」。
> **这个结论是错的。** 逐项实测后：
>
> | 指标 | v1.2 估算 | **本次实测** | 偏差 |
> |---|---|---|---|
> | MVP sprite 数 | ~275 | **201–212** | −63 ~ −24 |
> | 图集需求 | 2 张 1024² | **3 张 1024²**（切段优化后）<br>4 张（不切段） | **+1 ~ +2 张** |
>
> **错在哪**：v1.2 用「帧数 × 平均画布面积 ≈ 2.3M」直接与「2 张 1024² = 2.1M」比较，**漏掉了图集打包损耗**（trim 后的空白、图块间距、MaxRects 无法 100% 填充）。2.3M 的内容不可能装进 2.1M 的容器——**哪怕 100% 利用率也装不下**。
>
> 完整验算见 **§6**，修订提案见 **§8**。

## 2. 命名与元数据规范（v2 · 修订 §9.7）

### 2.1 文件名格式

```
{类别}_{主体}[_{部位}][_{动作}][_{变体}]_{序号}.png
```

**硬规则**：全小写 · 下划线分隔 · 序号两位补零 · 禁用空格/中文/大写/连字符。

| 前缀 | 类别 | 示例 |
|---|---|---|
| `chr_` | 角色（鲨鱼/游客/敌人） | `chr_shark_swim_03.png` |
| `env_` | 环境（天空/水体/沙滩） | `env_beach_palm_02.png` |
| `itm_` | 道具 | `itm_bottle_spin_01.png` |
| `vfx_` | 特效贴图 | `vfx_dither_075.png` |
| `ui_` | 界面（含世界空间标记） | `ui_hud_stam_full.png` |

**特殊后缀**：

| 后缀 | 含义 | 示例 |
|---|---|---|
| `_seg_{part}` | 切段件（§5） | `chr_shark_seg_head_02.png` |
| `_c` / `_eh` / `_ev` / `_m` | 9-slice 四件（角/横边/竖边/中心） | `ui_panel_ev.png` |
| 无序号 | 唯一件，不参与帧序列 | `chr_shark_eye_frenzy.png` |

### 2.2 朝向与镜像

> **默认朝向 = 朝右（+X）。向左一律运行时 `scaleX = -1`，不另出素材。**

例外：Logo、文字类资产因镜像后不可读，单独出件。

### 2.3 锚点（Pivot）

统一以 **归一化坐标 (0–1)** 存储于图集 JSON 的 `pivot` 字段，**按 trim 后的内容框计算**（非画布）。

| 类别 | 默认 pivot | 说明 |
|---|---|---|
| 角色 · 鲨鱼 | **(0.10, 0.50)** | ⭐ **= 眼睛位置**。§4.1.1 定义眼睛在「吻部后方 1/3 处」；头:身:尾 = 3:5:2 → 头长 50.4px，眼距吻部 16.8px = 体长 10%。**旋转中心与视觉焦点重合**，咬合判定与转向都以它为原点 |
| 角色 · 游客 | (0.50, 0.50) | 几何中心 |
| 角色 · 敌人 | (0.50, 0.50) | 几何中心 |
| 环境 | **(0.50, 1.00)** | 底边中心，便于贴地/贴水面 |
| 道具 | (0.50, 0.50) | 几何中心，旋转类以此为中心 |
| UI | 逐件标注 | 9-slice 件为 (0,0) |

**⚠️ 给程基岩**：`carry` 帧的游客挂点需单独约定——见 §3.2 注 A。

#### 注 A · `carry` 挂点约定（给程基岩）

游客需挂在鲨鱼嘴部。约定：
- 鲨鱼 `carry` 帧在图集 JSON 中额外记录 **`carryAnchor: {x, y}`**（归一化，trim 后内容框坐标），指向口腔中心
- 游客 `carried` 帧的 pivot 保持 (0.50, 0.50)，运行时对齐到 `carryAnchor`
- 抖动 ±2px 由**运行时位移**施加（不占帧），量化到像素网格（§6.7）

#### 注 B · 配色变体（零素材成本）

4 种泳衣配色用**运行时调色板交换（palette swap）**实现，**不出新素材**：
- MVP 可用（9 色板内）：`#C7CFD8` / `#F2F5F8` / `#FF8A3D` / `#FF3B3B`
- Standard 追加：`#00C2FF` / `#FFD23F` / `#2EE6A8`

## 5. 鲨鱼循环态切段方案（省 1 张图集的关键）

### 5.1 为什么切段

美术圣经 §9.5 已认可「程序化切段」用于 8 方向转向与身体 S 波。我把它**扩展到 5 个循环态**：

`idle` · `swim` · `dash` · `carry` · `surf`

理由是几何的：这 5 态的身体变形**本质上是同一条正弦波的不同相位 + 不同整体姿态**。画 30 张整帧 = 把同一段身体重画 30 遍。

### 5.2 结构

```
    ┌────────┐   ┌──────────────┐   ┌────────┐
    │ HEAD   │ + │    BODY      │ + │  TAIL  │   + 鳍 3 件
    │ 56×72  │   │    80×72     │   │ 56×72  │
    │ 6 变体 │   │   4 变体     │   │ 6 变体 │
    └────────┘   └──────────────┘   └────────┘
         │              │                 │
         └──────────────┴─────────────────┘
                        │
              程序化组合：相位驱动 + 部位旋转 + 位移
```

| 部位 | 变体维度 | 件数 |
|---|---|---|
| 头 HEAD | 摆头相位 3 × 嘴部开合 2 | 6 |
| 身 BODY | S 波相位 4 | 4 |
| 尾 TAIL | 摆尾相位 6（**相位滞后身部 2 帧**，§4.1.5） | 6 |
| 鳍 FIN | 背鳍 / 胸鳍 / 腹鳍 | 3 |

**组合参数表**（每态一组，交程基岩）：

| 状态 | 波形频率 | 尾相位滞后 | 整体 pitch | 附加 |
|---|---|---|---|---|
| `idle` | 0.5Hz | 2 帧 | 0° | 呼吸起伏 ±2px |
| `swim` | 1.2Hz | 2 帧 | 0° | — |
| `dash` | 0Hz（绷直） | — | 0° | + 抖动残影 4 段（§7.3 #2） |
| `carry` | 0.8Hz | 2 帧 | **头部上仰 8°** | 身体**下沉 6px**、尾摆幅度 **−30%** |
| `surf` | 1.0Hz | 2 帧 | **整体 −65°** | 尾部拖长亮痕（程序化） |

### 5.3 成本收益

| | 整帧方案 | **切段方案** |
|---|---|---|
| sprite 数 | 212 | **201**（−11） |
| 鲨鱼内容面积 | 1,619,584 | **1,144,000**（−475,584，−29%） |
| 全项目内容面积 | 2,327,032 | **1,851,448** |
| @80% 打包后 | 2,908,790（**= 2.77 张**） | 2,314,310（**= 2.21 张**） |
| 图集需求 | **4 张 1024²** | **✅ 3 张 1024²** |
| 运行时成本 | 0 | ⚠️ 需 **切段组合器**（每帧 4–5 次 drawImage + 旋转） |

> **为什么整帧方案是 4 张不是 3 张**：2.77 张的理论值意味着 3 张要跑到 **92.5% 利用率**。
> MaxRects 在尺寸跨度如此大（4×4 到 240×208）的图集上做不到 92.5%，实测合理区间是 70–85%。**按 4 张排。**

**⚠️ 若切段方案未被采纳，第一个该动刀的资产是 `breach`**（7 帧 / 256,256 px²，全项目单帧最大）。砍到 5 帧可省 73,216 px²，但**不足以**把 4 张压回 3 张——仍需切段。

### 5.4 风险与退路

| 风险 | 缓解 |
|---|---|
| 段接缝在旋转时出现 1px 裂缝 | 段件**互相重叠 4px**，绘制顺序 尾 → 身 → 头 → 鳍 |
| 切段组合器是新增运行时复杂度 | 回退路径明确：不采纳则整帧重画 30 帧，**多花 1 张图集**，不影响其他资产 |
| `carry` 的游客挂点需跟随头部段 | 挂点挂在 HEAD 段上（非整帧），`carryAnchor` 改记在 HEAD 段元数据里 |

> **这是 §8 待裁决项 #1。我的推荐：采纳切段。** 省下的不只是 1 张图集，还有后续所有循环态迭代的返工成本（改一个相位参数 vs 重画 8 帧）。

#### ⚠️ 动画状态覆盖的缺口：`flee`

派单要求覆盖 `flee`，但**美术圣经 §4.1.5 没有 `flee` 这个动画**，概念文档状态机也没有。

1. `carry` 动画本身（下沉 6px / 尾摆 −30% / 头部上仰 8°）
2. 身后持续的 **L1 水花拖尾**
3. **HUD 强调色从琥珀切到血红** + ALARM 条脉动 + 边缘收拢箭头

1. **§7.5 制作纪律**：数值未 playtest 验证前，多做的资产极可能被推翻
2. 余量要留给 **playtest 后的补帧**——鲨鱼 168px 是「可调常量」，若反馈说偏大/偏小，缩放后很可能需要补几帧中间帧

| | |
|---|---|
| **后果** | 副循环的**唯一视觉载体**。它崩了，R2「双循环割裂」风险（概念文档 §8.1 高等级）坐实，§7.5 的收集物资产与 COMBO 系统全部白做 |
| **概率** | **高**。鲨鱼**侧身旋转 −65°** 是唯一一个非标准朝向的姿态。**−65° 不是 90° 的倍数，像素艺术家必须手绘，不能靠旋转生成**——旋转生成的像素边缘必糊（§8.2 反模式 #6） |
| **已知隐患** | 浪尖卷曲弧线（`env_surf_wave`，240×72）与鲨鱼身体必须**严丝合缝贴合**，对位难度高；且收集物要沿同一弧线排布（间距 90–140px） |
| **缓解** | ① 先做**鲨鱼 + 浪线的贴合测试图**（1 帧，不做动画）<br>② 浪线出 3 帧但**鲨鱼只出 2 帧关键姿态**，中间帧由切段相位插值<br>③ 收集物排布用**程序化弧线采样**（给定曲率 + 间距自动生成坐标），不手工摆点 |

### 观察项（第四名）

**`breach`** —— 画布 184×224、单帧内容 36,608 px²（**全项目单帧最大**），且是锚点 02「全游戏最爽一帧」。它不进前三是因为**姿态简单**（就是一次旋转），但它**最贵**，且 `breach` 帧数从 7 砍到 5 能省 73K px²（≈7% 余量）——**如果后面发现图集不够，这是第一个该动刀的地方。**
