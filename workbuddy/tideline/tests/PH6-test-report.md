## 6. 问题清单（按严重度排序）

### 🔴 #1 · Critical · 安全硬红线① —— **可达的 3 次/秒屏闪**（✅ **已修复**，见 §11.2）
> 原始判定为项目内**唯一红项**。修复采用统一闸门方案，可达场景 1s 窗峰值已降至 **1**，safety 12/12。
- **触发条件**：`ALARM ∈ [25, 60)`（且未满档）时，一次冲刺命中**救生员**。
- **根因链**：
  1. `core/constants.js:153` `PREY.LIFEGUARD.danger = 2.0` → 一次捕食 **ALARM +40**；
  2. `game/game.js:117` `updateAlarm` **每帧只升一档**，故 +40 跨两个阈值（如 40→80 跨 50、75）
     会在**连续两帧**各触发一次 `onTierChange`；
  3. `game/game.js:133-137` `onTierChange` 的 `triggerFlash` **没有任何冷却**（对比咬合闪有
     `BITE.SHAKE_CD=0.5` 把关，见 `game.js:186-190`）；
  4. 再叠加同帧的咬合闪 → **0.083s 内 3 次全屏色闪**。
- **实测**：`ALARM 40 → 84（tier 1→3）`，屏闪 t=`[0, 0.067, 0.083]`，**1s 窗峰值 = 3**（预期 ≤2）。
  另一组 `ALARM 10 → 54（tier 0→2）` 同样 =3。
- **期望 / 实际**：期望 ≤2 Hz（项目自定红线，严于 WCAG）；实际 **3 Hz**。
- **可达性**：**是**。救生员在 MVP 里被当作**猎物**生成（`entities.js:47` 与 `:59`），
  刷新点 `x∈[2600,2940]`（沙滩区），玩家在冲浪/沙滩段很正常地会撞到。
- **是否阻塞发布**：**是**（按项目自定的"硬红线①"，我判定阻塞；**最终放行由用户决定**）。
- **注**：WCAG 2.3.1 的阈值是"1 秒内不超过 3 次"，3 次**恰好卡在** WCAG 允许边界；
  但本项目 README 与 GDD 都把 **≤2Hz** 写成了自我加严的硬红线，故按项目标准判 FAIL。
- **修复方向（**我不改 src/**，交由主理人裁决）**：给"档位闪 / 满值闪"加与咬合闪同级的
  最小间隔（例如在 `G` 上加 `tierFlashCd = 0.5`），或把同一"1 秒窗"内的多次 `onTierChange`
  合并为 1 次闪。修好后 `test-safety-fx.js` 的 ①c 应自动转绿。

### 🟠 #2 · Major · 设计/实现范围不一致（MVP 越界）
- **现象**：MVP 把**日光浴者（100）**与**救生员（300 / danger 2.0）**当作**猎物**生成与捕食
  （`entities.js:44-47` 的 `preyReset` plan、`:59` 的重生 pick、`constants.js:150-153` 的 `PREY` 表）。
- **对照设计**：`PH1-concept-doc.md` §5 明确 MVP 目标 = **2 类游客（泳客 100 / 冲浪者 150）**；
  §v1.2 裁决更写明「**MVP：救生员是敌人，不是猎物** → 不影响 MVP 资产」。
- **影响**：救生员作为猎物正是问题 #1 的**触发源**；且它把 Standard 层的危险系数机制提前引入 MVP。
- **是否阻塞发布**：**否**，但**发布前必须二选一**：移除"救生员/日光浴者"的猎物身份，
  或保留但先修掉 #1。

### 🟡 #3 · Minor ·（已修复）并行编辑期间的"调用点先于模块落地"
- **现象（我开工时实测）**：`game/game.js:90` 调用 `TL.Pickups.reset(G)`，但当时全仓无
  `TL.Pickups` 定义、无 `pickups.js`、`index.html` 也未加载它 → `Game.init()` 必抛
  `TypeError: Cannot read properties of undefined (reading 'reset')`，
  **冒烟基线从 40/40 直接变红，且浏览器里游戏也起不来**。
- **现状**：已由主理人补齐（`entities.js:567` 定义 `TL.Pickups`，`game.js` 增加 update/draw 调用），
  基线已恢复 **40/40**。
- **是否阻塞发布**：**否**（已修复）。**流程建议**：改 `src/` 时"调用点 + 模块"应在同一批落地；
  QA 门在合并前必跑，避免基线瞬时红。

### ⚪ #4 · Informational · 档位闪/满值闪通道无冷却（与 #1 同源，仅观测）
- 在"每帧 +20 ALARM"这种**不可达**输入下，1s 窗峰值可达 **5**（档位闪 3 次 + 满值闪 1 次 + 咬合闪 1 次）。
- 真实可达性低（捕食受 `DASH.CD=1.2s` 节流）。但它与 #1 同根：**档位/满值闪没有最小间隔**。
  修 #1 时若一并加冷却，本项会自然降到 ≤2。

### 🟢 #5 · 正向确认 · 主理人怀疑的 `input.js` 失焦残留缺陷
- **判定：曾是真缺陷，现已修复。** 旧版 `onBlur()` 只清 `keys/dirX/dirY/dragId`，
  不清 `dashFlag/pauseFlag/muteFlag/confirmFlag/taps` → "按住空格切出去，切回来凭空冲一次"。
- 现行 `core/input.js:39-44` 已全部清零（并附注释说明原因）。
- 我加了 **5 条回归护栏** + **1 条对照断言**（"不模糊时确实置位"，防止断言空跑），实测全绿。

### 11.2 修复内容（`src/`，主理人执行）

**统一闸门**：把限频放在**唯一出口**上，而不是给每种闪各打补丁——
将来新增任何闪光源都自动受约束，不会再出现同源回归。

```js
// src/src/game/game.js
var lastFlashAt = -1e9;
function triggerFlash(hex, amount) {
  if (!G.opts || !G.opts.flash) return;
  if (G.time - lastFlashAt < C.FLASH_GAP) return;   // 任意 1s 窗至多 2 闪
  lastFlashAt = G.time;
  G.flashCol = U.hex2rgb(hex);
  G.flash = amount;
}
// reset() 中：lastFlashAt = -1e9;   ← 防止新一局开局被上一局压住
```

- 常量：`C.FLASH_GAP = 0.51`（配 `FLASH_DUR = 0.45`，保证闪烁之间留出完整的暗间隔）。
- **视觉限频不压制音效与 toast**：被限频的那次闪仍会播 `tierUp` 音与文字提示，
  因此「闪烁 ≤2Hz」这条视觉红线不会削减玩家的信息通道（可访问性要求：颜色/闪烁永不作为唯一通道）。
