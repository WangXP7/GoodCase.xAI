## 1. 背景（Context）

美术圣经里有三处设计，各自都合理，但**它们指向同一个未命名的技术需求**：

| # | 需求 | 出处 |
|---|---|---|
| 1 | **色闪**：捕食/高危时"**整屏调色板切换 1–2 帧**——所有颜色临时映射为高对比黑白 + 单一血红" | §6.6 |
| 2 | **色盲模式**：完整色盲 HEX 映射表（**血红 → 电光蓝**），MVP 就要 | §9.8 / `PHASE1-SUMMARY.md` §6 |
| 3 | **一抹血色**：强调色 = 稀缺性，靠**面积配额**控制（§2.6 双预算模型） | §2.0 / §2.6 |

**三者的共同点是：它们都要求"同一张贴图，在不同时刻显示成不同的颜色"。**

- 方案甲：**为每种变体各存一份贴图**。色闪 1 套 + 色盲 1 套 = 资产 ×3，且每次改配色要改 3 处，必然漂移。
- 方案乙：**运行时染色（tint）**。但 tint 只能做**统一乘算**——它无法把"血红变蓝、同时深海蓝不变"这种**非线性、逐色映射**表达出来。色闪要求"所有颜色→高对比黑白 + 单一血红"，这是**重映射（remap）不是染色**。
- 方案丙：**索引色 + 调色板查找表（LUT）**。

美术圣经 §2.1 已经把调色板定义为**索引式 16 色**，§9.1 已经要求资产用 **PNG-8 索引色**。**换句话说，美术侧已经在生产索引色资产了——只是渲染端还没有利用这个事实。**

## 2. 决策（Decision）

> ## 精灵纹理存储**调色板索引**而非颜色；最终颜色在片元着色器里通过一张 **256×1 的调色板 LUT 纹理**查得。

### 2.1 数据布局

```
┌─ 精灵纹理（资产）───────────────────────────────────┐
│  单通道（R8 / 或灰度 RGBA），每纹素 1 字节          │
│  值 = 调色板索引 0..255                             │
│  例：0 = 深渊黑 #0A0E17，7 = 血红 #FF3B3B …         │
└────────────────────────────────────────────────────┘
                        │ 采样（NEAREST）
                        ▼
┌─ 调色板 LUT（运行时生成，非资产）──────────────────┐
│  256 × 1 RGBA 纹理 = 1 KB                          │
│  内容由 palette.json 决定                           │
│                                                     │
│  可用调色板：                                        │
│    · base      基础（§2.1 16 色）                    │
│    · hiContrast 色闪（§6.6 高对比黑白 + 单一血红）    │
│    · cvdDeutan  色盲（§2 血红→电蓝）                 │
│    · cvdProtan / cvdTritan / mono                   │
└────────────────────────────────────────────────────┘
                        │
                        ▼
                   最终片元颜色
```

### 2.2 片元着色器（与 ADR-004 的抖动合并在同一 pass）

```glsl
precision mediump float;

uniform sampler2D uSprite;   // R 通道 = 调色板索引
uniform sampler2D uPalette;  // 256×1 RGBA LUT
uniform sampler2D uDither;   // 8×8 Bayer（ADR-004）
uniform float     uArtScale; // = 2（ADR-002）

varying vec2  vUv;
varying float vDensity;      // 1.0 = 实体（不抖动）；<1.0 = 粒子/残影

void main() {
    float idx = texture2D(uSprite, vUv).r;
    if (idx < 0.002) discard;                     // 索引 0 保留为"透明"

    // —— 有序抖动（ADR-004）——
    if (vDensity < 0.999) {
        float thresh = texture2D(uDither, gl_FragCoord.xy / (uArtScale * 8.0)).r;
        if (vDensity < thresh) discard;
    }

    // —— 调色板查找 ——
    gl_FragColor = texture2D(uPalette, vec2(idx, 0.5));
}
```

### 2.3 一句话，三个设计全解决

| 需求 | 实现方式 | 成本 |
|---|---|---|
| **色闪**（§6.6） | `palette.bind('hiContrast')` → **1 次纹理绑定** | 1 行代码 |
| **色盲模式**（§2 / §9.8） | `palette.bind('cvdDeutan')` → **1 次纹理绑定** | 1 行代码 |
| **一抹血色面积配额**（§2.6） | 构建期扫描索引直方图 → 自动统计强调色占比 | 构建脚本，零运行时成本 |

**色闪与色盲从"两套需要手工同步的资产"变成一个 1 KB 的纹理切换。** 而且——

> **这直接把可访问性等级从 Standard 推到 Comprehensive**（§9.8），成本从"重新出一套图"降到"加一行 JSON"。

### 2.4 资产生产管线（需要林绘澄配合的部分）

**这是本 ADR 唯一会改变美术工作流的部分，我尽量做到不改变"怎么画"，只改变"怎么导出"。**

```
美术在 Aseprite / Photoshop 中按 §2.1 的 16 色调色板绘制（工作方式不变）
        │
        ▼ 导出 PNG-8 索引色（§9.1 现有要求，不变）
        │
        ▼ 构建脚本 tools/build-atlas.mjs
        │   ① 读取 PNG-8 的实际调色板
        │   ② 把每个像素的「颜色」映射回「权威调色板索引」
        │      （权威调色板 = design/art/palette.json，单一真源）
        │   ③ 输出灰度 PNG-8：灰度值 = 索引号（0..255）
        │   ④ 输出图集 JSON（TexturePacker hash 格式，§9.1 现有要求）
        │   ⑤ 校验：若出现调色板外的颜色 → 构建失败并列出违例
        ▼
   atlas_*.png（灰度索引图）+ atlas_*.json + palette.json
```

**关键收益：第 ⑤ 步把美术圣经 §2.5「配色纪律（硬约束）」从人工检查变成构建期自动门禁。** 任何表外颜色会直接让 CI 失败——这正好落实了 `PHASE1-SUMMARY.md` §10.3 待办 #1「调色板取证脚本（扫描图集，列出表外颜色）」，那个待办本来是分配给我做的。

### 2.5 为什么用 256 索引而不是 16

§2.1 定义的是 16 色主调色板。但：

- 4 张图集（characters / environment / ui / vfx）可能需要各自的强调色
- 色闪调色板需要"高对比黑白 + 血红"，是另一组颜色

**用 256 索引（1 字节）可以容纳全部调色板的所有变体于一张 LUT 中**，代价是每纹素 1 字节而非 4 bit——**完全无所谓**（1024×1024 图集 = 1 MB，与 RGBA 的 4 MB 相比仍然省 75%）。

**约束被消除**：不再有"单张图集最多 16 色"的限制，林绘澄可以自由使用任意数量的颜色（只要总索引 ≤ 256）。

## 3. 理由（Rationale）

1. **美术侧已经在生产索引色资产了**（§9.1 PNG-8 + §2.1 索引式调色板）。本 ADR 只是让渲染端**利用这个既成事实**，而不是新增要求。
2. **色闪与色盲是重映射，不是染色。** 这是技术判断：tint（`gl_FragColor *= tint`）在数学上无法表达"把颜色 A 变成 B，同时把颜色 C 变成 D"。只有 LUT 能做到。
3. **它让可访问性几乎免费。** §9.8 目标 Comprehensive 级，其中"完整色盲模拟模式"在 RGBA 方案下意味着**重新导出所有图集**；在 LUT 方案下是**一行 JSON**。
4. **带宽与显存降低 75%。** 单通道 vs RGBA。对移动端低端机是实打实的收益。
5. **它把配色纪律变成 CI 门禁。** 这是 `PHASE1-SUMMARY.md` 已经分配给我但还没做的待办，本 ADR 顺带完成。

---

## 4. 后果（Consequences）

### 正面

- 色闪 / 色盲 / 未来任何配色变体 = 1 次纹理绑定
- 可访问性直达 Comprehensive 级
- 显存与纹理带宽 −75%
- 配色纪律由 CI 自动强制，不再依赖人工检查
- 一抹血色的面积配额可**自动统计**（构建期直方图），§2.6 的双预算模型有了可信的度量手段

### 负面 / 需偿还

| 代价 | 说明 |
|---|---|
| **需要一个新的构建步骤** `tools/build-atlas.mjs` | 约 150 行 Node 脚本（读 PNG-8 调色板 → 重映射 → 输出灰度索引图）。**一次性成本** |
| **美术无法直接"看图确认"导出的索引图** | 灰度索引图肉眼不可读。**缓解**：构建脚本同时输出一份**还原后的 RGBA 预览图**，供美术验收 |
| **渐变与抗锯齿会破坏方案** | 索引色要求每个像素严格来自调色板。**但美术圣经本来就禁止渐变与柔化**（§6.7 禁渐变发光、§7.4 禁模糊与 alpha 羽化、§6.7 要求硬边）。**所以这不是新增约束，是把既有约束变成技术前提。** |
| 索引 0 被占用为"透明" | 实际可用索引 1..255，足够 |
| 若未来要引入真 alpha 层（暗角/遮罩） | 那些层**不走**索引色管线，走独立的真 alpha 后期层（ADR-004 §2.4 已划分） |

## 5. 备选方案（Alternatives Considered）

| 方案 | 结论 | 理由 |
|---|---|---|
| **RGBA 贴图 + 每变体导出一份** | ❌ 否决 | 资产 ×3，改配色要改 3 处，必然漂移；包体 ×3 |
| **RGBA 贴图 + 运行时 tint** | ❌ 否决 | 数学上无法实现色闪要求的**非线性逐色重映射** |
| **RGBA 贴图 + 全屏 LUT Filter** | ⚠️ 保留为 Spike 失败回退 | 可行（按颜色近似匹配到 LUT），但：① 依赖颜色匹配的模糊性，易出错；② 多一次全屏 pass；③ 无法自动做配色纪律检查 |
| **16 索引（4 bit 打包）** | ❌ 否决 | 省下的 0.5 字节/纹素毫无意义，却带来"单图集 ≤16 色"的硬约束 |
| **纹理数组（Texture2DArray）+ 变体切换** | ❌ 否决 | 等价于"每变体一份资产"的显存版本，只是把包体问题换成显存问题 |

## 6. Spike 依赖

本 ADR 依赖 ADR-001 Spike 的第 1 项（"索引色纹理上传 + 调色板 LUT 采样"）与第 5 项（"整屏调色板切换 + 色盲模式切换"）。

**若 Spike 第 1 项失败（单通道纹理在某些设备上不支持）**，降级路径：

- 把索引存进 **RGBA 的 R 通道**（灰度 PNG 上传为 LUMINANCE/RGBA），其余三通道浪费
- 显存收益从 −75% 降到 −0%，但**色闪 / 色盲 / 配色门禁三项收益全部保留**
- **这是可接受的降级**，因为它保住了本 ADR 90% 的价值
