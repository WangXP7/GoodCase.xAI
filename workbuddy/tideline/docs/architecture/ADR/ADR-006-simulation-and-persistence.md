## 1. 背景（Context）

有三处文档表述需要统一，且有一处**隐含矛盾**：

**§9.2 说**：
> "逻辑 / 物理更新：**60fps（固定步长）**，与渲染帧率**解耦**（见 §9.6）"

**§9.6 说**：
> "固定时间步长：逻辑 60fps 固定步长 + **渲染插值**（`accumulator` 模式），避免物理抖动"

**§6.7 说**：
> "**位置**：必须**量化到像素网格**（步进 2px 或整数倍），**禁止亚像素插值**。"

> ⚠️ **§9.6 的"渲染插值"与 §6.7 的"禁止亚像素插值"直接冲突。**
> 渲染插值的全部意义就是在两个逻辑帧之间产生**亚像素位置**，而 §6.7 要求所有位置吸附到 2px 网格。
> 两者不能同时执行——插值完再吸附，等于没插值；吸附完再插值，等于违反 §6.7。

同时还有两个没人回答的问题：
- **要不要引入物理引擎？**（概念文档没提，但"碰撞/搁浅/击退"这些词容易让人默认需要一个）
- **无后端，存档怎么存？防不防作弊？**

---

## 2. 决策（Decision）

### 2.1 不引入物理引擎

> **手写 AABB 碰撞 + 高度场（海床），约 300 行。不引入 Matter.js / Planck.js / Box2D。**

| 我们需要的 | 物理引擎提供的 | 判定 |
|---|---|---|
| AABB 重叠检测 | ✅ | 需要，但 30 行 |
| 海床高度场碰撞 | ⚠️ 需转成多边形/链 | 用 `seabedY(x)` 查表更简单（ADR-003） |
| 冲刺时的扫掠（CCD） | ✅ | 需要，但只对鲨鱼，约 40 行 |
| 击退冲量 | ✅ | `v += impulse` 一行 |
| 刚体旋转、摩擦力矩、关节约束、休眠优化 | ❌ 全都不需要 | 这是物理引擎 90% 的体积 |

**三条否决理由**：

1. **求解器非确定性**。这是最要命的一条。约束求解器的迭代顺序依赖浮点累加顺序，跨浏览器/跨设备可能不同。本作是**街机计分游戏**，我要求"同种子 + 同输入 = 同结果"（见 §2.4）。物理引擎让这件事做不到。
2. **隧道效应仍需自己解决**。冲刺 448 设计 px/s → 单帧 7.47 设计 px，对 1px 渔网必然穿透。物理引擎的 CCD 有性能代价且行为难预测，不如手写扫掠 AABB 精确可控。
3. **体积与复杂度**。Matter.js ≈ 90 KB（gzip ≈ 25 KB），换来的是我们要绕开的一套 API。

**唯一会后悔的场景**：如果 Phase 2 出现了"可堆叠的刚体物件"（比如推倒沙堡、物体连锁倒塌）。**目前 GDD 里没有这类设计。若出现，重新评估（记录为技术债）。**

### 2.2 固定步长 60Hz + **不做渲染插值**（解决 §9.6 ↔ §6.7 冲突）

> **裁决：§6.7 的"量化优先"胜出。不做渲染插值。**

**理由**：这是像素游戏，不是 3D 游戏。

- 渲染插值存在的目的是：逻辑帧率（60Hz）低于显示帧率（144Hz）时，用中间位置让运动看起来平滑。
- 但 §6.7 要求位置吸附到 2 设计 px 网格。**插值产生的中间位置会被吸附掉**——插值在数学上变成了空操作，只留下计算开销和一份"我们在插值"的错觉。
- 更糟的是：如果插值后再吸附，位置会以不均匀的节奏跳变（有时 1 帧跳 1 格，有时 2 帧跳 1 格），**比不插值更抖**。

**执行方案**：

```ts
const FIXED_DT = 1 / 60;          // 秒，唯一定义
let accumulator = 0;

function frame(now: number) {
  let frameTime = Math.min((now - last) / 1000, 0.25);  // 防死亡螺旋（切后台回来）
  last = now;
  accumulator += frameTime * timeScale;                 // timeScale 用于顿帧（=0）

  while (accumulator >= FIXED_DT) {
    stepLogic(FIXED_DT);          // 固定步长，确定性
    accumulator -= FIXED_DT;
  }
  render();                       // 位置在此处吸附到艺术网格（ADR-002 snapArt）
}
```

**高刷新率屏幕（120/144Hz）的处理**：

| 选项 | 说明 | 结论 |
|---|---|---|
| A · 渲染锁 60fps | 简单、省电、与逻辑 1:1 | ⚠️ 高刷屏用户会感到"不够顺" |
| B · 渲染跑满刷新率，逻辑仍 60Hz，不插值 | 画面每 2–2.4 帧才变化一次 | ❌ 感觉像掉帧 |
| C · **渲染跑满，逻辑 60Hz，只对"非网格量"插值** | 尾部旋转、缩放脉冲、镜头、CRT 参数做插值；**位置仍吸附** | ✅ **采用** |

**方案 C 的精妙之处**：§6.7 只禁止**位置**的亚像素插值，而明确允许"缩放 / 旋转使用缓动"。所以：

- **位置** → 吸附（§6.7 硬约束）
- **旋转角、缩放、镜头偏移、后期参数** → 平滑插值（§6.7 允许，且高刷屏受益）

这同时满足了 §6.7 和"高刷屏不要浪费"。

**顿帧（Hit Stop）**：通过 `timeScale = 0` 实现，持续 0.08s。**顿帧期间输入采集照常**（见 §2.5）。

### 2.3 时间源分离

| 时间源 | 受顿帧影响 | 受暂停影响 | 用途 |
|---|---|---|---|
| `clock.scaled` | ✅ | ✅ | 游戏逻辑、动画、粒子 |
| `clock.unscaled` | ❌ | ✅ | 呼吸脉动（ADR-004）、UI 动画 |
| `clock.wall` | ❌ | ❌ | 性能统计、遥测 |

### 2.4 确定性（Determinism）

> **目标：同种子 + 同输入序列 = 完全相同的一局。**

**规则**：

1. **全局唯一 RNG**：`mulberry32(seed)`，实例化在 `World` 上。**禁止 `Math.random()`**（lint 规则 + CI 检查）。
2. **禁止在逻辑中使用 `Date.now()` / `performance.now()`**。所有时间来自 `clock.scaled`。
3. **禁止依赖对象遍历顺序**（`for...in`）：实体数组用稳定排序的稠密数组。
4. **浮点是 IEEE-754 双精度**，在 JS 中是确定的（同一份代码、同一引擎语义下）。**不追求跨浏览器比特级一致**，只追求**同一浏览器内的可复现**——这对 bug 复现与回归测试已经足够。

**价值**：

| 收益 | 说明 |
|---|---|
| **回放 / 输入日志** | 记录 `seed + 输入序列`，任何 bug 都能 100% 复现。对 QA（严守真）是质变 |
| **回归测试** | 固定输入跑一局，断言最终分数。改动后数值漂移立即暴露 |
| **反作弊基础** | 见 §2.6 |
| **可复现的 playtest** | 同一关、同一随机序列给不同测试者 |

### 2.5 顿帧与输入

> **顿帧冻结逻辑推进，但不冻结输入采集。**

ADR-003 §2.6 的 QTE、以及 §6.6 ③ "受击时绝不触发顿帧（会被感知为输入延迟）"都依赖这一条。

```
帧 N：玩家在顿帧窗口内按下冲刺
   → 输入进入缓冲区（不丢失）
   → 逻辑不推进（timeScale = 0）
帧 N+5：顿帧结束
   → 缓冲区中的冲刺被消费，立即生效
```

输入缓冲：`dash` 120 ms，`mash` 200 ms（QTE 用）。

### 2.6 无后端持久化与安全态势

#### 存储

```ts
// 命名空间 + 版本号，为将来迁移留口
localStorage['tideline.v1.settings']   // 5 开关 + 音量 + a11y + 已见提示
localStorage['tideline.v1.profile']    // 最高分、双货币、升级树、统计
localStorage['tideline.v1.telemetry']  // 环形缓冲，最近 200 条事件（调试用）
```

**存档时机**：

| 触发 | 策略 |
|---|---|
| 设置变更 | 立即写（量小、频率低） |
| 单局结束 | 写一次（防抖 500 ms） |
| **`visibilitychange` → hidden** / `pagehide` | **必须写**（移动端不触发 `beforeunload`） |
| 运行中 | **绝不每帧写**（localStorage 是同步 API，会阻塞主线程） |

**模式版本化**：每份存档带 `schemaVersion`，加载时跑迁移链 `v1→v2→…`。迁移失败 → 回退到默认 + 保留损坏数据副本（便于诊断）。

#### 防作弊态势（明确表态）

> **本作不做实质反作弊。这是有意的，不是遗漏。**

| 理由 | 说明 |
|---|---|
| **纯前端无后端 = 客户端完全不可信** | 任何 JS 层面的校验都能被绕过。做"看起来有用"的混淆是安全剧场（security theater） |
| **没有排行榜后端 → 作弊只伤害作弊者自己** | 单机高分没有外部性 |
| **成本收益比极差** | 真正的客户端加固（WASM + 完整性校验 + 服务端校验）远超本项目预算 |

**我们做这些**（低成本、有真实价值）：

- 存档 JSON 加一个**校验和**（防止手滑改坏，不防恶意）
- 设置与进度**分离存储**（清缓存不会丢设置）
- 明确**不请求任何权限**（概念文档 §7.2）

**我们不做的**：加密混淆、反调试、代码自校验。

> 🔴 **给主理人的前置警告**：**如果未来要加"在线排行榜 / 每日挑战 / 分享成绩"，本 ADR 的这部分必须推翻重做。** 那需要服务端权威 + 回放校验，是另一个量级的工程。**请在加这类功能之前先找我评估，不要先承诺。**

## 3. 理由（Rationale）

1. **物理引擎的体积与不确定性换不来我们需要的东西。** 我们要的是 AABB + 高度场 + 扫掠，不是刚体动力学。
2. **插值与像素吸附在数学上互斥**，必须选一个。像素游戏选吸附——这不是偏好，是 §6.7 已经定下的视觉契约。
3. **方案 C 让这个选择不必牺牲高刷屏**：只对 §6.7 明确允许的量（旋转/缩放/镜头）插值。
4. **确定性几乎免费**，却换来可复现的 bug、回归测试和 playtest 一致性。
5. **在防作弊上诚实**：承认做不到并说明原因，比做一堆无效混淆更负责任。

---

## 4. 后果（Consequences）

### 正面

- 逻辑确定、可复现、可回归测试
- 无物理引擎依赖，包体与复杂度双降
- 顿帧不吞输入，手感有保障
- 存档模式版本化，未来可迁移
- 明确不做反作弊 → 省下的预算用在别处

### 负面 / 需偿还

| 代价 | 说明 |
|---|---|
| **手写碰撞约 300 LOC** | 一次性成本，且比调物理引擎更好测 |
| **全局禁止 `Math.random()` / `Date.now()`** | CI 强制（lint 规则）。团队需适应 |
| **高刷屏的位置更新仍是 60Hz** | 方案 C 缓解了大部分，但位置本身仍是 60Hz。这是像素游戏的固有取舍 |
| **无成就/排行榜的反作弊** | 见 §2.6 的前置警告 |

## 5. 备选方案（Alternatives Considered）

| 方案 | 结论 | 理由 |
|---|---|---|
| **Matter.js** | ❌ 否决 | 非确定性求解器破坏可复现；CCD 行为难控；90 KB 换 30 行能写完的功能 |
| **Planck.js（Box2D 移植）** | ❌ 否决 | 同上，且更重 |
| **逻辑跑可变 dt（无固定步长）** | ❌ 否决 | 违反 §9.2；物理行为随帧率变化（低帧率下冲刺距离会变短），街机游戏不可接受 |
| **固定步长 + 位置插值** | ❌ 否决 | 被 §6.7 的吸附抹平，只剩开销；且吸附后的跳变节奏不均，比不插值更抖 |
| **逻辑跑 120Hz** | ⚠️ 记录 | 能让高刷屏位置更新更密，但：① 违背 §9.2 的 60fps 规定；② CPU 翻倍；③ 在 2px 网格上，120Hz 的位置变化有一半会被吸附掉 → **收益低于成本** |
| **存档加密混淆** | ❌ 否决 | 安全剧场。纯前端混淆可被逆向，成本真实、收益为零 |
| **IndexedDB 替代 localStorage** | ⚠️ 记录 | 容量更大、异步不阻塞主线程。但本作存档 <10 KB，localStorage 足够。**若未来要存回放（输入日志可能达数百 KB），改用 IndexedDB** |
