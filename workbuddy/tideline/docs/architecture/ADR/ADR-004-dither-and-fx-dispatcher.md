## 第一部分 · 有序抖动（阻塞项 4）

### 1. 背景

§7.6 把有序抖动从"光柱的可选项"推广为**全项目默认的半透明替代方案**，并给了一条实现要求：

> "用 **Bayer 4×4 有序抖动矩阵**，预生成 4 张（或 16 张）抖动图案，按寿命索引取用。**禁止每帧计算抖动**（性能）。"
> "给程基岩的实现要求：抖动图案**预生成为 4–16 张小 sprite**，打包进 `atlas_vfx`，运行时按粒子寿命索引取用。**禁止运行时逐像素计算 Bayer 矩阵。**"

这条要求在其预设的技术前提下是**正确的**——如果渲染是 Canvas2D，逐像素 CPU 计算 Bayer 矩阵确实会在 60fps 下崩掉。

**但 ADR-001 已裁决渲染方案为 WebGL2。** 技术前提变了，约束的最优解也变了。我需要在**不违背这条要求意图**的前提下重新求解。

### 2. 决策：GPU 片元着色器抖动，屏幕锚定于艺术网格

#### 2.1 意图保全分析（先把"禁止"的意图讲清楚）

| | §7.6 的字面要求 | §7.6 的**意图** |
|---|---|---|
| 抖动从哪来 | 预生成 sprite 贴片 | **不要有 CPU 逐像素开销** |
| 为什么 | 性能 | 性能 |
| 隐含假设 | 渲染在 CPU / Canvas2D | — |

**GPU 片元着色器满足这个意图，而且满足得更好**：每个片元确实"逐像素计算"了，但是**在 GPU 上、数千个核心并行、每个片元 1 次纹理采样 + 1 次比较**。它的成本比"从图集里取一张预烘焙贴片"只多约 1 个纹理采样单元，却**省掉了组合爆炸**。

#### 2.2 为什么预烘焙贴片方案在 WebGL 下反而更差

预烘焙必须回答一个问题：**贴片是什么颜色的？**

- 若烘焙成**白色遮罩**，运行时染色 → 需要 17 级（Bayer 4×4）× 1 = 17 张。可行。
- 若烘焙成**实际颜色** → 16 色 × 17 级 = **272 张**。每次改配色都要重烘焙。

而 GPU 方案：**0 张资产**，任意颜色，任意密度，且与 ADR-005 的索引色 LUT 天然同源。

| | 预烘焙贴片 | **GPU shader** |
|---|---|---|
| 资产数 | 17 张（需染色）或 272 张（预着色） | **0** |
| 改配色的成本 | 重烘焙全部 | **改 1 个像素的 LUT** |
| 密度分辨率 | 17 级（4×4） | **65 级（8×8）** |
| 批量绘制 | 每次换贴片 = 换纹理区域（可批合） | 密度作顶点属性，**同一批** |
| 运行时 CPU 开销 | 0 | 0 |
| GPU 开销 | 1 次采样 | 1 次采样 + 1 次比较 |

**结论：GPU 方案在每一项上都优于或等于预烘焙，且严格满足"零 CPU 逐像素开销"的意图。**

#### 2.3 具体规格

**矩阵：Bayer 8×8（不是 4×4）**

```
 0 32  8 40  2 34 10 42
48 16 56 24 50 18 58 26
12 44  4 36 14 46  6 38
60 28 52 20 62 30 54 22
 3 35 11 43  1 33  9 41
51 19 59 27 49 17 57 25
15 47  7 39 13 45  5 37
63 31 55 23 61 29 53 21
```

选 8×8 而非 §7.6 建议的 4×4：**4×4 只有 17 级密度**，粒子淡出会出现明显色带（banding）；8×8 有 **65 级**，淡出连续。代价是抖动单元从 4×4 变成 8×8 艺术像素（= 16×16 设计 px），网格更粗一点——但 §7.6 本来就要的就是可见的网点纹理，粗一点更符合街机 authenticity。

**编码**：8×8 单通道纹理（64 字节），值 = `(M[r][c] + 0.5) / 64 * 255`。采样用 `NEAREST` + `REPEAT`。

**锚定方式：屏幕空间**（关键决策）

```glsl
// 抖动阈值：按屏幕片元坐标取，并除以 ART_SCALE 以对齐艺术网格
float ditherThreshold(vec2 fragCoord) {
    return texture2D(uDitherTex, fragCoord / (uArtScale * 8.0)).r;
}

// 粒子/残影片元：density 由顶点属性传入（= 粒子寿命剩余比例）
if (vDensity < ditherThreshold(gl_FragCoord.xy)) discard;
```

**为什么选屏幕锚定而不是物体锚定**：

| | 屏幕锚定 | 物体锚定 |
|---|---|---|
| 单独一个粒子移动时 | 像素会随网格进进出出（"闪"） | 稳定 |
| **多个粒子重叠时** | **共享同一网格，无摩尔纹** ✅ | 各粒子网格不重合 → **摩尔纹** ❌ |
| 与真实硬件行为 | **一致**（街机硬件的抖动就是屏幕锚定的） | 不一致 |

水花是 25–40 个粒子重叠的密集事件（§7.3 #3 / #9）。**重叠场景远多于单粒子场景**，所以选屏幕锚定。且"像素随网格进出"正是真·硬件抖动的外观，属于特性不是缺陷。

> 通过 uniform `uDitherAnchor`（`0` = 屏幕 / `1` = 物体）可实时切换，供林绘澄 A/B 观感。

#### 2.4 与暗角/遮罩的边界（确认 §7.6 的判断）

§7.6 保留暗角与遮罩用**真 alpha**，理由是"全屏抖动会产生可见网格纹"。**我确认这个判断，并补上机理**：

> 抖动产生可见网格纹的条件是被抖动的量**在空间上低频且平滑**。
> - **暗角**：一个跨越整个屏幕的平滑径向渐变 → 除了抖动图案本身，画面里**没有别的空间频率** → 网格纹成为唯一可见结构 → 必然显形。
> - **粒子**：本身就是高频的、离散的、运动的 → 抖动图案混在里面**读起来像材质**，不显形。

**所以判据不是"全屏 vs 局部"，而是"被抖动的对象是否本身具有更高的空间频率"。** 这条判据比面积更准，未来新增元素时用它可以自行判断。

| 元素 | 处理 | 频率判据 |
|---|---|---|
| 粒子淡出 / 冲刺残影 / 光柱 / 水珠 / 泡沫线 | ✅ 抖动 | 高频 ✅ |
| **暗角 / 暂停遮罩 / 结算遮罩** | ⚠️ 真 alpha | 低频平滑 ❌ |
| 实体 sprite | ❌ 100% 不透明硬边 | 不适用 |

#### 2.5 密度曲线

§7.6 给的寿命→密度映射是线性的（100/75/50/25%）。我建议改为**轻微下凹**：

```ts
// lifeRatio ∈ [0,1]，1 = 刚生成
const density = Math.pow(lifeRatio, 0.75);
```

理由：线性映射下粒子在最后 25% 寿命里密度从 25% 掉到 0，视觉上"突然消失"；`^0.75` 让密度在早期下降稍快、末期拖长，消散更自然。**这是一个观感参数，交林绘澄定；代码里做成常量 `DITHER_CURVE_POW`。**

#### 2.6 与粒子系统的集成

- 粒子记录增加 `density: Float32`，每帧由 `life / lifetime` 计算
- `density` 作为**顶点属性**随批合一并提交（不打断批合）
- 抖动在**同一个批**内完成，**不产生任何额外绘制调用**
- 成本估算：最坏情况（40 粒子 × 5×5 艺术 px）= 1,000 片元 → **可忽略**

#### 2.7 Canvas2D 逃生舱（兑现 §7.6 的字面要求）

若 ADR-001 的 Spike 失败、降级到 PixiJS 且自定义 shader 受阻，抖动回退到预烘焙方案：

- 预生成 **17 张**（Bayer 4×4）白色遮罩贴片，打包进 `atlas_vfx`
- 运行时用 `tint` 染色
- **这张逃生路线已设计就绪，不需要额外决策**

## 第二部分 · 呼吸式脉动统一实现（阻塞项 5）

### 3. 背景

§9.9.2 的硬红线：

> **全项目禁用硬 on/off 切换，一律改呼吸式明暗渐变。全局频闪上限 ≤2Hz。** 亮度突变才是主要诱因，而非频率本身。

需要一个统一实现，供：QTE 圆环（§6.8.4）、ALARM 条、威胁等级 T4（§4.4）、深海生物发光（§5.3.1）、连打提示图标（§6.8.4）、扫描线抖动（§6.6）、张力预告（§5.4.3.1）等至少 7 处复用。

### 4. 决策：`breath()` 单一时间函数 + CI 强制

#### 4.1 函数契约

```ts
// src/core/anim/breath.ts —— 全项目唯一的脉动时间源
export type BreathChannel = 'ui' | 'hazard' | 'ambient' | 'world';

export interface BreathSpec {
  channel: BreathChannel;   // 决定相位（见 §4.3）
  hz: number;               // 频率，会被 clamp 到 [0, BREATH_MAX_HZ]
  lo: number;               // 下限
  hi: number;               // 上限
  phase?: number;           // 可选覆盖（默认取 channel 相位）
  unscaled?: boolean;       // true = 用不受顿帧影响的时间（用于 UI）
}

export const BREATH_MAX_HZ = 2;   // §9.9.2 硬红线，全项目唯一定义

export function breath(spec: BreathSpec, t: number): number {
  const hz = Math.min(spec.hz, BREATH_MAX_HZ);          // 硬 clamp，无法绕过
  if (__DEV__ && spec.hz > BREATH_MAX_HZ) warnOnce(...); // 开发期告警
  if (opt.flash === false) return spec.hi;              // 开关关闭 → 常亮（§9.9.1）
  if (hz === 0) return spec.hi;                         // reduced-motion

  const ph   = spec.phase ?? CHANNEL_PHASE[spec.channel];
  const time = spec.unscaled ? clock.unscaled : clock.scaled;
  // 升余弦：两端导数为 0，在极值处"停留"，读起来像呼吸而非摆动
  const w = 0.5 - 0.5 * Math.cos(2 * Math.PI * hz * (time + ph));
  return spec.lo + (spec.hi - spec.lo) * w;
}
```

#### 4.2 波形：升余弦，不是 sin

§9.9.2 给的实现是 `alpha = 0.6 + 0.4 * sin(2πft)`。我改为**升余弦** `0.5 − 0.5·cos(2πft)`：

| 波形 | 过中点速度 | 在极值处 | 观感 |
|---|---|---|---|
| `sin` | 最快 | 不停留 | 像"摆动" |
| **升余弦** | 最快 | **导数为 0，停留** | **像"呼吸"** |

两者数学上只差一个相位，但升余弦在极值处的停留正是"呼吸"的语义来源。§9.9.2 要的就是"呼吸式"，所以采用升余弦。

#### 4.3 相位错开（一条 §9.9 没有但必须有的规则）

> 🔴 **这是我在阅读 §9.9 时发现的缺口。**

§9.9 限制了**单个元素**的频率 ≤2Hz。但光敏性癫痫的真实诱因是**大面积相对亮度变化**（WCAG 2.3.1 判据：面积 > 视野 10% 且相对亮度变化 > 10%）。

**如果 7 个脉动元素同相位，它们的亮度变化会叠加**——每个都是 2Hz、每个都是局部的，但合起来就是一次 **全屏 2Hz 的亮度摆动**。这恰恰是 §9.9 想防的东西，而"每个元素 ≤2Hz"这条规则**管不到它**。

**对策：按 channel 错开相位，并设全局亮度预算。**

```ts
const CHANNEL_PHASE: Record<BreathChannel, number> = {
  ui:      0.000,   // HUD、QTE 圆环
  hazard:  0.137,   // 威胁等级、ALARM 高危、张力预告
  ambient: 0.271,   // 生物发光、环境微光
  world:   0.413,   // 世界内可交互物
};
```

（相位取无理数相关的错开值，避免任意两个 channel 的拍频落在低频。）

**全局亮度预算（运行时审计，仅开发期启用）**：

```
Σ (元素面积 / 视口面积 × 亮度调制幅度) ≤ 0.10
```

`BreathAudit` 在开发模式下记录所有注册脉动元素的面积与幅度，超预算即在控制台告警并列出贡献最大的元素。

#### 4.4 与 5 个开关的联动

| 开关 | `breath()` 行为 |
|---|---|
| `opt.flash = false` | 返回 `spec.hi` → **常亮**（§9.9.1"所有闪烁改为常亮"），信息不丢失 |
| `prefers-reduced-motion` | 等价于 `hz = 0` → 返回 `hi` |
| `opt.crt / jitter / shake / particles` | 不影响 `breath()`（正交，见 §6） |

#### 4.5 强制执行机制（三条，缺一不可）

1. **CI 静态检查**：`Math.sin(` / `Math.cos(` / `setInterval` 出现在 `src/gameplay/**` 或 `src/presentation/**` 中即失败（`src/core/anim/breath.ts` 白名单）。
2. **Lint 规则**：`no-restricted-syntax` 禁止上述模式。
3. **开发期运行时审计**：`BreathAudit` 统计每个注册元素的 `hz` 与面积，断言 `max(hz) ≤ 2` 且亮度预算 ≤ 0.10。

> **为什么必须三条**：光敏性安全是**安全红线**，不能依赖"程序员记得"。§9.9.5 的验收清单里"全项目闪烁频率 ≤2Hz（代码搜索 `Math.sin(2 * Math.PI * f` 核验 f 值）"是一条**人工**检查——我把它变成**自动化**的。

#### 4.6 我对 §6.6「色闪」的安全意见（需林绘澄 / 严守真确认）

> ⚠️ **这是我在本次评审中发现的、全项目最高的光敏性风险点，必须提出来。**

§6.6 定义色闪为：

> "**整屏调色板切换 1–2 帧**：所有颜色临时映射为高对比黑白 + 单一血红。"

**这是全项目唯一一个全屏、高对比、突变的效果**，而且§9.9 明确说"亮度突变才是主要诱因"。它与其他所有被 §9.9 约束的元素不是同一量级。

为它辩护的事实：它只有 1–2 帧（16–33 ms），是**单次瞬变**而非重复闪烁，WCAG 的"3 次/秒"判据不适用于单次事件。**所以它是合规的。**

但它仍然是风险最高的单点。我的建议（**不擅自改美术决策，仅提方案**）：

| 选项 | 说明 |
|---|---|
| **A（现状）** | 保留 1–2 帧全屏高对比切换 |
| **B（我建议）** | 改为**部分调色板切换**——只重映射最暗的 3 档色阶，其余不变。亮度变化幅度降到约 40%，视觉冲击力保留约 80% |
| **C** | 色闪默认跟随 `opt.flash` 开关；**且在首次启动的光敏提示中明确列出"色闪"** |

**我的立场**：A 合规，但 B 的性价比更高（损失 20% 冲击力，换来一个数量级的安全边际）。**这是美术决策，不是技术决策，请林绘澄定。** 无论选哪个，`opt.flash` 必须能关掉它。

## 第三部分 · 中央特效调度器 FX Dispatcher（阻塞项 6）

### 5. 背景

美术圣经里有**两套规则，需要一个仲裁层，而且它们会互相冲突**：

**§6.7 互斥规则**（防认知过载 R3）：
> "同一时刻最多允许一个「屏幕级视觉特效」发生。**色闪 > 震屏 > 扫描线抖动**，若同时触发多个，按优先级执行，其余丢弃。"
> "需要一个**中央特效调度器**（FX Dispatcher）……建议在程基岩的架构中预留。"

**§9.9.1 五开关正交规则**（防光敏性）：
> "这 5 个开关必须**两两正交**——任意组合都要能正常工作，且**组合后不能出现『关掉了震屏但打击感完全消失』的退化**。"

**冲突在哪？** 举个具体例子：

> 玩家关闭了「屏幕闪烁」。捕食事件触发 `{色闪 + 震屏 + 顿帧}`。
> - 互斥规则：色闪优先级最高 → 色闪胜出，震屏丢弃。
> - 开关规则：色闪被关 → 色闪不生效。
> - **结果：色闪因开关关闭不生效，震屏因互斥被丢弃。捕食只剩顿帧。**
>
> 而 §9.9.1 明确要求"关闭震屏后，捕食仍有顿帧 + 色闪反馈"——**这里反过来了：关闭色闪后，震屏被互斥规则吃掉了。**

**这不是边缘情况，这是必然发生的组合。** 两套规则必须由同一个仲裁层、在同一次求值中处理，否则必然产生"死区"。

### 6. 决策：三段式管线

```
 请求 Request
    │
    ▼
┌─ Stage 1 · 准入 Admission ──────────────────────────────────┐
│  ① 开关过滤：受控开关关闭 → 不丢弃，转为「补偿令牌」           │
│  ② 频率限制：同一 fxId 在 minInterval 内不重复                │
│  ③ 并发上限：每类同时活跃数量上限                             │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─ Stage 2 · 互斥仲裁 Arbitration ────────────────────────────┐
│  仅「屏幕级」特效争夺唯一名额：                               │
│    flash(30) > shake(20) > jitter(10)                       │
│  高优先级到达 → 抢占，低优先级软停 2 帧后退出（防 pop）        │
│  低/同级到达 → 丢弃，并发 fx:suppressed 事件（供调优）         │
│  ⚠️ 顿帧 / 缩放脉冲 / 粒子 / 飘字 / 音效 不参与互斥            │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─ Stage 3 · 降级补偿 Compensation ──────────────────────────┐
│  被阻断（开关关闭 或 仲裁落败）的请求 → 查补偿表 → 换替代反馈  │
│  补偿递归深度上限 2，防死循环                                 │
│  目标：任何组合下，任一核心事件至少留 1 个可感知反馈通道        │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
                     Active FX Set → 渲染 / 音频 / 时序
```

#### 6.2 互斥集与非互斥集（明确边界）

| 集合 | 成员 | 依据 |
|---|---|---|
| **参与互斥**（争夺唯一屏幕名额） | 色闪 / 震屏 / 扫描线抖动 | §6.7 |
| **不参与互斥**（正交） | **顿帧**（时序层）<br>**缩放脉冲**（作用于整层）<br>粒子（世界空间）<br>飘字（世界空间）<br>音效<br>HUD 状态变化 | §6.7 v1.2 修正 + §6.6 ② |

> §6.7 v1.2 已经把顿帧和缩放脉冲移出互斥表，**我确认这个修正是对的**，并在数据结构上把它固化下来（`screenLevel: false`），防止后续有人误加回去。

#### 6.3 抢占规则（§6.7 没说，我补上）

§6.7 只说"按优先级执行，其余丢弃"，没说**高优先级在中途到达时怎么办**。这是一个必然发生的时序问题（捕食 0.08s 内可能被受击打断）。

| 情形 | 行为 |
|---|---|
| **高优先级到达，低优先级正在播** | **立即抢占**；低优先级**软停 2 帧**后退出（不是硬切） |
| **低/同级到达，高/同级正在播** | **丢弃**，发 `fx:suppressed` 事件 |
| **低优先级播出不足 3 帧时被抢占** | 同上，仍然软停（保证至少可见 2 帧，避免出现"闪一下就没"的 pop） |

**为什么用软停而不是硬切**：1–2 帧的效果被硬切会产生亮度/位移突变，而**突变本身就是我们要防的东西**。软停把"丢弃"也纳入安全约束。

#### 6.4 补偿表（Stage 3 —— 本 ADR 的核心贡献）

> **这就是"互斥与开关不冲突"的答案。** 被阻断的特效不是消失，而是**降级为另一种通道的反馈**。

| 被阻断的 FX | 一级补偿 | 二级补偿（一级也不可用时） |
|---|---|---|
| **震屏**（开关关 / 仲裁落败） | **顿帧 0.08s** | 缩放脉冲 ×1.5 强度 + 粒子数 ×1.5 |
| **色闪**（开关关 / 仲裁落败） | **震屏**（若可用） | 缩放脉冲 + 高对比色块常亮（信息保留） |
| **扫描线抖动**（开关关） | 扫描线**保持静态**（仍显示） | ALARM 高危改用 HUD 边缘箭头 **2Hz 呼吸** |
| **CRT 后期**（关） | 无（纯视觉降级，无信息损失） | — |
| **粒子**（0%） | **几何替代**：1px 硬边描边扩散环（无粒子） | 缩放脉冲 |

**补偿递归**：若一级补偿也不可用，走二级；**深度上限 2**，超出则记录 `fx:deadzone` 告警（开发期）并在生产环境静默降级为顿帧。

#### 6.5 正交性不变量（可自动验证）

> **不变量**：对 5 个开关的 **2⁵ = 32 种组合**，与 **6 个核心事件**，每一种组合下，该事件必须在反馈通道集合 `{视觉, 时序, 音频, HUD}` 中产生 **≥1 个非零反馈**。

**6 个核心事件**（覆盖 §7.3 全部 VFX 触发点）：

`bite`（捕食成功）· `hit`（受击）· `combo`（COMBO 爆发）· `rarePickup`（稀有拾取）· `beachLand`（搁浅落地）· `alarmEscalate`（ALARM 升级）

**= 192 个测试用例，全部可自动化。** 这就是 §9.9.5 验收清单第 1 条（"5 个开关两两正交，任意组合不崩溃、不出现无反馈的死区"）的机械化实现。

```ts
// tests/fx-dispatcher.orthogonality.test.ts
for (const combo of allSwitchCombinations()) {        // 32
  for (const evt of CORE_EVENTS) {                    // 6
    const out = dispatcher.resolve(evt, combo);
    expect(feedbackChannels(out)).not.toHaveLength(0);  // 至少一个通道非零
    expect(maxFlashHz(out)).toBeLessThanOrEqual(2);     // 同时守住 2Hz 红线
  }
}
```

> **这条测试同时守住了三个东西**：§6.7 互斥、§9.9.1 正交不死区、§9.9.2 的 2Hz 上限。一套规则，一处验证——这正是中央调度器的价值。

#### 6.6 架构位置与强制约束

```
gameplay（L2）
    │  只发领域事件：BiteLanded / PlayerHit / ComboAchieved ...
    ▼
EventBus
    │
    ▼
FX Dispatcher（L1 core）── 唯一有权触发屏幕级特效的组件
    │
    ├──▶ Renderer（震屏 / 色闪 / 缩放 / 后期参数）
    ├──▶ Clock（顿帧）
    ├──▶ ParticleSystem
    └──▶ AudioBus
```

**两条硬约束**：

1. **gameplay 层禁止直接调用 `screenShake()` / `flash()` / `hitstop()`**。只能发事件。
2. **Lint 规则**：`src/gameplay/**` 中禁止 import `src/core/fx/dispatcher` 以外的特效模块。

**为什么这么严**：如果任何一处游戏逻辑能直接触发震屏，§6.7 的互斥规则就形同虚设——它只在"所有人都走调度器"时成立。这是**结构性保证**，不是约定。

## 7. 理由（Rationale）

1. **抖动**：GPU 方案严格满足 §7.6 的意图（零 CPU 逐像素开销）且在资产数、配色灵活性、密度分辨率上全面优于预烘焙。屏幕锚定消除了多粒子重叠的摩尔纹。
2. **breath()**：把安全红线从"人工检查清单"变成"类型系统 + CI + 运行时审计"三道自动防线。相位错开补上了 §9.9 管不到的**叠加亮度**风险。
3. **FX Dispatcher**：§6.7 与 §9.9 是两套**都会阻断特效**的规则，分开放置必然产生死区。三段式管线让"被阻断"成为一个**显式的、有补偿的状态**，而不是一个静默的丢弃。
4. **192 例正交测试**：把 §9.9.5 里两条需要人工核验的验收项变成 CI 里的一条命令。这是本 ADR 里我最看重的一条——**安全约束一旦依赖人去记，它就一定会失效。**

---

## 8. 后果（Consequences）

### 正面

- 抖动零资产、零 CPU 开销、65 级密度、任意配色
- 呼吸脉动有唯一实现，频率上限由类型系统强制，无法绕过
- 发现并修补了 §9.9 管不到的"同相位叠加亮度"风险
- FX 互斥与开关正交由**一个**组件处理，192 例自动化验证
- 顿帧白名单（受击绝不触发）由数据表达，不会被人误加回去

### 负面 / 需偿还

| 代价 | 说明 |
|---|---|
| **FX Dispatcher 是一个新组件，约 400 LOC** | 但它是 §6.7 明确要求的，不做不行 |
| 抖动从"美术可预览的贴片"变成"shader 行为" | 林绘澄无法在 Photoshop 里预览抖动效果。**缓解**：提供一个 dev 面板，实时切换抖动密度 / 锚定模式 / 矩阵大小供她调 |
| `breath()` 的 CI 检查会拦住一些合理的非脉动用法 | 白名单机制 + `// breath-ignore:` 行内豁免注释 |
| 亮度预算审计需要元素上报面积 | UI 元素需额外声明 `area` 字段，少量额外工作 |

## 9. 备选方案（Alternatives Considered）

| 方案 | 结论 | 理由 |
|---|---|---|
| **抖动：Bayer 4×4（§7.6 原议）** | ❌ 否决 | 17 级密度，粒子淡出会出色带 |
| **抖动：蓝噪声（Blue Noise）** | ⚠️ 记录 | 观感上比 Bayer 更"有机"，无固定网格感。但：需预生成大尺寸噪声图（64×64）+ 无法用 8×8 小纹理 REPEAT；且 Bayer 的**规则网格**正是街机硬件的真实外观。**Bayer 更符合 authenticity 目标**。若林绘澄认为 Bayer 网格感太重，可切换（矩阵以纹理形式注入，换图即可） |
| **抖动：物体锚定** | ❌ 否决 | 多粒子重叠产生摩尔纹；水花是 25–40 粒子重叠场景 |
| **呼吸：维持 §9.9.2 的 `sin`** | ❌ 否决 | 极值处不停留，读起来是"摆动"不是"呼吸" |
| **呼吸：允许各处自行实现** | ❌ 否决 | 安全红线不能依赖约定 |
| **FX：无中央调度器，各处自行判断开关** | ❌ 否决 | §5 的冲突案例必然发生，且无法测试 |
| **FX：把开关判断放在互斥之前（先过滤再仲裁）** | ❌ 否决 | 这正是 §5 里冲突案例的成因——被过滤掉的请求不会释放它占的互斥名额 |
| **FX：让所有特效都不互斥（取消 §6.7）** | ❌ 否决 | §6.7 是为概念文档风险 R3（认知过载）服务的，那是设计决策不是技术决策。**若文策渊/林绘澄认为该规则过严，应先改设计再改架构** |
