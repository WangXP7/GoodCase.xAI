## 1. 背景（Context）

林绘澄在 §9.4 提出：原型基准分辨率 **1444×880 不能被 3 整除**，会导致像素缩放出现非整数倍、产生像素抖动。她建议改为 **1440×864**，并列出了整除性证明。主理人把这条列为阻塞项 1，要求我确认。

但 §9.4 真正 unresolved 的不是"选哪个数"，而是**"1440×864 到底是哪一个空间"**。文档里出现了三个互相矛盾的读法：

| §9.4 的表述 | 暗示的含义 |
|---|---|
| "Canvas 显示尺寸（1440×864 或 1444×880）" | 1440×864 = 显示画布 |
| "内部渲染缓冲（低分辨率，如 **480×288** 或 **720×432**）" | 1440×864 ≠ 实际渲染分辨率 |
| "整数倍放大（**2× 或 3×**）" | 放大倍率未定，两个候选都列了 |
| §3.1 概念文档："**鲨鱼体长 168 px（@1440×864）**" | 1440×864 = 美术/设计坐标空间 |
| §3.3 字号层级："8px 网格系统"，字号 12/16/24/32/48/64 | 字号是**设计 px**，但像素字体要求渲染到**整数艺术像素** |

**核心问题：如果"艺术像素"（玩家看到的那个方块）就是设计 px，那么"量化到像素网格"应该量化到 1px；可 §6.7 写的是"步进 **2px** 或整数倍"。这个 2px 从哪来？文档没说。**

这就是我要解决的：把三个空间分开命名，并定死它们之间的倍率。

---

## 2. 决策（Decision）

### 2.1 采纳 1440×864 作为设计分辨率 ✅

**采纳林绘澄的建议。** 我复核了整除性，并补充一条她没提到但很重要的性质：

```
1440 = 2⁵ × 3² × 5
 864 = 2⁵ × 3³

1440 × 864 = 1,244,160 px²  （与 §2.6 面积配额计算中已使用的值一致）
宽高比 = 1440 : 864 = 5 : 3 = 1.667   ← 精确值，不是 16:9.6 的近似
```

| 缩放档 | 结果 | 是否整除 |
|---|---|---|
| 1/2 | 720 × 432 | ✅ |
| **1/3** | 480 × 288 | ✅ |
| 1/4 | 360 × 216 | ✅ |
| 1/6 | 240 × 144 | ✅ |
| 1/8 | 180 × 108 | ✅ |
| 1/9 | 160 × 96 | ✅ |
| 1/12 | 120 × 72 | ✅ |
| 1/16 | 90 × 54 | ✅ |

**补充性质（林绘澄未指出）**：1440×864 是**精确的 5:3**，不是 16:9（1.778）。这带来一个必须提前接受的后果：

> ⚠️ **在 16:9 屏幕上必然出现左右黑边（pillarbox）。**
> 1920×1080 下：`min(1920/1440, 1080/864) = min(1.333, 1.25) = 1.25`
> → 画面 1800×1080，左右各 **60px** letterbox。
> 这是可接受的（占屏宽 6.25%），但**必须在美术出图时按 5:3 构图，不能按 16:9 构图**，否则上线后两侧内容被裁掉。

### 2.2 三层空间模型（本 ADR 的核心贡献）

```
┌─ [L0] DESIGN SPACE ────────────────────────────────────────┐
│  1440 × 864 设计像素                                        │
│  · 所有设计数值、布局、物理量的唯一坐标空间                    │
│  · 鲨鱼体长 168 · 字号 12/16/24/32/48/64 · 安全区 48px       │
│  · 恒定不变，永不随设备改变                                   │
└──────────────────────────┬──────────────────────────────────┘
                           │  ÷ ART_SCALE (=2)
┌─ [L1] ART GRID ──────────▼──────────────────────────────────┐
│  720 × 432 艺术像素（= RT_WORLD 渲染目标）                    │
│  · 玩家眼中"一个方块像素"的真实大小                            │
│  · 所有精灵、UI、粒子位置与尺寸必须落在整数格点上                │
│  · 位移量化单位 = 2 设计 px = 1 艺术像素                       │
└──────────────────────────┬──────────────────────────────────┘
                           │  × 2 NEAREST 整数放大
┌─ [L2] COMPOSITE ─────────▼──────────────────────────────────┐
│  1440 × 864（= RT_POST 后期目标）                             │
│  · CRT 弯曲 / 色差 / 余晖（需连续坐标，必须在高分辨率做）        │
│  · 真 alpha 层：暗角 / 遮罩 / 危险染红                         │
└──────────────────────────┬──────────────────────────────────┘
                           │  fit + NEAREST + letterbox
┌─ [L3] DISPLAY ───────────▼──────────────────────────────────┐
│  视口自适应（DPR 感知），image-rendering: pixelated            │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 ART_SCALE = 2（关键推导）

§9.4 给了两个候选：480×288（1/3）与 720×432（1/2）。**我选 720×432，即 ART_SCALE = 2。**

**决定性证据来自 §3.3 的字号层级。** 像素字体（Press Start 2P 是 8×8 位图）在缩放倍率为非整数时会出现像素错位，§3.4 明令"**禁止对像素字体做非整数倍缩放**"。把 6 个字号分别映射到两个候选网格：

| 层级 | 字号（设计 px） | ART_SCALE=2 → 艺术 px | ART_SCALE=3 → 艺术 px |
|---|---|---|---|
| H0 | 64 | **32** ✅ | 21.33 ❌ |
| H1 | 48 | **24** ✅ | 16 ✅ |
| H2 | 32 | **16** ✅ | 10.67 ❌ |
| H3 | 24 | **12** ✅ | 8 ✅ |
| Body | 16 | **8** ✅ | 5.33 ❌ |
| Caption | 12 | **6** ✅ | 4 ✅ |

**ART_SCALE = 2 时 6/6 全部落在整数格点；ART_SCALE = 3 时只有 3/6。**

**第二条佐证 —— §6.7 的"步进 2px"。** 美术圣经要求位移"量化到像素网格（步进 **2px** 或整数倍）"，但从未解释这个 2 是哪来的。**ART_SCALE = 2 正好解释了它**：1 艺术像素 = 2 设计 px，所以最小合法步进就是 2 设计 px。这条规范在 ART_SCALE=2 下从"经验值"变成"几何必然"。

**第三条佐证 —— 粒子尺寸。** §7.3/§7.4 规定粒子为"**2–5px 硬边方块**"。

- 若 ART_SCALE=3：2 设计 px = 0.67 艺术 px → **小于一个像素，不可能绘制**。
- 若 ART_SCALE=2：2–5 设计 px = **1–2.5 艺术 px** → 最小 1 艺术像素，合法。✅

> 📌 **由此确认一条此前含糊的规范**：粒子尺寸 2–5px 是**设计 px**，最小粒子 = 1 艺术像素。请林绘澄在资产规格中按 1–2.5 艺术 px（即 2–5 设计 px）理解，不要按艺术像素理解。

**第四条佐证 —— 鲨鱼体型。** 168 设计 px ÷ 2 = **84 艺术像素**。§4.1 提到"8×8px 脸"：8×8 艺术 px = 16×16 设计 px，占体长 9.5% —— 对一条鲨鱼是合理的眼部比例。✅

### 2.4 缩放与适配策略

```ts
// L2 → L3：缩放到视口
const fit = Math.min(vw / 1440, vh / 864);
const scale = opt.integerSnap ? Math.max(1, Math.floor(fit)) : fit;
// canvas CSS 尺寸 = 1440*scale × 864*scale，居中，letterbox 填充 #0A0E17
```

**关于非整数缩放的诚实说明**：

> **在任意视口上做完美整数缩放是不可能的**，这不是方案缺陷，是数学事实。
> 1080p 下 fit = 1.25，艺术像素 = 2 × 1.25 = **2.5 设备像素**。

我的处理：

1. **默认允许非整数 fit** —— 1 个艺术像素 ≥ 2 设备像素时，±0.5 设备像素的不规则性低于感知阈值（这也是绝大多数已发售像素游戏的实际做法）。
2. **提供 `integerSnap` 选项**（默认关）给纯净主义者与截图场景，代价是大黑边。
3. **扫描线绝不参与非整数缩放** —— 这是最关键的一条：扫描线在 **L1（720×432 艺术网格）** 上绘制，之后与整幅画面一起被 ×2 整数放大，因此**永远锁死在艺术像素上，永不产生摩尔纹**。若把扫描线放到 L2/L3，1.25 倍非整数缩放会立即产生可见滚动条纹。

### 2.5 降级时**不改** ART_SCALE

美术圣经 §9.3 的降级策略提到"帧率 <40fps → 自动关闭 CRT 至 LITE"。我在此基础上明确一条：

> **RT_WORLD 恒为 720×432，降级时绝不改变。**

理由：改变 RT_WORLD 等于改变 ART_SCALE，会让精灵以 2/3 等非整数比例重采样，**像素画立刻劣化**（这正是 §9.4 想避免的"像素抖动"）。而 720×432 = 311,040 像素，填充率在任何能跑 WebGL 的设备上都不是瓶颈。

**真正的性能开销在 RT_POST（1,244,160 像素）的 CRT 后期 pass 上，而不是世界渲染。** 因此降级轴定义为：

| 档 | CRT 后期 | DPR 上限 | 粒子 | 噪点/余晖 |
|---|---|---|---|---|
| HIGH | FULL | 2.0 | 400 | 开 |
| MED | LITE（仅扫描线+暗角） | 1.5 | 200 | 关 |
| LOW | **OFF（整个 RT_POST pass 跳过）** | 1.0 | 100 | 关 |

LOW 档跳过整个 RT_POST，直接把 RT_WORLD ×2 放大到显示 —— **这是最有效的一档降级，一次性省掉 124 万像素的多重采样后期**。

## 3. 理由（Rationale）

1. **1440×864 的整除性林绘澄已经证明**，且 §2.6 的面积配额计算已经在用这个数——改回去会导致她已完成的定量结论作废。
2. **ART_SCALE=2 是被 §3.3 字号表唯一确定的**，不是我的偏好。字号 6/6 命中整数格点是硬证据。
3. **它反过来解释了 §6.7 的"步进 2px"**，把一条经验规范变成几何必然，消除未来实现时的歧义。
4. **它解释了 §7.3 的粒子尺寸下限**，并暴露出 ART_SCALE=3 会与之矛盾。
5. **扫描线锁在 L1** 是整个方案里收益最高的一条：用几何手段（而非调参）根治摩尔纹。

## 4. 后果（Consequences）

### 正面

- 三层空间命名清晰，设计 / 资产 / 程序三方不会再混淆"px"指的是哪个 px
- "量化到像素网格"有唯一、可执行的定义： **`Math.round(designPx / 2) * 2`**
- 扫描线永久免疫摩尔纹
- 降级不产生像素劣化
- 720×432 的世界渲染填充率极低，为 CRT 后期留足预算

### 负面 / 需偿还

| 代价 | 说明 |
|---|---|
| **16:9 屏幕必有左右黑边（各 60px @1080p）** | 不可消除（5:3 vs 16:9）。美术必须按 5:3 安全区构图 |
| **非整数最终缩放在部分分辨率下存在轻微像素不均** | 已论证低于感知阈值；提供 `integerSnap` 选项 |
| **美术侧需重新表达一批数值** | §3.3 字号、§7.3 粒子尺寸、§6.8 QTE 圆环半径等，需注明单位。见 §7 待确认 |
| 竖屏（移动）体验必然受损 | 5:3 横屏在竖屏手机上 fit 极小。按 §7.2 处理：显示"建议横屏"提示 + 可玩降级 |

### 需立即执行的资产规格变更

| 项 | 原表述 | 新表述（本 ADR 后） |
|---|---|---|
| 精灵绘制网格 | 未定义 | **720×432 艺术网格（1 艺术 px = 2 设计 px）** |
| 位移量化 | "步进 2px 或整数倍" | **步进 = 2 设计 px = 1 艺术 px，或其整数倍**（定义已闭合） |
| 粒子尺寸 | "2–5px" | **2–5 设计 px（= 1–2.5 艺术 px）**，最小 1 艺术 px |
| 图集尺寸 | 1024×1024 / 2048×2048 | 不变，但**图块坐标须为偶数**（对齐艺术网格） |
| 抖动单元 | Bayer 4×4（§7.6） | 见 ADR-004，改为 **Bayer 8×8 @ 艺术网格** |

## 5. 备选方案（Alternatives Considered）

| 方案 | 结论 | 理由 |
|---|---|---|
| **保持 1444×880** | ❌ 否决 | 不能被 3 整除（1444/3=481.33，880/3=293.33），且**不能整除任意 >1 的奇数**，降级档位只有 1/2 与 1/4。§9.4 已论证 |
| **1440×810（16:9）** | ❌ 否决 | 810 不能被 4 整除（202.5），丢掉 1/4、1/8、1/16 三档，而 1/4 恰是降级实际运行区间。§9.4 v1.2 已自我修正删除此选项，**我复核确认该修正正确** |
| **ART_SCALE = 3（480×288）** | ❌ 否决 | 字号 3/6 落在非整数格点（违反 §3.4 禁令）；粒子最小尺寸 2 设计 px = 0.67 艺术 px，**物理上不可绘制** |
| **ART_SCALE = 1（1440×864 即艺术网格）** | ❌ 否决 | 那就没有"像素风"了——1 艺术像素 = 1 设备像素量级，得不到复古颗粒感；且 §9.4 明确要求内部缓冲低于显示分辨率 |
| **可变 RT_WORLD 分辨率做降级** | ❌ 否决 | 会让精灵非整数重采样，像素画劣化。降级改走 CRT 档位（§2.5） |
| **1280×720（16:9，整除性同样良好）** | ⚠️ 记录 | 与 16:9 屏幕完美契合、无黑边。但**会让美术圣经中全部已完成的定量工作作废**（§2.6 面积配额按 1,244,160 px² 算过、§4.1 鲨鱼 168px 是按 8.6 身长跑道推的、§5.3 明度阶梯按 864 高算的）。**重算成本高于接受 60px 黑边。** 若用户强烈反对黑边，这是一条可行路径，但需美术侧全面返工 |

## 6. 常量表（实现唯一真源）

```ts
// src/core/render/constants.ts —— 全项目唯一定义，禁止在别处硬编码
export const DESIGN_W      = 1440;   // 设计空间宽（设计 px）
export const DESIGN_H      = 864;    // 设计空间高（设计 px）
export const ART_SCALE     = 2;      // 1 艺术 px = 2 设计 px
export const RT_WORLD_W    = DESIGN_W / ART_SCALE;  // 720
export const RT_WORLD_H    = DESIGN_H / ART_SCALE;  // 432
export const SAFE_MARGIN   = 48;     // §9.4 UI 安全区（设计 px）
export const LETTERBOX     = '#0A0E17';

// 量化：把设计 px 吸附到艺术网格
export const snapArt = (v: number): number => Math.round(v / ART_SCALE) * ART_SCALE;
```
