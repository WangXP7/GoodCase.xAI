## 1. 背景（Context）

美术圣经 §9.6 给出的建议是「**Canvas2D 足够**（本项目无 3D、粒子 <500），若需 CRT 弯曲/色差 shader 则用 WebGL 后期 pass」。主理人把这条列为**阻塞项**，要求我在写第一行渲染代码前定案。

要裁决的不是"哪个更好"，而是：**本项目的视觉身份，是否真的需要 Canvas2D 给不了的东西？**

把美术圣经里所有"必须有"的效果列一遍，逐条问 Canvas2D 能不能给：

| # | 效果 | 出处 | Canvas2D 可行性 |
|---|---|---|---|
| 1 | **CRT 屏幕弯曲**（桶形畸变，曲率 0.08–0.12） | §6.5 | ❌ 不可行。Canvas2D 无逐像素重映射。CSS `perspective()` 只能做平面透视，不是桶形；`border-radius` 是裁切不是形变 |
| 2 | **色差**（RGB 通道水平偏移，中心 0 → 边缘 ±3px） | §6.5 | ⚠️ 理论可行但代价高：3 次全屏 `drawImage` + `globalCompositeOperation='lighter'` + 通道遮罩 = **每帧 3 次全屏合成** |
| 3 | **有序抖动**（全项目替代 alpha 淡出） | §7.6 | ❌ 只能预烘焙贴片或 CPU 逐像素。`putImageData` 逐像素在 60fps 下完全不可行 |
| 4 | **整屏调色板切换（色闪）** | §6.6 | ❌ 需要逐像素颜色重映射。Canvas2D 只能"再画一遍不同颜色的图"，意味着**双倍素材** |
| 5 | **荧光余晖**（高亮像素外扩 1px） | §6.5 | ❌ 相当于一次卷积，CPU 上太慢 |
| 6 | 扫描线、暗角、噪点 | §6.5 | ✅ 可行（预烘焙 pattern / 渐变图叠加） |

**结论：6 项里有 4 项 Canvas2D 做不到，1 项勉强但极贵，只有 1 项便宜。**

## 2. 决策（Decision）

> ## 采用 **WebGL2**（WebGL1 回退），渲染层为**自研薄封装**（约 1.2k LOC），**不引入 PixiJS / Phaser 等 2D 引擎**。
>
> 同时采纳 **Canvas / DOM 混合分层**：
> - **世界与实体 → WebGL Canvas**（含 CRT 后期）
> - **HUD 与全部菜单 → DOM 覆盖层**（不在 canvas 内绘制）

### 2.1 为什么必须是 WebGL：量化论证

**色差这一项就足以定案。** 按 §6.5，色差需要把 R/G/B 三通道分别以 −3px / 0 / +3px 偏移后相加：

```
Canvas2D 方案：3 次全屏 drawImage + 混合
  = 3 × (1440 × 864) 像素写入/帧
  = 3,732,480 像素写入/帧
  = 223,948,800 像素写入/秒 @60fps
```

这还不算通道遮罩本身也要各一次全屏操作。**仅色差一项就吃掉中低端移动 GPU 的大部分填充率预算**，而且它是**纯浪费**——同一件事在 WebGL 里是**一次全屏 pass 里的 3 次纹理采样**，成本约为 Canvas2D 的 1/20。

**绘制调用是第二个决定性因素。** §9.3 定同屏 400 粒子，加上实体、敌人、背景元素，单帧绘制对象约 500+。

| | Canvas2D | WebGL（自研批处理器） |
|---|---|---|
| 单帧绘制调用 | ~500（每个 `drawImage` 一次状态切换） | **2–4**（按混合模式分桶批合） |
| 状态切换开销 | 500 次/帧 | 4 次/帧 |
| 400 粒子的填充 | CPU 光栅化或逐次 GPU 上传 | 一次 `bufferSubData` + 1 次 draw |

**第三，抖动（ADR-004）在 WebGL 里是 3 行 GLSL，在 Canvas2D 里是"按颜色 × 密度预烘焙的组合爆炸"**——16 色 × 17 级密度 = 272 张贴片，且每次改配色都要重烘焙。

### 2.2 为什么不用 PixiJS / Phaser

这是本 ADR 里最需要辩护的一条，因为它与"开发效率"直接冲突。

| 候选 | 体积 (gzip) | 评估 |
|---|---|---|
| **Phaser 3** | ~450 KB | ❌ 否决。带来 Arcade Physics / Scene / Tween 三套我们会重写或绕开的系统（见 ADR-006 不用物理引擎）；后处理管线（v3.60+ PostFXPipeline）比自研更不灵活；包体超标 |
| **PixiJS v8** | ~180 KB | ⚠️ **备选**。精灵批合、图集加载、RenderTarget 管理成熟，能省约 1 周样板代码 |
| **自研 WebGL2** | **0 KB** | ✅ **采用** |

**否决 PixiJS 的三条理由**：

1. **我们 90% 的精灵都要走自定义 shader。** ADR-005 要求所有精灵走「索引色 + 调色板 LUT」，ADR-004 要求粒子走「抖动阈值 discard」。Pixi 的自动批合**只对内置材质生效**——一旦挂自定义 shader，批合失效，我们仍然得自己写批处理器。**也就是说，Pixi 最能帮我们的那部分（批合），恰好在我们必须自定义的领域里失效。**
2. **Pixi 最省事的部分，我们改用 DOM 了。** 2D 引擎里工作量最大的一块通常是文字渲染（位图字体图集、字距、换行）。本 ADR 把 HUD 与菜单全部交给 DOM（见 §2.3），这部分工作量直接归零，Pixi 的剩余价值只剩"图集解析 + 纹理上传 + RT 管理"——合计约 200 行自研代码。
3. **WebGL2 单通道纹理（R8）在 Pixi v8 里不是一等公民。** ADR-005 的索引色方案依赖单通道纹理，走 Pixi 需要绕它的 `TextureSource` 格式抽象，风险不可控。

**净账**：Pixi 省约 1 周，代价是 +180 KB、一份必须绕过的抽象、以及 ADR-005 的实现风险。自研多花约 1 周，换来 0 依赖与完全可控。**在"整个视觉身份就是渲染器"的项目里，我选择拥有它。**

### 2.3 HUD 与菜单走 DOM：一条被低估的架构决策

**决策**：HUD（分数 / ALARM / COMBO / 体力 / QTE 圆环）与全部屏幕（Title / Pause / Results / Options）用 **HTML + CSS** 实现，作为 canvas 之上的覆盖层。

| 收益 | 说明 |
|---|---|
| **可访问性质变** | 文本是真实文本 → 屏幕阅读器可读、浏览器缩放可用、系统字体替换可用。这直接把美术圣经 §9.8 的 **Standard 级**从"要做很多工作"变成"基本免费" |
| **文本缩放 3 档免费** | §9.8 要求 100/125/150% 三档——DOM 改一个 CSS 变量即可；canvas 内做要重排全部布局 |
| **中文字体不再是性能问题** | §3.2 的中文字体子集化（~80 KB）在 DOM 里正常工作，不需要位图字体图集 |
| **零字体资产** | 省掉一整套位图字体 sprite（约 200+ 字形） |
| **开发效率** | 菜单用 CSS 布局比手写 canvas UI 快一个数量级 |

**代价与缓解**：

| 代价 | 缓解 |
|---|---|
| HUD 吃不到 CRT 桶形弯曲 | **可接受**：曲率主要作用在屏幕边缘，而 §9.4 规定 UI 安全区距边 ≥48px（≈3–5% 裁切区）。**安全区内的曲率形变小于 1 个艺术像素**，肉眼不可辨 |
| HUD 吃不到扫描线 | **用 CSS 覆盖层补偿**：一层 `repeating-linear-gradient` 扫描线 + 径向渐变暗角，**盖在 canvas 与 DOM 之上**，两者视觉统一。该层随 `opt.crt` / `opt.jitter` 开关联动 |
| DOM 布局与 canvas 缩放需同步 | 覆盖层容器复用**同一个 fit 变换**（CSS `transform: scale()` + 居中），缩放系数由渲染层唯一产出，DOM 只消费 |

### 2.4 UI 层结构

```
<div id="stage">                          ← 与 canvas 同尺寸，共享 fit 变换
  <canvas id="gl">                        ← WebGL2：世界 + 实体 + 粒子 + CRT 后期
  <div id="hud">...</div>                 ← DOM：游戏中 HUD
  <div id="screens">...</div>             ← DOM：Title / Pause / Results / Options
  <div id="crt-overlay"></div>            ← CSS：扫描线 + 暗角（盖在所有内容之上）
</div>
```

`prefers-reduced-motion` 与 5 个开关（§9.9.1）通过 `<html>` 上的 class 与 CSS 变量统一下发，`#crt-overlay` 与 WebGL 后期读同一份设置。

## 3. 理由（Rationale）

1. **视觉身份即渲染器。** 本作最独特的三件事——硬边像素、有序抖动、整屏调色板切换——全部是渲染层行为。放弃对渲染层的控制等于放弃视觉身份的控制权。
2. **性能是功能。** §9.3 的 400 粒子预算 + §6.5 的 FULL 档 CRT 后期，在 1440×864 下对 Canvas2D 是不现实的；WebGL 让"高端机开 FULL、低端机关后期"成为可行的降级轴（见架构文档 §13）。
3. **90–150 秒单局的稳定性来自确定性**。自研渲染层可以做严格的"热路径零分配"（对象池 + 预分配顶点缓冲），避免 GC 尖峰导致的掉帧。通用引擎的临时对象分配是我们控制不了的（见架构文档 §17 控制清单）。
4. **包体是硬约束。** 纯网页即开即玩，首屏 JS 预算 ≤250 KB gzip（架构文档 §13）。180 KB 的引擎会挤掉这个预算的 72%。

## 4. 后果（Consequences）

### 正面

- 色差 / 弯曲 / 余晖 / 抖动 / 调色板切换**全部可行且几乎免费**
- 单帧绘制调用从 ~500 降到 **2–4**
- 首屏 JS 预算从 180 KB 降到 **~0 KB**（渲染层自研计入业务代码）
- HUD 可访问性达到 **Comprehensive** 级，成本接近零
- 完全掌控内存分配 → 无 GC 尖峰 → 单局帧率稳定

### 负面 / 需偿还的代价

| 代价 | 缓解措施 |
|---|---|
| **自研渲染层约 1.2k LOC，工期 +1~2 周** | 见 §5 Spike 闸门；不通过则降级 PixiJS |
| **需自建批处理器** | 只需支持"纹理四边形 + 两种混合模式"，约 250 行 |
| **WebGL 上下文丢失（移动端切后台）需处理** | 必须实现 `webglcontextlost` / `restored` 恢复路径，重建所有 GL 资源（约 80 行）。**列为 P0 必做项** |
| **WebGL1 回退需额外 shader 变体** | 用 GLSL ES 1.00 写 shader，WebGL2 下通过 `#version 100` 兼容运行；**不引入 WebGL2 专属特性**，一套代码通吃 |
| **团队需具备 WebGL 调试能力** | 提供 dev 调试面板（架构文档 §16） |

### 中性 / 需持续管理

- 依赖浏览器 WebGL 支持率：WebGL2 ≈ 96%，WebGL1 ≈ 99%（caniuse 2026）。**低于 WebGL1 的设备不做支持**，直接显示"浏览器不支持"页（无降级渲染路径，避免维护两套）。

## 5. Spike 闸门（Go / No-Go Gate）

**这是本 ADR 最重要的执行条款。** 自研渲染层是新方案，必须先用最小代价证伪。

> **Spike 目标（5 个工作日）**：用 1 张测试图集，跑通完整链路
> 1. 索引色纹理（R8 / 单通道）上传 + 调色板 LUT 采样
> 2. 精灵批合（≥1000 个四边形，2 个绘制调用）
> 3. 双 RT 管线：RT_WORLD(720×432) → ×2 NEAREST 放大 → RT_POST(1440×864) → CRT 后期（弯曲 + 色差 + 扫描线）→ 显示
> 4. 抖动 discard（Bayer 8×8，屏幕锚定）
> 5. 整屏调色板切换（LUT 换贴图，1 次绑定）+ 色盲模式切换
> 6. 在一台中低端安卓机上实测 ≥55fps

| 判定 | 行动 |
|---|---|
| ✅ **6/6 通过** | 按本 ADR 执行 |
| ⚠️ **3–5 项通过** | 延长 3 天修复；仍不达标 → 转备选方案 B |
| ❌ **≤2 项通过** | 立即转备选方案 B |

**备选方案 B（已设计就绪）**：改用 **PixiJS v8（锁定 `preference: 'webgl'`）**，精灵改为**预着色 RGBA 纹理**（放弃逐精灵 LUT），色闪与色盲模式改用**全屏 LUT Filter** 实现（牺牲逐精灵调色能力，但保住 90% 视觉效果）。首屏 JS 增至约 200 KB gzip，需削减其他预算或接受首屏变慢。

## 6. 备选方案（Alternatives Considered）

| 方案 | 结论 | 否决理由 |
|---|---|---|
| **A. Canvas2D + CSS filter 近似** | ❌ 否决 | §6.5 的 5 项效果中 4 项不可行；色差一项的填充率成本（2.24 亿像素/秒）在中低端机必然掉帧；CSS filter 强制每帧合成，在移动端常**比 WebGL 更慢** |
| **B. PixiJS v8** | ⚠️ 保留为 Spike 失败回退 | 见 §2.2：批合在自定义 shader 下失效，+180 KB，R8 纹理非一等公民 |
| **C. Phaser 3** | ❌ 否决 | ~450 KB 超包体预算；Arcade Physics / Scene / Tween 与 ADR-006（不用物理引擎 + 自研固定步长）重叠，会形成两套时间系统 |
| **D. Three.js（正交相机 2D）** | ❌ 否决 | 为 3D 场景图设计，2D 精灵批合需 `InstancedMesh` 手搓；~170 KB 却用不上 95% 的功能 |
| **E. WebGPU** | ❌ 否决（当前） | Safari 支持尚不完整，覆盖率不足以支撑"即开即玩"。**列为 Epic 层可选优化**，渲染层接口预留 |
| **F. Canvas2D 出图 + 砍掉弯曲与色差** | ⚠️ 诚实记录为**真实可选路径** | 若用户愿意放弃桶形弯曲与色差，Canvas2D + 预烘焙扫描线/暗角是可行的，**可省约 2 周工期**。代价：CRT 观感退化为"扫描线滤镜"，失去 §6.5 的核心质感。**这是唯一一个"降低美术目标换工期"的选项，需要用户拍板，不是我能替美术做的决定。** |
