> **§6.8 整节演出依赖本 ADR。** 林绘澄把它标为 🔴 阻塞，是对的——搁浅是本作的招牌机制，而它目前只有一句"停留超时且速度不足"的自然语言描述，没有可实现的判据。本 ADR 把它变成可执行的状态机。

---

## 1. 背景（Context）

概念文档 §3.1 对搁浅的完整描述只有一句：

> "在沙滩区停留超过阈值时间且速度不足时，鲨鱼侧翻搁浅，进入连打 QTE。"

这句话里有 **4 个未定义项**，任何一个都会在实现时产生分歧：

| 未定义 | 问题 |
|---|---|
| **"沙滩区"** | 是 X 坐标区间？还是"水太浅"？两者在动态水面下不等价 |
| **"停留"** | 停留在什么上？沙面？还是只要进入该区域就计时？ |
| **"速度不足"** | 阈值是多少？标量速度还是水平分量？ |
| **"超过阈值时间"** | 多少秒？ |

同时还有一个更根本的问题没人回答：**四层水体（深海/浅滩/冲浪区/沙滩）的边界到底由什么定义？** §5.3 只给了明度与配色，没给几何。而 §5.0 明确这是横向卷轴（视差系数 0.05–1.6），所以区域是世界坐标里的 X 区间——但沙滩的边界显然不是一条竖线，它是**海床升出水面的那条线**。

一个 Bug 被设计化成招牌机制，前提是它有**确定、可读、可学习的触发条件**。否则它还是一个 Bug，只是多了个 QTE。

---

## 2. 决策（Decision）

### 2.1 几何模型：海床剖面 + 水面线，区域由"水深"导出

**不手工划定四个 X 区间，而是从海床剖面导出它们。** 这是本 ADR 最重要的一条。

```
        y=0 ─────────────────────────────────────────────┐
             ░░░ 天空（§5.3.5）░░░                        │
   ────────── 水面线 waterLineY(x,t) ≈ 105 ──────────    │  ← 含 ±6px 波浪
             ～～～～～～～～ 水 ～～～～～～╲             │
                                          ╲              │
   深海 DEEP              浅滩 SHALLOW      ╲冲浪区 SURF  │沙滩 BEACH
   海床 = 864             海床抬升中         ╲ ▒▒▒▒▒▒▒▒▒▒▒│▒ 干沙（实体）
   ──────────────────────────────────────╲  ▒▒▒▒▒▒▒▒▒▒▒│▒▒▒▒▒▒▒▒
        y=864 ────────────────────────────╲▒▒▒▒▒▒▒▒▒▒▒▒│▒▒▒▒▒▒▒▒┘
        x=0                          shoreX↑        x=2160
                                   （潮线 TIDELINE：海床 = 水面）
```

**定义**：

```
seabedY(x)      海床（固体上表面）的 y 坐标，静态，由控制点 + Catmull-Rom 插值
                加载时烘焙成 SEABED_LUT[]（每 8 设计 px 一采样），运行时 O(1) 查表

waterLineY(x,t) 水面 y 坐标 = WATER_BASE + wave(x, t)
                WATER_BASE = 105（设计 px），wave 振幅 ±6px、波长 180px、速度 40px/s（§5.3.2）

waterDepth(x,t) = seabedY(x) − waterLineY(x, t)      // 该 x 处的水柱厚度
```

**四个区域由 `waterDepth` 的静态部分（不含波浪）划分**：

| 区域 | 判据（用静态 `seabedY`，不用含水面的 depth） | 明度 | 说明 |
|---|---|---|---|
| **DEEP** | `waterDepthStatic(x) ≥ 400` | 8% | 含 BANK 结算点 |
| **SHALLOW** | `120 ≤ depth < 400` | 28% | 过渡带 |
| **SURF** | `0 < depth < 120` | 55% | 副循环主场景，破浪带 |
| **BEACH** | `depth ≤ 0`（海床 ≥ 水面） | 82% | 干沙，唯一可搁浅区 |

> ⚠️ **关键分离**：**区域归属用静态海床，接触判定用动态水面。**
> - 区域（Zone）决定：ALARM 增减速率、敌人生成、视觉明度、BANK 可用性 → **必须稳定**，否则潮汐一动，敌人生成表就抖动。
> - 接触/搁浅判定用**含水面的实时 depth** → 让潮线与波浪真正影响操作手感。
>
> 这个分离让"潮线"既是一个可玩的物理边界，又不会让游戏系统在边界上反复横跳。

**区域表在加载时烘焙成 `ZONE_LUT[]`（每 8 设计 px 一项），运行时零计算。** 加 8 设计 px 迟滞（hysteresis）防止边界抖动。

### 2.2 海床剖面控制点（设计 px，y 向下）

MVP 默认值，关卡可调，存 `levels/beach_01.json`：

| x | 0 | 576 | 864 | 1080 | 1296 | 1512 | 1728 | 1944 | 2160 |
|---|---|---|---|---|---|---|---|---|---|
| **seabedY** | 864 | 864 | 800 | 660 | 480 | 300 | 160 | 104 | 96 |

- `WORLD_W = 2160`（1.5 屏），相机夹取范围 `[0, 720]`
- 由此导出 `shoreX ≈ 1746`（海床穿过 y=105 处）
- 干沙区：`x ≥ shoreX`，`y ≥ seabedY(x)` 为实体

> **给文策渊**：关卡 GDD 只需给这张 9 点控制表，不要给逐点坐标。改这张表 = 改整个关卡的地形与四区分界，回跑 `PH1-R1-numerical-sandbox.md`。

### 2.3 单位制（填掉一个文档里的空档）

概念文档混用 "6 m/s" 与 "168 px"，从未给出换算。**我定死一个**：

```
PX_PER_M = 32    // 1 米 = 32 设计 px = 16 艺术 px
```

| 量 | m/s | 设计 px/s | 艺术 px/s | 每帧（60Hz，设计 px） |
|---|---|---|---|---|
| 巡游 Cruise | 6 | **192** | 96 | 3.20 |
| 冲刺 Dash | 14 | **448** | 224 | 7.47 |

选 32 的理由：巡游与冲刺在**设计空间与艺术网格两个空间都落在整数**（192/96 与 448/224），且鲨鱼 168 px = 5.25 m 落在真实大白鲨体长区间（4–6 m）。备选 33 同样可行但数值不整。

### 2.4 搁浅状态机

```
                    ┌──────────────────────────────────────┐
                    │                                      │
   [SWIMMING] ──进入 BEACH 且 grounded 且 |v| < V_TH──▶ [STRAND_ACCUM]
        ▲                                                  │
        │                                          progress ≥ T_STRAND
        │ 离开 BEACH / 不再 grounded / 冲刺逃脱            │
        │                                                  ▼
        └──────────── QTE 成功 ◀──── [BEACHED / QTE] ──▶ [DEAD]
                                            │
                                     progress ≥ T_WARN
                                            ▼
                                     （仅进入一次）
                                     [STRAND_WARNING]  ← 预警：拖尾扬尘 + 音 sting + HUD 提示
```

**唯一真源伪码**（每个逻辑帧执行）：

```ts
// 常量（设计 px / 秒）
const V_TH      = 96;    // 速度阈值 = 3 m/s = 0.5 × 巡游速度
const T_STRAND  = 1.2;   // 有效停留时间阈值（秒）
const T_WARN    = 0.72;  // 预警触发点 = 60% × T_STRAND
const REC_IN    = 2.0;   // 沙滩内但速度足够 → 回落倍率
const REC_OUT   = 4.0;   // 离开沙滩区 → 快速回落倍率

function updateStranding(shark, dt) {
  const zone     = zoneAt(shark.x);                    // ZONE_LUT 查表，O(1)
  const grounded = shark.bottomY >= seabedY(shark.x);  // 接触固体上表面
  const speed    = Math.hypot(shark.vx, shark.vy);     // 标量速度

  if (zone === Zone.BEACH && grounded && speed < V_TH) {
    // 速度越低，累积越快；达到 V_TH 时累积速率为 0
    const rate = 1 - speed / V_TH;                     // ∈ (0, 1]
    shark.strandProgress += dt * rate;
  } else if (zone === Zone.BEACH) {
    shark.strandProgress -= dt * REC_IN;
  } else {
    shark.strandProgress -= dt * REC_OUT;
  }

  shark.strandProgress = clamp(shark.strandProgress, 0, T_STRAND);

  if (shark.strandProgress >= T_STRAND) enterBeached();
  else if (shark.strandProgress >= T_WARN) enterStrandWarning();  // 幂等
}
```

**读数解释**（这几条是给策划和 QA 的，不是给编译器的）：

| 情境 | 结果 |
|---|---|
| 完全静止停在沙滩 | **1.2 s** 搁浅 |
| 以 1.5 m/s 缓慢蹭沙 | **2.4 s** 搁浅（累积速率减半） |
| 以 ≥3 m/s 滑过沙滩 | **不累积**，且以 2× 速率回落 |
| 冲上沙滩后立刻掉头回水 | 离区后以 4× 速率回落，**0.3 s** 清零 |

### 2.5 `STRAND_WARNING` 预警态（本 ADR 的设计增量）

> **我加了一个美术圣经与概念文档都没有的状态。** 理由见 §3.2：**没有预警，搁浅就还是一个 Bug。**

在 `progress ≥ 0.72s` 时进入（幂等），持续到脱困或搁浅：

| 通道 | 表现 | 目的 |
|---|---|---|
| 视觉 | 鲨鱼尾部拖沙（4 粒子/次拍打，`#C7CFD8`），身体轴线开始向 −8° 倾斜 | 让玩家"看见"自己正在陷进去 |
| HUD | 鲨鱼上方出现**挣扎提示图标**（复用 §6.8.4 的连打提示图形），**2Hz 呼吸**（走 ADR-004 的 `breath()`） | 明确告知"现在按冲刺还能救" |
| 音频 | 一声低沉 sting（与搁浅落地音同源，音量 40%） | 余光通道 |
| 玩法 | **此窗口内按下冲刺（消耗 1 格体力）可立即清零 progress 并把鲨鱼推回水中** | **这就是技巧轴** |

### 2.6 QTE 逃脱规格

| 项 | 值 | 说明 |
|---|---|---|
| 时间窗口 | **2.5 s** | 与 §6.8.4 外环收缩 140px→80px 同步 |
| 需要有效输入 | **6 次** | 概念文档 §3.1 的示意值 |
| 最小输入间隔 | **100 ms** | 防连点器与物理连打宏；6 次仅需 1.5 s，留 1.0 s 余量 |
| 进度衰减 | **无** | 进度只增不减。§6.8.4 的圆环已用"收缩半径"表达时间压力，再叠进度衰减会变成双重惩罚 |
| 接受的输入 | `Space` / `Enter` / **画布内任意 `pointerdown`** / 触屏任意点按 | 满足"单指可玩"与键盘可玩 |
| 排除的输入 | `Escape` / `P`（暂停）、`M`（静音） | 防止误触退出 |
| ALARM | QTE 期间 **+8 /s** | 2.5 s 满窗 = +20，与一次捕食同量级 |
| 可访问性档 | **3 次输入 / 3.5 s** | 由 `opt.qteAssist` 或 `prefers-reduced-motion` 自动启用 |
| 成功 | `breach` 动画 + L1 水花 + **顿帧 0.08 s** + 震屏 6px + 围观者后退 20px | 沿用 §6.8.5 |
| 失败 | 死亡，画面降饱和至灰白 | §6.8.5 |

**QTE 期间输入不被顿帧吞掉**：顿帧只冻结逻辑推进，输入采集照常（架构文档 §8.4）。

### 2.7 碰撞层与矩阵

**形状只用 AABB。** 鲨鱼的旋转（S 波、冲浪 −65°）**纯视觉**，碰撞盒始终保持轴对齐，尺寸取旋转后的外接矩形。理由：旋转 OBB 会让"擦边"判定变得不可预测，而街机游戏需要玩家能靠肌肉记忆预判判定。

| 层 | 位 | 内容 | 是否阻挡 |
|---|---|---|---|
| `L_WORLD` | 1<<0 | 海床、岩石、沙堡、轮胎 | ✅ 阻挡 |
| `L_SHARK` | 1<<1 | 玩家 | — |
| `L_PREY` | 1<<2 | 游客（泳客 / 冲浪者） | ❌ 触发（咬合判定） |
| `L_ENEMY` | 1<<3 | 救生员浮标、摩托艇、捕鲨队弹体 | ❌ 触发 |
| `L_PICKUP` | 1<<4 | 收集物（瓶子 / 星星） | ❌ 触发 |
| `L_HAZARD` | 1<<5 | 探照灯锥、渔网 | ❌ 触发 |
| `L_ZONE` | 1<<6 | SURF / DEEP / BANK 触发器 | ❌ 触发 |

**碰撞矩阵**（✅ = 检测，空 = 不检测）：

|  | WORLD | SHARK | PREY | ENEMY | PICKUP | HAZARD |
|---|---|---|---|---|---|---|
| **SHARK** | ✅ | — | ✅ | ✅ | ✅ | ✅ |
| **PREY** | ✅ | ✅ | — | — | — | — |
| **ENEMY** | ✅ | ✅ | — | — | — | — |

- 粒子**完全不参与碰撞**，且不在碰撞系统里分配（走独立对象池）
- 敌人之间、猎物之间**互不检测**（省 90% 的配对）

**扫掠 AABB（CCD）**：冲刺 448 设计 px/s → 单帧位移 7.47 设计 px ≈ 3.7 艺术 px。对渔网这类 1px 细线必须做扫掠，否则必然穿透。**只对 `L_SHARK` vs `L_HAZARD` / `L_WORLD` 做扫掠**，其余用离散 AABB（物体尺寸远大于单帧位移）。

**宽阶段**：`n ≤ 120`（实体上限，见架构文档 §13），暴力两两检测 ≤ 7,140 对/帧，实测远低于预算。**不引入空间划分**——加网格是过早优化；若在剖析中成为热点，再补均一格（128 设计 px）。

### 2.8 冲浪模式（副循环入口）判定

概念文档 §4.3："贴浪面自动进入"。补上判据：

```
进入 SURF 模式 ⟺ zone(x) ∈ {SURF}
             ∧ |shark.centerY − waterLineY(x,t)| ≤ 24 设计 px   （贴浪带）
             ∧ |vx| ≥ 150 设计 px/s                              （约 4.7 m/s）
退出 ⟺ 任一条件不满足，或离开 SURF 区
```

`SURF_BAND = 24 设计 px = 12 艺术 px`。

## 3. 理由（Rationale）

### 3.1 为什么用"水深"而不是"X 区间"定义四层水体

1. **它让"潮线"成为真的。** 本作叫《潮线 TIDELINE》。如果沙滩边界是一条硬编码的 X 竖线，那"潮线"只是个名字；用海床与水面求交，潮线就成了一个**物理上真实存在、随波浪轻微呼吸**的边界——玩家可以学会"蹭着潮线走"。
2. **它消除了两处数据不一致的风险。** X 区间与海床剖面是两份数据，改地形时必然漏改其一。单一真源（`seabedY`）意味着关卡设计只需维护一张 9 点表。
3. **它让搁浅的几何直觉成立。** 鲨鱼必须**先上浮、再冲上沙坡**才可能搁浅——这解释了为什么搁浅是"冲过头"的惩罚，而不是"游到了某个 X"。

### 3.2 为什么必须加 `STRAND_WARNING`（设计增量）

概念文档 §3.1 说搁浅是"设计化的 Bug"，§6.8 说要按"名场面"标准做。**但名场面的前提是玩家觉得自己活该，而不是被系统坑了。**

没有预警时：玩家在沙滩上减速 → 1.2 秒后突然进入 QTE → 玩家的第一反应是"什么？为什么？" → 这是 Bug 的体验，不是招牌机制的体验。

有预警时：玩家看到拖沙 + 听到 sting + 看到冲刺提示 → **有一个 0.48 秒的窗口可以自救** → 如果没反应过来才搁浅 → **这是"我失误了"的体验**。

**这一条直接把沙盘里的 `p_beach` 从一个概率变成一个技巧函数**（见 §6 给文策渊的交接）。

### 3.3 为什么用标量速度而不是水平分量

鲨鱼可能贴着沙坡"向上爬"（vy 大而 vx 小）。若只看水平分量，玩家垂直撞沙会被判为"速度足够"从而永不搁浅——这是一个可被利用的漏洞。用标量速度闭合这个洞。

### 3.4 为什么 QTE 进度不衰减

§6.8.4 已经用**收缩外环（140→80px）**表达了时间压力，这是"剩余可能性"的视觉隐喻。再叠加进度衰减等于对同一个信息施加两次惩罚，会让圆环的语义变成"你不但要快，还不能停"——与"可能性正在归零"的叙事冲突。**时间到就是时间到，够了。**

## 4. 后果（Consequences）

### 正面

- 搁浅有了**唯一、可测、可调**的判据，QA 可以写确定性用例
- 四层水体从"美术概念"变成"从地形导出的几何"，关卡与美术不会再对不上
- 单位制（PX_PER_M = 32）闭合，概念文档的 m/s 与美术圣经的 px 可以互相换算
- 预警态把搁浅从"随机惩罚"变成"可练的技巧"，直接支撑 R1 沙盘的 `p_beach` 技巧曲线
- 碰撞层矩阵明确，敌人/猎物之间零配对，性能可控

### 负面 / 需偿还

| 代价 | 说明 |
|---|---|
| **海床剖面需要美术与关卡共同调** | 地形形状直接影响四区分界与手感，需要 2–3 轮迭代。**列为 P0 的可调常量，不要写死** |
| **Catmull-Rom 剖面 + LUT 烘焙** | 约 60 行代码 + 一个构建期/加载期烘焙步骤。可接受 |
| 区域迟滞（8 设计 px）增加一点复杂度 | 必要，否则潮汐会造成 ALARM 速率抖动 |

### 中性

- `shoreX` 是**导出量**不是配置量。改地形 → 潮线自动移动 → 需回跑沙盘。

## 5. 备选方案（Alternatives Considered）

| 方案 | 结论 | 理由 |
|---|---|---|
| **四个 X 区间硬编码** | ❌ 否决 | 与海床剖面两份数据必然漂移；"潮线"变成摆设；沙滩边界会是一条垂直的、视觉上无法解释的线 |
| **用物理引擎（Matter.js / Planck.js）** | ❌ 否决 | 见 ADR-006。简言之： solver 非确定性会破坏可测试性与回放，且我们要的只是 AABB + 海床扫掠，约 300 行 |
| **搁浅判定只看 X（进入沙滩即计时）** | ❌ 否决 | 鲨鱼高速掠过沙滩不应搁浅——那会让"冲浪逃生"路径完全无法走通，直接破坏 R1 沙盘的平衡 |
| **不做预警态** | ❌ 否决 | 见 §3.2。会让招牌机制退化成"看起来像 Bug 的随机死亡" |
| **QTE 进度随时衰减** | ❌ 否决 | 见 §3.4。与 §6.8.4 圆环的语义冲突，且双重惩罚 |
| **用多边形碰撞（海床为多边形）** | ⚠️ 记录 | 更精确，但 AABB + 高度场对本作够用，且高度场（`seabedY(x)`）更简单、更快、更容易让关卡设计师用一张表描述 |
| **世界宽度 1440（单屏无卷轴）** | ⚠️ 记录为真实选项 | 单屏能让"危险梯度 = 屏幕左右"这条支柱最强，且搁浅构图稳定。但 §5.2 明确给了视差系数 0.05–1.6，说明美术侧已按卷轴设计。**我采用卷轴 + 1.5 屏（2160）作为折中**；若文策渊 prefer 单屏，改动成本很低（改一个常量 + 相机夹取为 0） |

## 6. 给文策渊的交接（重要）

### 6.1 `p_beach` 不是一个概率，是一个技巧函数

R1 沙盘（`PH1-R1-numerical-sandbox.md` §1.3）把搁浅风险建模为一个标量：

```
p_beach = 0.03（专家）/ 0.15（新手）
```

**按本 ADR 的设计，它实际由三个可调旋钮决定**：

```
p_beach = f( T_WARN, N_qte, 玩家在预警窗口内的反应率 )
```

| 旋钮 | 默认值 | 影响 |
|---|---|---|
| `T_WARN`（预警窗口时长） | 0.48 s（= T_STRAND − T_WARN 阈值） | 越长越容易救，直接线性影响 `p_beach` |
| `N_qte`（QTE 需要输入数） | 6 次 / 2.5 s | 越难越容易失败 |
| 冲刺逃脱的体力代价 | 1 格 | 决定是否"总能靠体力买命" |

**这比一个抽象概率好得多**：它是三个可以被 playtest 直接观测和调节的量，而且"新手 0.15 → 专家 0.03"可以解释为"新手注意不到预警，专家次次在预警内冲刺脱身"。

**建议**：Phase 2 的 ALARM / 移动系统 GDD 里，把 §1.3 表格中的 `p_beach` 改为引用本 ADR 的三个旋钮。

### 6.2 冲上沙滩必须"先上浮"

因为海床是实体，鲨鱼在深度上会**撞到沙坡**，无法从深水直接水平冲进干沙区。它必须先上浮到水面附近，再冲上沙坡。

> **这是一个玩法推论，也是一条设计约束**：如果 GDD 里有"从深水直接冲上沙滩叼走游客"的设计，它在本几何下**不成立**，需要先设计"上浮 → 冲坡"的两段式路径。

### 6.3 搁浅构图需要相机配合（需林绘澄确认）

§6.8.4 规定 QTE 圆环位于**屏幕正中央**。但在卷轴下，鲨鱼搁浅位置约在 `x ≈ 1760–1900`，相机夹取后其屏幕 x ≈ **1040–1180**，与圆环（x=720）相距约 320–460 px —— 圆环与鲨鱼会分处画面两侧，§6.8.6 要的"一眼看懂"构图会散掉。

**我的建议（二选一，请林绘澄定）**：

| 方案 | 说明 |
|---|---|
| **A（我推荐）** | 搁浅瞬间相机在 0.35 s 内缓推，把鲨鱼送到画面水平 **65%** 处（屏幕 x ≈ 936）并锁定。圆环仍在中央，与鲨鱼形成"左圆环 / 右鲨鱼"的稳定二联构图 |
| **B** | 圆环改为**锚定鲨鱼**（正上方偏移 60px），并 clamp 在安全区内。构图更紧凑，但 §6.8.4 的"屏幕正中央"需改写 |
