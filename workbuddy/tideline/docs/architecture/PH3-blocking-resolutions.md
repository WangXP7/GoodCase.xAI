## 阻塞项 1 · 基准分辨率

### 结论

> **采纳 1440×864。**
> 并且我要在你的方案之上**补一层你没定义但必须定义的东西**：**1440×864 是"设计空间"，不是"玩家看到的像素网格"。玩家看到的艺术像素是它的 1/2，即 720×432。**

### 理由

**① 你的整除性论证我复核了，完全成立，并且比你说的更强。**

```
1440 = 2⁵ × 3² × 5      864 = 2⁵ × 3³
1440 × 864 = 1,244,160 px²   ← 与你在 §2.6 做面积配额计算时已经使用的数值一致
宽高比 = 精确 5:3
```

1/2、1/3、1/4、1/6、1/8、1/9、1/12、1/16 全部整除。你 v1.2 删除 1440×810 的自我修正也是对的（810/4 = 202.5，会连丢 1/4、1/8、1/16 三档，而 1/4 正是降级策略实际运行的区间）。

**② 但你的文档里"px"这个词指了三个不同的东西，必须拆开。**

| 你在文档里的写法 | 暗示的含义 |
|---|---|
| "Canvas 显示尺寸 1440×864" | 1440×864 = 显示画布 |
| "内部渲染缓冲（如 **480×288** 或 **720×432**）" | 1440×864 ≠ 实际渲染分辨率 |
| "整数倍放大（**2× 或 3×**）" | 倍率未定，两个候选都列了 |
| §3.1 "鲨鱼体长 **168 px**（@1440×864）" | 1440×864 = 设计坐标 |
| §6.7 "位移量化到像素网格（步进 **2px**）" | 网格是 2px？那 1440×864 就不是网格 |

**最后一条是关键**：如果网格就是设计 px，量化步进应该是 1px。你写的是 **2px**。**这个 2 从哪来，你没说——但它是对的，只是需要一个解释。**

**③ 我用你的字号表把这个 2 反推出来了。**

§3.3 定字号 12/16/24/32/48/64，§3.4 明令"禁止对像素字体做非整数倍缩放"。把 6 个字号分别映射到你的两个候选网格：

| 层级 | 字号 | 1/2 网格（720×432） | 1/3 网格（480×288） |
|---|---|---|---|
| H0 | 64 | **32** ✅ | 21.33 ❌ |
| H1 | 48 | **24** ✅ | 16 ✅ |
| H2 | 32 | **16** ✅ | 10.67 ❌ |
| H3 | 24 | **12** ✅ | 8 ✅ |
| Body | 16 | **8** ✅ | 5.33 ❌ |
| Caption | 12 | **6** ✅ | 4 ✅ |

**1/2（720×432）6 中 6；1/3（480×288）只有 3 中 6。**

**④ 两条旁证同时指向同一个结论。**

- **粒子**：§7.3 规定粒子 "2–5px"。若网格是 1/3，2 设计 px = **0.67 个艺术像素 —— 画不出来**。若网格是 1/2，2 设计 px = 1 艺术像素，合法。✅
- **鲨鱼**：168 设计 px ÷ 2 = **84 艺术像素**；§4.1 提到的"8×8px 脸" = 8×8 艺术 px = 16×16 设计 px，占体长 9.5%。对一条鲨鱼是合理的眼部比例。✅

**所以：`ART_SCALE = 2`，艺术网格 = 720×432。你的"步进 2px"从一条经验值变成了一条几何必然。**

### 实现要点

```ts
DESIGN_W = 1440   DESIGN_H = 864     // 设计空间：所有设计数值的唯一坐标
ART_SCALE = 2                         // 1 艺术 px = 2 设计 px
RT_WORLD  = 720 × 432                 // 艺术网格 = 世界渲染目标
snapArt(v) = Math.round(v / 2) * 2    // §6.7「量化到像素网格」的唯一实现
```

**扫描线必须画在 720×432 这一层，不能画在 1440×864。** 这是整条管线里收益最高的一条：扫描线一旦挪到高分辨率层，1080p 下的 1.25 倍非整数缩放会立刻产生滚动摩尔纹；锁在艺术网格上则**永久免疫**。

**降级时绝不改变 ART_SCALE。** 真正的性能开销在 1440×864 的 CRT 后期 pass，不在 720×432 的世界渲染（填充率仅 311k 像素）。降级关后期、不降分辨率——否则精灵会被非整数重采样，画面劣化，正是你想避免的"像素抖动"。

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 🟠 **16:9 屏幕必有黑边** | 1440×864 是**精确 5:3**，不是 16:9。1080p 下 fit = 1.25，画面 1800×1080，**左右各 60px 黑边** | **请按 5:3 构图，不要按 16:9 构图**，否则两侧内容上线后被裁。若黑边不可接受，备选是改 1280×720 —— 但那会让 §2.6 面积配额、鲨鱼体型推导、明度阶梯**全部重算**，成本很高 |
| 🟡 非整数最终缩放 | 1080p 下 1 艺术 px = 2.5 设备 px | 1 艺术像素 ≥ 2 设备像素时，±0.5 的不规则性低于感知阈值；另提供 `integerSnap` 纯净选项 |
| 🟡 竖屏体验差 | 5:3 横屏在竖屏手机上 fit 极小 | 按 §7.2 处理：提示条 + 可玩降级，不强制旋转 |

### 🔴 需你会签

1. **ART_SCALE = 2（艺术网格 720×432）** —— 这决定所有精灵的绘制网格
2. §3.3 字号表补一列"艺术 px"：64/48/32/24/16/12 → 32/24/16/12/8/6
3. 确认 §7.3 的 "2–5px 粒子" 是**设计 px**（= 1–2.5 艺术 px），最小 1 艺术像素
4. 图集内图块坐标须**对齐偶数**（艺术网格）→ 建议写入 §9.1

## 阻塞项 2 · 渲染方案（Canvas2D vs WebGL）

### 结论

> **WebGL2 + 自研薄渲染层（约 1.2k LOC），否决 Canvas2D。**
> **同时：HUD 与全部菜单改用 DOM，不在 canvas 内绘制。**

### 理由

**① 我逐条查了 §6.5 的 6 项效果，Canvas2D 只能便宜地做到 1 项。**

| 效果 | Canvas2D | 说明 |
|---|---|---|
| CRT 屏幕弯曲 | ❌ | 无逐像素重映射。CSS `perspective()` 是平面透视不是桶形；`border-radius` 是裁切不是形变 |
| 色差 ±3px | ⚠️ | 3 次全屏 drawImage + 混合 = **3,732,480 像素写入/帧 = 2.24 亿/秒**。纯浪费 |
| 有序抖动 | ❌ | 只能预烘焙或 CPU 逐像素 |
| 整屏色闪（调色板切换） | ❌ | 需逐像素重映射，等于双倍素材 |
| 荧光余晖 | ❌ | 一次卷积，CPU 上太慢 |
| 扫描线 / 暗角 / 噪点 | ✅ | 预烘焙叠加即可 |

**② 色差这一项就足以定案。** WebGL 里它是**一次全屏 pass 里的 3 次纹理采样**，成本约为 Canvas2D 方案的 **1/20**。

**③ 绘制调用是第二个决定性因素。** 单帧约 500 个绘制对象（400 粒子 + 实体 + 背景）：

| | Canvas2D | WebGL 自研批处理器 |
|---|---|---|
| 单帧 draw call | ~500 | **2–4** |
| 状态切换 | 500 次 | 4 次 |

只有两种混合模式（§7.4：光效 ADD，粒子 SOURCE_OVER），按桶排序后就是 2 个批。**这是"不引入引擎"仍能高性能的关键。**

**④ 为什么不用 PixiJS（这条我反复权衡过）。**

Pixi 最能帮我们的那部分（精灵批合、图集加载、RT 管理）**恰好在我们必须自定义的领域里失效** —— 一旦挂自定义 shader，Pixi 的自动批合就不工作了，我们仍然得自己写批处理器。而 Pixi 最省事的部分（文字渲染）**我们改用 DOM 了，工作量直接归零**。剩下的价值只剩图集解析 + 纹理上传，约 200 行自研代码。

**净账**：Pixi 省约 1 周，代价 +180 KB、一份必须绕过的抽象、以及 R8 单通道纹理（ADR-005 需要）的非一等公民地位。

> **一句话：本作的视觉身份就是渲染器。硬边像素、有序抖动、整屏调色板切换——三件最独特的事全是渲染层行为。**

**⑤ HUD 走 DOM 是一条被低估的决策，收益远大于代价。**

| 收益 | 说明 |
|---|---|
| **可访问性质变** | 文本是真实文本 → 屏幕阅读器可读、浏览器缩放可用、字体替换可用。**把 §9.8 的 Standard 级从"要做很多工作"变成"基本免费"** |
| 文本缩放 3 档免费 | 一个 CSS 变量 vs 重排全部 canvas 布局 |
| 中文子集化正常工作 | §3.2 的 ~80 KB 子集在 DOM 里直接可用，**不需要位图字体图集**（省 200+ 字形资产） |
| 开发效率 | CSS 布局比手写 canvas UI 快一个数量级 |

**代价与缓解**：HUD 吃不到桶形弯曲 —— **可接受**，因为曲率主要作用在边缘，而 §9.4 规定 UI 安全区距边 ≥48px，**安全区内的形变小于 1 个艺术像素**。HUD 吃不到扫描线 —— 用一层 CSS 扫描线 + 暗角覆盖在 canvas 与 DOM 之上，两者视觉统一。

### 实现要点

```
RT_WORLD (720×432)   L1天空 → L2海面 → L3浅海 → L4主玩法 → 粒子 → L5前景 → 扫描线+噪点
        ↓ ×2 整数 NEAREST
RT_POST  (1440×864)  真 alpha 层（暗角/遮罩/染红）→ 桶形弯曲 + 色差 + 余晖
        ↓ fit + NEAREST + letterbox
Display（DPR 感知）  ▲ DOM 覆盖层（HUD/屏幕）+ CSS 扫描线暗角层
```

- **层是绘制桶，不是排序键**。绝不对精灵逐个 z 排序（会打碎批合）。层内不排序；若将来需要，只允许 ≤3 档显式排序标记。
- **必须处理 `webglcontextlost`**（移动端切后台），CPU 侧资产副本常驻内存以便重建。

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 🔴 **自研渲染层是新方案，未经验证** | 约 1.2k LOC，工期 +1~2 周 | **5 天 Spike 闸门**（ADR-001 §5）：6 项验收全过才执行；3–5 项修 3 天；≤2 项立即转 PixiJS 备选方案 B（已设计就绪） |
| 🟠 WebGL 上下文丢失 | 移动端切后台黑屏 | 恢复路径 + dev 面板"强制丢失"测试 |
| 🟡 WebGL 覆盖率 | WebGL2 ≈ 96%，WebGL1 ≈ 99% | Shader 用 GLSL ES 1.00 写，一套通吃；低于 WebGL1 直接显示不支持页，**不做第二套渲染路径** |

### 🔴 需确认

1. **（用户 / 主理人）是否批准 5 天 Spike**
2. **（用户 / 林绘澄）方案 F 是否可接受**：若放弃 CRT 弯曲与色差，Canvas2D 可行，**可省约 2 周工期**，代价是 CRT 观感退化为"扫描线滤镜"。**这是唯一一个"降低美术目标换工期"的选项，我不能替你做这个决定。**
3. **（林绘澄）HUD 走 DOM 后，CSS 扫描线/暗角覆盖层的观感需你验收**

## 阻塞项 3 · 搁浅碰撞与沙滩边界判定

> **§6.8 整节演出依赖此项。你标 🔴 阻塞是对的——它目前只有一句自然语言描述，没有可实现的判据。**

### 结论

> **四层水体的边界不由 X 坐标硬编码，而由「海床剖面 vs 水面线」导出的水深决定。**
> 搁浅 = 三段式状态机（`累积 → 预警 → 搁浅/QTE`），并**新增一个你和文策渊都没有的「预警态」**。

### 理由

**① 用"水深"而不是"X 区间"定义四层水体。**

```
seabedY(x)                海床剖面（9 点控制表 + Catmull-Rom，加载时烘焙成 LUT）
waterLineY(x, t)          水面线 = 105 + 波浪(±6px, 波长 180, 速度 40)
waterDepth(x, t) = seabedY(x) − waterLineY(x, t)
```

| 区域 | 判据 |
|---|---|
| DEEP | `depth ≥ 400` |
| SHALLOW | `120 ≤ depth < 400` |
| SURF | `0 < depth < 120` |
| BEACH | `depth ≤ 0`（海床升出水面） |

**为什么**：本作叫《潮线 TIDELINE》。如果沙滩边界是一条硬编码的 X 竖线，那"潮线"只是个名字；用海床与水面求交，潮线就成了一个**物理上真实存在、随波浪轻微呼吸**的边界，玩家可以学会"蹭着潮线走"。

**关键分离**：**区域归属用静态海床（稳定），接触判定用动态水面（可玩）**。区域决定 ALARM 速率、敌人生成、视觉明度——这些**必须稳定**，否则潮汐一动，敌人生成表就抖动。而搁浅判定用实时水面，让潮线真正影响手感。

**② 一个几何推论，会直接影响你的演出设计。**

因为海床是实体，鲨鱼在深处会**撞到沙坡**，无法从深水直接水平冲进干沙区。**它必须先上浮到水面附近，再冲上沙坡。**

> 这意味着搁浅是"冲过头"的惩罚（上浮 + 冲坡 + 速度耗尽），**不是"游到了某个 X"**。
> §6.8.2 的"侧躺、腹面朝右侧、身体轴线 −8°"——**头略高于尾**，正好对应"从水里冲上斜坡后被抛在坡上"的姿态。你的设计直觉是对的，几何支持它。

**③ 我加了一个 `STRAND_WARNING` 预警态（这是设计增量，请你和文策渊过目）。**

> **没有预警，搁浅就还是一个 Bug。**

概念文档说搁浅是"设计化的 Bug"，你说要按"名场面"标准做。**但名场面的前提是玩家觉得自己活该，而不是被系统坑了。**

- 没有预警：玩家减速 → 1.2 秒后突然进 QTE → 第一反应是"什么？为什么？" → **这是 Bug 的体验**。
- 有预警：拖沙 + 音 sting + 冲刺提示图标，**留 0.48 秒自救窗口**（消耗 1 格体力冲刺脱身）→ 没反应过来才搁浅 → **这是"我失误了"的体验**。

**这一条顺带把文策渊沙盘里的 `p_beach` 从一个抽象概率变成了可练的技巧轴**（见 §7.2）。

### 实现要点

```ts
// 每逻辑帧
if (zone === BEACH && grounded && speed < V_TH) {
  strandProgress += dt * (1 - speed / V_TH);   // 越慢累积越快
} else if (zone === BEACH) {
  strandProgress -= dt * 2.0;
} else {
  strandProgress -= dt * 4.0;
}
strandProgress = clamp(strandProgress, 0, T_STRAND);
```

| 常量 | 值 | 读数解释 |
|---|---|---|
| `PX_PER_M` | **32** | 巡游 6 m/s = 192 设计 px/s；冲刺 14 m/s = 448 设计 px/s |
| `V_TH` | 96 设计 px/s（3 m/s） | 0.5× 巡游速度 |
| `T_STRAND` | 1.2 s | 完全静止 → **1.2 s** 搁浅 |
| `T_WARN` | 0.72 s（60%） | 慢速蹭沙（1.5 m/s）→ **2.4 s**；≥3 m/s 滑过 → 不累积 |
| QTE | 2.5 s / 6 次 / 间隔 ≥100 ms | **进度不衰减** |
| QTE 期 ALARM | +8 /s | 满窗 +20，与一次捕食同量级 |

**QTE 进度不衰减**：§6.8.4 已经用收缩外环（140→80px）表达了时间压力。再叠加进度衰减是对同一信息施加两次惩罚，会让圆环语义变成"你不但要快，还不能停"，与"可能性正在归零"的叙事冲突。

**单位制**：概念文档用 m/s、美术圣经用 px，两者从未打通。**我定 `PX_PER_M = 32`** —— 巡游与冲刺在设计空间与艺术网格**两个空间都落在整数**（192/96 与 448/224），鲨鱼 168 px = 5.25 m 落在真实大白鲨区间。

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 🟠 **搁浅构图在卷轴下会散** | §6.8.4 规定圆环在"屏幕正中央"，但鲨鱼搁浅处屏幕 x ≈ 1040–1180，与圆环（x=720）相距 320–460 px | **二选一**（见下方 🔴）：A. 搁浅时相机 0.35s 缓推，把鲨鱼送到画面 65% 处并锁定；B. 圆环改为锚定鲨鱼正上方 60px 并 clamp 在安全区 |
| 🟡 海床剖面需美术与关卡共同调 | 地形直接影响四区分界与手感 | 9 点控制表，关卡可调，**不写死** |
| 🟡 手感常量未经 playtest | `T_STRAND` / `V_TH` / `N_qte` 都是初值 | 全部进 `tuning.ts`，MVP 可玩后 5–8 人小样本测试 |

### 🔴 需会签

**林绘澄**：
1. 🔴 **搁浅构图方案 A（相机聚焦）还是 B（圆环跟随）** —— 我推荐 A
2. 预警态的表现规格需补进 §6.8（拖沙粒子 / 提示图标 / 音 sting）
3. 海床剖面 9 点控制表的初始值（与文策渊共同定）

**文策渊**：
4. 🔴 `PX_PER_M = 32` 会签
5. 手感常量初值确认
6. 世界宽度 2160（卷轴 1.5 屏）vs 1440（单屏）

## 阻塞项 4 · 抖动图案预生成

### 结论

> **Bayer 8×8 + GPU 片元着色器，屏幕锚定于艺术网格。**
> **不预生成贴片** —— 但我会保留预烘焙方案作为逃生舱。

### 理由

**① 先把你的"禁止"的意图讲清楚，再说我为什么换了解法。**

你在 §7.6 写：*"预生成为 4–16 张小 sprite，打包进 atlas_vfx，运行时按粒子寿命索引取用。**禁止运行时逐像素计算 Bayer 矩阵**。"*

这条要求**在它预设的技术前提下完全正确**——如果渲染是 Canvas2D，CPU 逐像素算 Bayer 在 60fps 下必然崩掉。但 ADR-001 已把渲染改判为 WebGL2，**技术前提变了**。

| | 你的字面要求 | **你的意图** |
|---|---|---|
| 抖动从哪来 | 预生成 sprite 贴片 | **不要有 CPU 逐像素开销** |

**GPU 片元着色器满足这个意图，而且满足得更好**：每个片元确实"逐像素计算"了，但是在 GPU 上、数千核心并行、每片元 1 次纹理采样 + 1 次比较。成本比"从图集取一张预烘焙贴片"多约 1 个采样单元，却**省掉了组合爆炸**。

**② 预烘焙在 WebGL 下反而更差，因为它必须回答"贴片是什么颜色的"。**

| | 预烘焙贴片 | **GPU shader** |
|---|---|---|
| 资产数 | 17 张（需运行时染色）或 **272 张**（16 色 × 17 级，预着色） | **0** |
| 改配色的成本 | **重烘焙全部** | 改 1 个像素的 LUT |
| 密度分辨率 | 17 级（Bayer 4×4）→ **粒子淡出会出色带** | **65 级（8×8）** |
| 批量绘制 | 换贴片 = 换纹理区域 | 密度作顶点属性，**同一批** |
| 运行时 CPU 开销 | 0 | 0 |

**③ 为什么用 8×8 而不是你建议的 4×4**：4×4 只有 17 级密度，粒子淡出会看到明显色带。8×8 有 65 级，淡出连续。代价是抖动单元从 4×4 变 8×8 艺术像素（= 16×16 设计 px）——**但你要的本来就是可见的网点纹理，粗一点更符合街机 authenticity。**

**④ 屏幕锚定 vs 物体锚定（这是观感决策，请你定）。**

| | 屏幕锚定 | 物体锚定 |
|---|---|---|
| 单粒子移动时 | 像素随网格进出（"闪"） | 稳定 |
| **多粒子重叠时** | **共享同一网格，无摩尔纹** ✅ | 各粒子网格不重合 → **摩尔纹** ❌ |
| 与真实硬件 | **一致**（街机硬件的抖动就是屏幕锚定的） | 不一致 |

**水花是 25–40 个粒子重叠的密集事件**（§7.3 #3 / #9）。**重叠场景远多于单粒子场景**，所以我默认选屏幕锚定。且"像素随网格进出"正是真·硬件抖动的外观，是特性不是缺陷。**uniform 可实时切换，供你 A/B。**

**⑤ 我确认你保留暗角用真 alpha 的判断，并补上机理。**

> **抖动产生可见网格纹的条件是：被抖动的量在空间上低频且平滑。**
> - **暗角**：跨越全屏的平滑径向渐变 → 除了抖动图案，画面里**没有别的空间频率** → 网格纹成为唯一可见结构 → 必然显形。
> - **粒子**：本身高频、离散、运动 → 抖动图案混进去**读起来像材质** → 不显形。

**所以判据不是"全屏 vs 局部"，而是"被抖动对象本身是否具有更高的空间频率"。** 这条判据比面积更准，未来新增元素时你和团队都能自行判断。

### 实现要点

```glsl
float ditherThreshold(vec2 fragCoord) {
    return texture2D(uDitherTex, fragCoord / (uArtScale * 8.0)).r;  // 对齐艺术网格
}
// 粒子片元：
if (vDensity < ditherThreshold(gl_FragCoord.xy)) discard;
```

- 8×8 单通道纹理（64 字节），`NEAREST` + `REPEAT`
- `density = pow(lifeRatio, 0.75)` 作**顶点属性**传入，**不打断批合**，**不产生额外 draw call**
- 密度曲线我建议 `^0.75` 而非线性：线性映射下粒子在最后 25% 寿命里密度从 25% 掉到 0，视觉上"突然消失"；`^0.75` 让消散更自然
- 成本：最坏 40 粒子 × 5×5 艺术 px = 1,000 片元 → **可忽略**

**逃生舱已就绪**：若 Spike 失败，回退到预烘焙 17 张（Bayer 4×4）白色遮罩 + 运行时染色。不需要额外决策。

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 🟠 **你无法在 Photoshop 里预览抖动效果** | 从"美术可预览的贴片"变成"shader 行为" | dev 面板提供**实时切换**（密度曲线 / 锚定模式 / 矩阵大小 / 蓝噪声备选），你可以直接调 |
| 🟡 Bayer 网格感可能过重 | 规则网格是街机的真实外观，但有人会觉得脏 | 备选**蓝噪声**已备好（矩阵以纹理形式注入，换图即可）。蓝噪声更"有机"但失去规则感与硬件 authenticity |

### 🔴 需你会签

1. 屏幕锚定 vs 物体锚定（默认**屏幕**）
2. Bayer 8×8 的网格感是否过重？是否需要蓝噪声备选
3. 密度曲线 `pow 0.75` vs 线性
4. 逃生舱（预烘焙 17 张）是否可接受为回退方案

## 阻塞项 5 · 呼吸式脉动的统一实现

### 结论

> **单一 `breath()` 时间函数 + 三条强制机制（CI + lint + 运行时审计）+ 相位错开。**

### 理由

**① 波形改用升余弦，不用 §9.9.2 给的 `sin`。**

| 波形 | 在极值处 | 观感 |
|---|---|---|
| `sin` | 不停留，匀速穿过 | 像"摆动" |
| **升余弦 `0.5 − 0.5cos`** | **导数为 0，停留** | **像"呼吸"** |

两者只差一个相位，但极值处的停留正是"呼吸"的语义来源。**§9.9.2 要的就是"呼吸式"，所以升余弦更贴合你自己的意图。**

**② 我发现 §9.9 有一个缺口：它管不到"叠加亮度"。**

> 🔴 **这是我在本次评审中发现的第二个安全问题，必须提出来。**

§9.9 限制了**单个元素**的频率 ≤2Hz。但光敏性癫痫的真实诱因是**大面积相对亮度变化**（WCAG 2.3.1 判据：面积 > 视野 10% 且相对亮度变化 > 10%）。

**如果 7 个脉动元素同相位，它们的亮度变化会叠加** —— 每个都是 2Hz、每个都是局部的，但合起来就是一次**全屏 2Hz 的亮度摆动**。这恰恰是 §9.9 想防的东西，而"每个元素 ≤2Hz"这条规则**管不到它**。

**对策**：4 个 channel 固定错开相位（`ui` / `hazard` / `ambient` / `world`），并设**全局亮度预算**：`Σ(元素面积占比 × 亮度调制幅度) ≤ 0.10`，开发期实时审计。

**③ 安全红线不能依赖人去记。**

§9.9.5 的验收清单第 4 条是：*"全项目闪烁频率 ≤2Hz（**代码搜索** `Math.sin(2 * Math.PI * f` 核验 f 值）"*。

**这是一条人工检查，它一定会失效。** 我把它变成三道自动防线：

1. **CI 静态检查**：`src/gameplay/**` 与 `src/presentation/**` 中出现 `Math.sin/cos` 直接用于亮度 → 构建失败（`breath.ts` 白名单）
2. **Lint 规则**：`no-restricted-syntax` 同上
3. **开发期运行时审计**：`BreathAudit` 统计所有注册元素的 `hz` 与面积，断言 `max ≤ 2` 且预算 ≤ 0.10

**频率 clamp 写在 `breath()` 内部**（`Math.min(spec.hz, BREATH_MAX_HZ)`），**从 API 层面无法绕过**。

### 实现要点

```ts
export const BREATH_MAX_HZ = 2;   // 全项目唯一定义

export function breath(spec: BreathSpec, t: number): number {
  const hz = Math.min(spec.hz, BREATH_MAX_HZ);      // 硬 clamp
  if (opt.flash === false) return spec.hi;          // 开关关闭 → 常亮（信息保留）
  if (hz === 0) return spec.hi;                     // reduced-motion
  const w = 0.5 - 0.5 * Math.cos(2 * Math.PI * hz * (t + phase));
  return spec.lo + (spec.hi - spec.lo) * w;
}
```

**覆盖 7 个使用点**：QTE 圆环（§6.8.4）· ALARM 条 · T4 威胁等级（§4.4）· 深海生物发光（§5.3.1）· 连打提示图标 · 扫描线抖动（§6.6）· 张力预告（§5.4.3.1）

**与开关联动**：`opt.flash = OFF` → 返回 `hi`（**常亮**，符合 §9.9.1"所有闪烁改为常亮"），**信息不丢失**。

### 风险 + 🔴 一个必须你拍板的安全问题

> ⚠️ **§6.6 的「色闪」是全项目唯一一个全屏、高对比、突变的效果，也是全项目最高的单点光敏风险。**

为它辩护的事实：只有 1–2 帧（16–33ms），是**单次瞬变**而非重复闪烁，WCAG 的"3 次/秒"判据不适用于单次事件。**所以它合规。**

但它仍然是风险最高的单点，而 §9.9 明确说"亮度突变才是主要诱因"。

| 选项 | 说明 |
|---|---|
| **A（现状）** | 保留 1–2 帧全屏高对比切换 |
| **B（我建议）** | 改为**部分调色板切换**——只重映射最暗的 3 档色阶。亮度变化降到约 40%，**视觉冲击力保留约 80%** |
| **C** | 色闪必须受 `opt.flash` 控制，且**在首次启动的光敏提示中明确列出"色闪"** |

**我的立场**：A 合规，但 B 的性价比更高（损失 20% 冲击力，换一个数量级的安全边际）。**这是美术决策不是技术决策，请你定。** 无论选哪个，`opt.flash` 必须能关掉它。

### 🔴 需你会签

1. 🔴 **色闪安全方案 A / B / C**（也需严守真确认）
2. 升余弦波形（替代 `sin`）
3. 4 channel 相位错开 + 亮度预算 0.10

## 阻塞项 6 · 中央特效调度器

### 结论

> **三段式管线：`准入 → 互斥仲裁 → 降级补偿`。**
> 核心是**第三段**——被阻断的特效不是消失，而是**降级为另一种通道的反馈**。

### 理由

**① 你标出了两套规则需要一个仲裁层，我找到了它们具体会怎么冲突。**

| §6.7 互斥 | §9.9.1 五开关正交 |
|---|---|
| 同时最多 1 个屏幕级特效，色闪 > 震屏 > 扫描线抖动，**其余丢弃** | 5 个开关两两正交，**不能出现"关掉震屏但打击感完全消失"的退化** |

> **冲突案例（这不是边缘情况，是必然发生的组合）**：
> 玩家关闭「屏幕闪烁」。捕食触发 `{色闪 + 震屏 + 顿帧}`。
> - 互斥规则：色闪优先级最高 → **震屏被丢弃**
> - 开关规则：**色闪不生效**
> - **结果：捕食只剩顿帧。**
>
> 而 §9.9.1 写的是"关闭震屏后，捕食仍有顿帧 + 色闪反馈"——**这里反过来了：关闭色闪后，震屏被互斥规则吃掉了。**

**这不是两套规则的错，是它们必须由同一个组件在同一次求值中处理。**

**② 顿帧的正交性我用数据结构固化，而不是靠人记。**

§6.7 v1.2 把顿帧和缩放脉冲移出互斥表，**我确认这个修正是对的**（顿帧不增加视觉信息量，它只是暂停逻辑，是时序层）。

但我把它从"文档里的一句话"变成**数据结构上的不可违抗**：特效表里 `hit.hitstop` **这一行根本不存在**。想加回来必须显式加一行并写理由。§6.6 ③ 的"受击绝不触发顿帧"也是同理。

### 实现要点

```
Request → ① 准入：开关关闭 → 不丢弃，转为「补偿令牌」
        → ② 互斥仲裁：flash(30) > shake(20) > jitter(10)
                     高优先级到达 → 抢占，低优先级软停 2 帧后退出（防 pop）
        → ③ 降级补偿：查补偿表，递归深度 ≤2
        → Active FX Set
```

**补偿表（这就是"互斥与开关不冲突"的答案）**：

| 被阻断 | 一级补偿 | 二级补偿 |
|---|---|---|
| 震屏 | **顿帧 0.08s** | 缩放脉冲 ×1.5 + 粒子 ×1.5 |
| 色闪 | 震屏（若可用） | 缩放脉冲 + 高对比色块常亮 |
| 扫描线抖动 | 扫描线**保持静态** | ALARM 高危改用 HUD 边缘箭头 2Hz 呼吸 |
| CRT | 无（纯视觉降级，无信息损失） | — |
| 粒子 0% | **几何替代**：1px 硬边描边扩散环 | 缩放脉冲 |

**抢占用软停而非硬切**：1–2 帧的效果被硬切会产生亮度/位移**突变**——而突变本身就是我们要防的东西。软停把"丢弃"也纳入安全约束。

**② 正交性不变量 —— 192 例自动化测试**

> 对 5 个开关的 **32 种组合** × **6 个核心事件**（`bite` / `hit` / `combo` / `rarePickup` / `beachLand` / `alarmEscalate`），每种组合下必须在 `{视觉, 时序, 音频, HUD}` 中产生 **≥1 个非零反馈**，且 **max Hz ≤ 2**。

**一条测试同时守住三件事**：§6.7 互斥、§9.9.1 不死区、§9.9.2 的 2Hz 红线。

> 这是 §9.9.5 验收清单第 1 条（"5 个开关两两正交，任意组合不崩溃、不出现无反馈的死区"）的**机械化实现**。你在验收清单里写的是人工核验，我把它变成 CI 里的一条命令。

**③ 架构强制**：`src/gameplay/**` **只能通过发领域事件触发特效**，禁止直接调用 `screenShake()` / `flash()` / `hitstop()`（lint 规则）。

**为什么这么严**：只要有一处游戏逻辑能绕过调度器，§6.7 就形同虚设。这是**结构性保证**，不是约定。

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 🟡 调度器是新组件，约 400 LOC | 但它是 §6.7 明确要求的，不做不行 | 数据驱动（`FX_TABLE`），加特效只改表不改代码 |
| 🟡 6 个"核心事件"清单可能不完整 | 覆盖 §7.3 的全部 VFX 触发点 | 请文策渊确认（🔴） |
| 🟡 `breath()` 的 CI 检查会拦住合理用法 | 误报 | 白名单 + `// breath-ignore:` 行内豁免 |

### 🔴 需确认

**文策渊**：6 个核心事件清单是否完整；补偿表参数（顿帧时长、缩放倍数、粒子倍率）
**林绘澄**：补偿后的观感（如"震屏关闭 → 顿帧 + 缩放脉冲"是否仍有打击感）

## 7. 给 Phase 2 的技术边界约束（文策渊请重点看这一节）

### 7.1 约束（请在此范围内设计）

| # | 约束 | 说明 |
|---|---|---|
| **C1** | **世界宽度建议 2160（1.5 屏），相机夹取 [0, 720]** | §5.2 给了视差系数 0.05–1.6，说明美术已按卷轴设计。但 1.5 屏能让"危险梯度 = 屏幕左右"这条支柱基本成立。**若你 prefer 单屏 1440，改动成本很低**（改一个常量），但需与林绘澄确认视差层如何处理 |
| **C2** | **同屏实体上限 120**（不含 400 粒子） | 关卡 GDD 的"游客数量""同时出现的敌人数"需在此内。超了需要分区流化，那是另一个量级的工作 |
| **C3** | **冲浪路线 8 个收集物用参数化曲线描述** | 不要给 8 个逐点坐标。用 **Catmull-Rom 3 控制点**，程序按弧长等距排布（§5.3.3 要求间距 90–140px、沿曲率排布）。改曲线比改 8 个点快得多，也更容易调节拍 |

### 7.2 🔴 `p_beach` 不是一个概率，是三个旋钮（请更新沙盘）

R1 沙盘（`PH1-R1-numerical-sandbox.md` §1.3）把搁浅风险建模为标量 `p_beach = 0.03 / 0.15`。

**按本架构，它由三个可观测、可调、可练的旋钮决定**：

| 旋钮 | 默认值 | 影响 |
|---|---|---|
| `T_WARN` 预警窗口时长 | 0.48 s | 越长越容易救，**线性影响 `p_beach`** |
| `N_qte` QTE 需要输入数 | 6 次 / 2.5 s | 越难越容易失败 |
| 冲刺逃脱的体力代价 | 1 格 | 决定是否"总能靠体力买命" |

**这比抽象概率好得多**，因为：

- **"新手 0.15 → 专家 0.03"有了机制解释**：新手注意不到预警，专家次次在预警窗口内冲刺脱身
- 三个量都能在 playtest 中直接观测（预警响应率、QTE 成功率、体力消耗率），而 `p_beach` 本身只能事后反推
- **建议沙盘 §1.3 把 `p_beach` 改为引用这三个旋钮**

### 7.3 ❌ 技术上做不到或代价过高的设计（请提前规避）

| 设计 | 判定 | 原因与替代 |
|---|---|---|
| **实时流体 / 液体模拟**（海面波动、水花流体） | ❌ **做不到** | WebGL 2D 下代价过高。替代：**预烘焙波形 + 顶点位移**近似（§5.3.2 的波浪线已是这个思路）。水花靠粒子物理，不靠流体 |
| **真正的软阴影 / 动态光照** | ❌ **做不到** | 与索引色调色板**根本冲突**——光照必然产生调色板外的中间色，而 ADR-005 要求每像素严格来自调色板。替代：**硬边色阶带**（§5.3.2 已在用） |
| **全局调色板的连续渐变过渡**（如 ALARM 升高时整屏缓慢变色） | ❌ **做不到** | 索引色只能做**离散档位切换**。好消息：你已有 4 级敌人 + 4 档 ALARM 配色，离散档位完全够用 |
| **从深水直接冲上沙滩叼走游客** | ❌ **几何上不成立** | 海床是实体，鲨鱼会撞到沙坡。必须走"**上浮 → 冲坡**"两段式。若 GDD 里有一气呵成的深水突袭，需改为两段 |
| **可堆叠刚体 / 连锁倒塌**（推倒沙堡压到敌人） | ⚠️ **代价高** | 需要物理引擎，而 ADR-006 否决了它。若这是核心设计，需重新评估（当前 GDD 无此设计，记录为技术债） |
| **逐帧 A\* 寻路的包围战术** | ⚠️ **代价高** | 本作敌人用**状态机 + 转向行为（steering）**即可，成本 1/10。若 GDD 要求"多单位包抄合围"，需要额外预算，请提前说 |
| **同屏 >30 个游客的大场面** | ⚠️ **可行但会吃掉粒子预算** | 实体上限 120，粒子 400。人一多，水花就得少 |
| **在线排行榜 / 每日挑战 / 成绩分享** | ⚠️ **现在不能承诺** | 纯前端无后端 = 客户端完全不可信，本架构**明确不做反作弊**（ADR-006 §2.6）。要加这些需要服务端权威 + 回放校验，**是另一个量级的工程**。**请先找我评估再对外承诺** |

### 7.4 💡 两个"顺手就能有"的能力（如果你要，现在说最便宜）

| 能力 | 成本 | 价值 |
|---|---|---|
| **回放 / 输入日志** | **+200 LOC**（确定性已由 ADR-006 具备，只需记录 seed + 输入序列并加 IndexedDB） | 任何 bug 100% 可复现；playtest 可给不同测试者同一局；**也是未来做排行榜的唯一正当基础** |
| **完整色盲模式（多种类型）** | **≈ 0**（ADR-005 的调色板 LUT，加一行 JSON 就是一种） | §9.8 直接到 Comprehensive 级 |

> **这两件事的共同点：现在做几乎免费，以后做要返工。** 特别是回放——它要求全项目 RNG 种子化与固定步长，**必须在 MVP 之前决定**，否则后期无法补。

## 8. 我额外提出的两条 ADR（不在派单范围内，但不做会返工）

| ADR | 内容 | 为什么必须现在定 |
|---|---|---|
| **ADR-005 · 索引色 + 调色板 LUT** | 精灵存调色板索引，颜色由 256×1 LUT 查得 | **色闪、色盲、一抹血色三个设计指向同一个需求：同一张贴图在不同时刻显示成不同颜色。** 而 tint 在数学上做不到"把 A 变 B 同时把 C 变 D"那种**非线性重映射**。LUT 方案下，色闪和色盲各是**一次纹理绑定**；否则是**两套要手工同步的资产**。§9.1 你已经要求 PNG-8 索引色，§2.1 已经是索引式调色板——**美术侧已经在生产索引色资产了，只是渲染端还没利用这个事实** |
| **ADR-006 · 无物理引擎 + 固定步长 + 确定性** | 手写 AABB；逻辑 60Hz 固定步长；**不做渲染插值**；全局种子 RNG | **§9.6 的"渲染插值"与 §6.7 的"禁止亚像素插值"直接冲突。** 插值产生的中间位置会被吸附抹平——数学上空操作。裁决：**§6.7 胜出，不插值**。但只对**位置**吸附，旋转/缩放/镜头仍插值（§6.7 明确允许），高刷屏不吃亏 |

### 🔴 ADR-005 需要你做的一件事

**建立权威调色板 `design/art/palette.json`（单一真源，含索引编号）。**

你的工作方式**不变**（仍在 Aseprite/Photoshop 按 §2.1 的 16 色画，仍导出 PNG-8），只多一个构建步骤：

```
PNG-8 → tools/build-atlas.mjs → ① 颜色映射回权威索引 ② 输出灰度索引图 ③ 输出图集 JSON
                                ④ 出现调色板外颜色 → 构建失败并列出违例
```

**顺带解决两件你已经挂账的事**：
- `PHASE1-SUMMARY.md` §10.3 待办 #1「调色板取证脚本（扫描图集，列出表外颜色）」—— 分配给我但还没做，**本方案把它变成 CI 门禁，自动完成**
- §2.5「配色纪律（硬约束）」—— 从人工检查变成**构建期自动失败**

**代价**：导出的灰度索引图肉眼不可读。**缓解**：构建脚本同时输出一份**还原后的 RGBA 预览图**供你验收。

## 10. 我认为最大的技术风险

> **T1 · 自研渲染层 + 索引色 LUT + 自定义 CRT/dither shader，三项新技术叠加，且尚未验证。**

**为什么它是最大风险**：

1. 它不是一个可以"边做边看"的风险——**渲染管线是所有后续工作的地基**。如果它在第三周被发现走不通，前面所有业务代码都要重写。
2. 三项技术**互相耦合**：索引色 LUT 依赖自定义 shader；自定义 shader 让引擎的自动批合失效，逼我们自研批处理器；抖动和 CRT 又都挂在同一个 shader 上。**它们会一起成功，也会一起失败。**
3. 其中 **ADR-005（索引色 LUT）依赖林绘澄的资产是严格索引色、无抗锯齿、无渐变**。这是一个**我无法单方面验证**的前提。

**缓解（已写入 ADR-001 §5）**：

| 措施 | 内容 |
|---|---|
| **5 天 Spike 闸门** | 6 项验收（索引纹理+LUT / 批合 / 双RT+CRT / 抖动 / 调色板切换+色盲 / 中低端安卓 ≥55fps）。**6/6 通过才执行；3–5 项修 3 天；≤2 项立即转 PixiJS 备选方案 B** |
| **备选方案 B 已设计就绪** | PixiJS v8 锁 WebGL，精灵改预着色 RGBA，色闪/色盲改用全屏 LUT Filter。**保住 90% 视觉效果**，代价 +180 KB 与逐精灵调色能力 |
| **ADR-005 的独立降级路径** | 即使 Spike 其他项通过而单通道纹理不支持，索引可存进 RGBA 的 R 通道。**放弃显存收益，但保住色闪/色盲/配色门禁 90% 的价值** |
| **要求一张真实图集参与 Spike** | 不能只用测试图。需要林绘澄提供一张按 §2.1 调色板画的真实图集（哪怕 256×256、几个 sprite 即可），用来验证 T2 |

**次级风险（按等级）**：T2 资产格式不符（高）· T3 CRT 在中低端移动端开销未知（中）· T4 黑边不被接受（中）· T5 色闪光敏风险（中）。
