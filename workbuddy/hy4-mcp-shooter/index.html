04

四个关键设计决策

其中第 1 条是地基，第 3 条是「能不能真的跑通」的分水岭。

① AI 编辑「场景清单」，而不是写代码

Scene Manifest 是一份纯 JSON —— 环境、道具、敌人、玩法数值全在里面。对应 UE 的 .umap。

  • 可序列化 → 存盘 / diff / 版本控制
  • 撤销重做天然支持（不像生成代码）
  • 非法状态被 sanitizeLevel() 兜住，不让游戏崩
  • 人工审查一眼看懂，不用读几百行
  • 同 seed 同结果，可复现

② 工具分两层：原子 + 语义

底层要精确可控，高层要一句出效果。两层都给，Agent 才不会退化成一堆坐标运算。

原子层：place_props 传 10 组精确坐标。

语义层：{pattern:"ring", count:10, radius:22, faceCenter:true, jitter:1.5} —— 在中心围一圈集装箱、朝向中心、带随机抖动。

最高层 build_arena 一次调用生成完整关卡。这正是官方 Demo 里「从零做一个射击游戏」对应的那个工具。

③ 给 AI 装眼睛和手 ← 最不能省

没有验证闭环，AI 只是在盲改。

  • capture_viewport → 回传 JPEG，AI 真的能看到画面
  • set_viewpoint → 能飞到任意高度/角度的「审图」能力
  • run_playtest → 机器人接管 N 秒，回报击杀/命中率/受伤，并给出难度判定

三者合起来才形成 执行 → 观察 → 修正 的闭环。UE 侧对应 start_play_in_editor + get_editor_logs。

④ 按变更类型增量下发

store 给每次变更打类别，浏览器走不同应用路径：

  • env → 只换光照/雾/色调
  • actors → 重建道具敌人，但保留玩家血量
  • gameplay → 只更新数值，完全不碰场景
  • full → 整体重建

好处：调数值时玩家不被打断，改美术时不卡顿。

验证记录

✓ 三层验证全部通过：语法检查 · 端到端冒烟 7/7 · 视觉验收 10 机位 · 完整演示 15 步零失败

截图回传不只是「交付好看」，它是主要调试手段。下面这些都是在「代码看起来没问题」的情况下 靠比对画面才发现的：

#症状根因修法
1所有截图一律超时浏览器端 _emit 没把请求 id 透给处理器，回包发不出去，Server 干等 15s透传 id；capture 加 try/catch 回报错误而不是静默超时
2所有机位图长得一模一样游戏没进运行态（running=false），player.update() 整段被跳过，相机卡死在原点加 ?autostart=1 + 把 start/stop PIE 做成 MCP 工具
3高空俯瞰能看穿地面边缘，关卡像悬浮板子地面平面只有 arenaSize+120，从 60 米高往下看直接越过边界地面放大到 arenaSize×8，配合指数雾自然淡出
4黄昏地面死黑、网格线看不见太阳强度与环境光过低，且相机正对太阳（逆光）提亮地表 albedo + 环境光系数 0.55→0.95
5灯泡糊成一大团白光斑自发光 4.5 + bloom threshold 0.85，HDR 值远超声阈值自发光降到 1.6、阈值提到 1.0、radius 收到 0.4；改用 PointLight 照亮地面
6夜景几乎全黑，只看见灯环境光不足 + 地表 albedo 过暗，掩体轮廓不可辨 → 玩法崩掉环境光提到 1.35；把平行光当「月光」用，保住背光面体积感
7出生点正前方 4 米杵着灯柱灯柱摆在 [0,·,30]，而出生点在 z=34灯柱挪到 [-13,·,31]
8玩家一睁眼背对竞技场Player 构造函数硬编码 yaw=π，出生点在 +Z 侧清单加 playerYaw 字段，respawn() 应用它
第 1 条是最值得记住的教训：MCP 工具遇到异常必须回报错误，绝不能静默超时 —— 否则 Agent 侧只能看到「超时」，完全无法判断是渲染管线坏了、还是浏览器压根没连上。 工具的错误语义设计，本身就是 Agent 可用性的一部分。

六套美术预设 · 十机位验收

环境美术全部由参数驱动：天空三段渐变 + 太阳方位/高度 + 雾色雾浓度 + 曝光 + 泛光。切换预设就是换一组数。

dusk
黄昏 · 低角度暖阳
长投影 + 网格地面 + 灯柱光池
逆光
正对太阳 · 剪影与大气光晕
塔楼天线、集装箱、油桶全部逆光成剪影
night
夜景 · 暗但有层次
月球光晕 · 塔楼灯带 · 灯柱照亮地面
俯瞰审图
关卡布局一目了然
四面围墙 · 对角双塔 · 中央高台 · 中场掩体 · 敌人分布
美术铁律 1：地表 albedo 必须明显低于道具。地面法线朝上吃满半球天光， 道具侧面只吃到掠射角的光 —— 两者 albedo 接近时，地面反而比道具亮， 所有箱体塔楼会退化成黑剪影，场景彻底失去体积感。
美术铁律 2：emissiveIntensity 超过 1.0 就必须配 bloom threshold。 阈值定低了整个画面会糊上层雾，暗部失去层次；自发光过高则被拉成一团光斑， 渲染出「发光的马赛克」而不是「灯泡」。

怎么跑起来

完整演示

node tools/run-demo.js

自动起服务 + 开浏览器，走完 15 步建关，每步截图存证，最后导出成品关卡 JSON。

端到端自检

node tools/smoke-test.js

启动 → 渲染 → 射击 → MCP 改场景 → 截图 → 试玩 → 撤销，7 项断言。

视觉验收

node tools/gallery.js

十个机位出图，覆盖六套美术预设 + 俯瞰审图 + 第一人称。

接进真实 AI 客户端：把 server/mcp-server.js 注册到 ~/.workbuddy/mcp.json， 然后在连接器管理页右上角「自定义连接器」点「信任」启用。之后直接说—— 「帮我做一个炼狱风格的废墟关卡，掩体稀疏一点，难度拉到 2.5，然后截图看看效果，再跑一次试玩确认难度。」 Agent 会自己走完 build_arena → capture_viewport → set_environment → run_playtest 的闭环。
08

能搬到哪些项目

引擎可行性要点
Three.js
本仓库 / 3D 场景系列		 已验证 浏览器天生可远程驱动，WebSocket 直接通。换成程序化 3D 世界项目时，只需把清单字段从 props 换成 terrain / landmarks / traffic 即可。
Phaser 3
TBOI 重制		 高 2D 但思路完全一致：清单字段换成 tilemap / entities / spawnTable， 监听 level:* 消息后 scene.restart() 重建。Phaser 重建成本几乎为零，热更新比 3D 还干净。
Godot 4
Nodebuster		 中 没有内置 MCP，推荐在 GDScript 里起 WebSocketServer， Node 监听消息 → 操作 SceneTree，概念与本实现同构。 额外好处：Godot 的 Resource 系统天然可序列化，.tres 就是现成的场景清单。
UE 5.8+ 官方已支持 直接启用内置 UnrealMCP 插件，端点 127.0.0.1:8000/mcp。 自定义能力靠 UToolsetDefinition 子类。注意仍是 Experimental，且仅 loopback、无认证。
通用移植四步
① 定义清单 —— 把可变状态抽成纯数据（JSON / Resource / ScriptableObject）
② 起本地服务 —— WS 或 HTTP，暴露给 MCP Server
③ 包工具 —— 底层原子 + 高层语义，两层都要
④ 加验证 —— 截图 + 自动跑测，让 AI 能自己看到结果
为什么值得做（对齐 Epic 的立场）
State of Unreal 2026 明确表态「用 Claude、Gemini 或任何适合你的模型来构建」—— AI 层被定位为可替换的基础设施，而不是绑定某家模型厂商。
同时要区分两件事：MCP 增强开发者控制力（社区欢迎） vs AI 直接生成美术资产（社区强烈反弹）。本方案只做前者。
