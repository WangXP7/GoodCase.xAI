## 0. 本文档要解决的那个矛盾

> **核心矛盾**：HUD 默认全隐、无任务列表、无教程弹窗、无进度条、无 hover 高亮（移动端）。
> **那么：新手如何知道该做什么？如何知道什么可以点？**

我的回答分三层，贯穿全文：

| 层 | 回答 | 位置 |
|---|---|---|
| **第一层** | **他不需要"知道该做什么"——他需要"想做点什么"。** 本作没有"该做的事"，这是 feature 不是 bug。设计目标是让玩家产生**内在目标**（"它会不会过来？"），而不是完成系统目标 | §3 隐形引导 |
| **第二层** | **可发现性靠场景内的三重冗余编码 + 物件层的必给反馈**，而不是靠 UI 提示 | §4 可发现性、§6 交互反馈 |
| **第三层** | **唯一破例**：截图按钮常驻（半透明）。因为 A11 已把截图列为 MVP 核心 KPI，**KPI 不能靠玩家自己发现** | §5.3 |

## 1. UX 原则（5 条）

### 原则 1 · 场景即界面（The Scene Is the Interface）

> **因为**：本作的四根支柱全部建立在"这是一个家"的信念上。任何浮在画面上的 UI 元素都会把"家"打回"游戏界面"——玩家从"我在看一只猫"切换到"我在玩一个软件"，沉浸瞬间断裂。
> **所以**：所有信息（当前时刻、猫的状态、物件可交互性、关系进展、离线内容）**优先编码进场景内的物理对象**。UI 是最后手段，且只允许存在 1 个常驻元素。

**可验证的落地标准**：
- 玩家关闭游戏后回忆，能说出的"信息载体"应该是"墙上的钟""沙发的坑""它尾巴的方向"，而不是"左下角的图标"
- 代码中常驻 UI 元素数量 = 1（截图按钮），其余全部为召唤式或场景内

---

### 原则 2 · 先给线索，再给确认（Clue Before Confirm）

> **因为**：移动端没有 hover，桌面端的 hover 也只在鼠标端存在。玩家必须在**不确定**中行动。如果反馈来得太明确（高亮框、描边、弹字），探索感会立刻消失——玩家从"我发现了一个可以点的东西"降级为"系统告诉我点这个"。
> **所以**：玩家的第一次接触只得到**弱线索**（物件微亮 5%、猫的 Ear-ack），重复接触后才得到**强确认**。

**可验证的落地标准**：
- 玩家描述自己发现某物件时的用语应该是"我试着点了点"，而不是"它提示我点"
- 首次接触与重复接触的反馈强度差 ≥ 2 倍

---

### 原则 3 · 可失败，不可阻塞（Fail-able, Never Blocking）

> **因为**：本作没有任务、没有失败态、没有"你必须先做 X"。任何一个"你必须先做 X 才能做 Y"的门槛都会摧毁"随时来、随时走、随时再来"——而这是核心用户的使用模式（单次 1–10 分钟、每日 1–3 次）。
> **所以**：任何交互都可以**失败**（被拒绝、被无视），但**没有任何交互会被系统阻止**。

**可验证的落地标准**：
- 代码中不存在 `if (!unlocked) { showModal(); return; }` 这类模式
- 任何输入都有响应（哪怕是"被吞掉 + 物件层反馈"），**不存在"点了完全没反应且无任何反馈"的输入**

---

### 原则 4 · 零退出摩擦（Zero Exit Friction）

> **因为**：核心用户单次 1–10 分钟。任何退出确认、"今日未完成"提示、二次挽留弹窗，都是对这种使用模式的敌意，且直接违反情绪禁区（无 FOMO）。
> **所以**：关闭标签页即离开。无确认、无总结、无挽留。**猫继续它的时间。**

**可验证的落地标准**：
- 代码中不存在 `beforeunload` 确认对话框
- 不存在任何形式的"你今天还没……"提示

---

### 原则 5 · 静默优先（Silence First）

> **因为**：U8 已裁决默认静音，且硬约束禁止震屏 / 色闪 / 顿帧。这意味着**反馈不能靠强度，只能靠时间和变化率**。
> **所以**：所有反馈是"慢的、小的、可以用余光感知的"——用**时长**（0.4–0.8s）换取强度，用**持续痕迹**换取瞬时冲击。

**可验证的落地标准**：
- 不存在 < 0.1s 的瞬时反馈（美术 §6.4 已定）
- 不存在任何全屏级别的视觉变化（闪白、震屏、暗场 > 5%）

### 2.1 路径 A · 首次进入

| 阶段 | 时间 | 内容 | 设计意图 |
|---|---|---|---|
| 加载 | 0–1.2s | **无进度条**。一张从暗到晨光的渐亮，遮盖加载 | 进度条会把"家"变成"软件" |
| 加载超时 | > 3s | 出现一行手写体「……」（猫在等你）。**这是唯一允许的加载提示** | 保持人格化 |
| 猫的生成 | 1.2s | 玩家三选一「来路」→ 决定 IND 分布 → 随机出一只猫。**不用"捏猫"界面** | 见 §2.4 |
| 首帧 | 1.2s | **锚点 01 晨光入室**（A3 已拍板） | 家，不是关卡 |
| 相机 | 1.2–9.2s | 从远景缓慢推到中景（8s） | 玩家不操作就有"走近"的感觉 |

### 2.2 路径 B · 回访进入

| 阶段 | 内容 |
|---|---|
| 淡入 | 1.2s，同路径 A |
| **离线痕迹先渲染** | 沙发压痕、地毯猫毛、日历翻页、碗空了 —— **进入时就已在场景里** |
| 离线结算 | 按 T0–T6 分档（系统 GDD §5.6.1） |
| 猫的位置 | 按 `lastState` + 离线时长推算 |
| 重逢反应 | 离线 ≥2 天时，玩家首次点击猫或 5s 无操作后触发 |
| **不自动弹日记** | 玩家点相册物件才翻开 |

### 2.3 路径 C · 异常恢复

| 情况 | 处理 | 玩家看到的 |
|---|---|---|
| 主槽损坏，副槽完好 | 静默切副槽 | **什么都不看到**（最理想） |
| 两槽都损坏 | 尝试元数据恢复 | 猫还在，但环境回到默认布置。一次性提示："屋子好像被谁动过" |
| 无痕模式 / IDB 禁用 | in-memory + 导出码 | 一次性提示：**"它记不住事了，但你们还能一起待着。"** + 一个「保存进度」按钮（导出 base64 存档码） |
| schema 版本升级失败 | 保留原存档不覆盖 | 提示："它还在，只是需要一点时间" + 联系途径 |

> **路径 C 的第一原则：绝不静默丢猫。** 丢一只养了一年的猫是不可接受的事故，宁可让玩家看到不优雅的提示，也不能让存档无声消失。

### 2.4 「来路三选一」的措辞设计（首次进入的唯一决策）

不用"捏猫"界面（破坏"它已经在那里了"的前提），改用**三个叙述性选项**：

| 选项 | 文案 | IND 分布 |
|---|---|---|
| A | 「它在外头待过一阵」 | 62–88（独立） |
| B | 「它从小就在这儿」 | 25–48（黏人） |
| C | 「别人家的猫托付给我」 | 45–70（中等） |

**关键设计**：
- **不给数值、不给性格标签**。玩家不知道自己选了"独立度 62–88"，他只知道"我选了一只流浪过的猫"
- **三个选项没有优劣**。这是设计红线——如果玩家能推理出"哪个选项更好"，这个选择就变成了优化问题，破坏叙事
- **外形完全随机**，与选项无关（概念文档 §10.3 已定：玩家不通过外形猜性格）
- **可以跳过**：若玩家 8 秒不做选择，系统随机选一个并继续（不阻塞，原则 3）

## 3. 首次进入的隐形引导设计

### 3.1 核心设计主张：「它比你先到了」

> 玩家第一次打开游戏，猫**已经在那里了**，已经在做自己的事。
> 玩家不是在"创建角色"，是在**推门进屋**。

这一条决定了后面所有设计。它同时解决了三个问题：不需要创建流程、不需要教程、玩家立刻进入"室友"而非"主人"的心理位置。

### 3.2 第一分钟逐秒设计

| 时间 | 玩家看到 | 猫在做什么 | 玩家大概率会做什么 | 系统如何响应 |
|---|---|---|---|---|
| **0.0–1.5s** | 暖光从暗渐亮 | — | 等待 | 无进度条。>3s 才出现「……」 |
| **1.5s** | **锚点 01 晨光入室**：斜切晨光从右上入，地板上有梯形光斑，灰尘在光柱里漂。**猫蜷在地毯的光斑里，只露一个头，耳朵尖透光** | 深睡，只有呼吸起伏 | 什么都不做，看 | 相机开始 8s 缓推（远→中） |
| **1.5–8.0s** | 同上 | **完全不动**。只有呼吸（脊椎 Y 偏移 ±1.5px，1Hz） | 什么都不做，看 | — |
| **8.0s** | 猫的**耳朵动了一下**（Ear_Twitch），尾巴尖卷一下 | 浅眠 | **伸手碰屏幕**（预判 92% 玩家会在此刻尝试） | 见下 |
| **8–20s** | — | 猫仍在睡 | 玩家拖拽 = 转视角 | **相机阻尼跟随（Lerp 0.1）**。这是第一个正反馈：**它教会玩家"我可以看"** |
| **20s** | 玩家撞到视角边界（水平 360° / 垂直 ±15°） | — | 继续拖 | **软回弹**（不是硬停）。教会玩家"这是个盒子，就这么多" |
| **20–45s** | 视线被引导到**地毯上的空猫碗** | — | 点它 | 食物倒入（0.6s 缓动）+ 极轻的颗粒落下声 |
| **45s** | **猫没有立刻来吃** | 仍在睡 | 等 / 再点 | **这是本作最重要的一课**：我做了一件事，它不一定来 |
| **45–60s** | 若玩家这 45 秒**没有任何有效互动** | **保底事件触发**：猫醒来 → 伸展 → 走向窗台 → 坐下看窗外 | 视线被猫的移动带走 → 跟着看窗户 | 窗户是交互物件（可开）。**这就教会了"猫会自己动，我应该跟着它看"** |

### 3.3 「不教的四件事」

> 这四条写给全体团队：**下面是刻意的"不设计"，如果有人提出要补上，请先回来读这一节。**

| # | 不教什么 | 为什么不教 |
|---|---|---|
| 1 | **不教"猫可以摸"** | 人类看到毛茸茸的东西会本能伸手。教这个是把玩家当傻子，且会破坏"我自己发现的"快感 |
| 2 | **不教"时间怎么看"** | 晨光本身就是时间。如果玩家需要被教"看光影判断时刻"，那说明光照做得不够好——**这是美术的问题，不是教程的问题** |
| 3 | **不教"日记怎么翻"** | 相册物件上"吐出一半的照片"就是提示。且**场景里的痕迹（沙发上的坑）会先勾起好奇心**——玩家是带着"它睡在哪儿"的疑问去翻日记的，这比任何教程都强 |
| 4 | **不教"它为什么会拒绝我"** | 拒绝的教学由拒绝本身完成：玩家摸深睡的猫 → 被甩尾 → 下次它会先看猫在不在睡。**这个过程叫"学会读猫"，它是本作的核心乐趣之一**，做成教程就毁了 |

### 3.4 ⚠️ 唯一破例：截图按钮常驻（与 A9 的部分冲突与裁决建议）

| 项 | 内容 |
|---|---|
| **冲突** | 美术 A9 已拍板「HUD 允许永远全隐」，美术 §6.1 定义截图按钮为「**隐藏**，鼠标悬停右下 / 玩家主动召唤」。但 **A11 已把"截图种子"列为 MVP 核心 KPI** |
| **我的判断** | **KPI 不能靠玩家自己发现。** 如果截图入口是隐藏的，相当比例的玩家永远不知道可以截图 → A11 这个核心 KPI 直接落空。而"隐藏截图按钮"带来的收益（HUD 纯粹性）远小于它的代价 |
| **裁决建议** | **截图按钮是唯一一个"默认可见但极低调"的 HUD 元素**，作为 A9「HUD 全隐」原则的**唯一例外**：<br>• 默认 `opacity: 0.35`（几乎融入背景）<br>• hover / 首次进入的前 30 秒 → `0.7`<br>• 点击时 → `1.0`<br>• 截图模式下 → 完全隐藏（保证画面纯净）<br>• 设置里可关闭（"纯净模式"） |
| **为什么这个破例是安全的** | 它是**唯一**一个，且它服务于最高优先级的目标（传播获客）。一个 0.35 透明度的 28×28 图标对"家的感觉"的破坏，远小于"玩家从不截图"对项目的破坏 |
| **需拍板** | **是**。这是对 A9 的部分修正，需主理人/用户确认 |

## 4. 可发现性设计

### 4.1 视觉优先级分级（对接美术 §5.2 三重冗余编码）

> 美术 §5.2 已定：可交互物件通过 **① 颜色微差（饱和度 +10~15%）② 形态（有"被人动过"的痕迹）③ 位置（不在死角）** 三重编码。
> **本节在此基础上加一个维度：时间。** 即"玩家预期在第几次访问发现它"。

| 层级 | 编码强度 | 物件举例 | 预期发现时机 | 设计意图 |
|---|---|---|---|---|
| **P1 · 主角** | 会动、有呼吸、在光里 | **猫** | **0–3 秒** | 不需要编码，它自己在动 |
| **P2 · 第一交互** | 饱和度 +12~15%<br>位于猫的视线/动线上<br>有使用痕迹 | 猫碗、水碗、逗猫棒 | **15–60 秒**（首访） | 这三个是"养猫"的语义入口。第一分钟必须被发现 |
| **P3 · 次级交互** | 饱和度 +8~10%<br>在常用路径上 | 玩具球、抱枕、书、杯子 | **第 2–3 次访问** | 让玩家第 2、3 次来还有新发现 |
| **P4 · 场景交互** | 饱和度 +5%<br>靠**位置合理性**（灯的开关在灯上、窗把手在窗上） | 窗、灯、洗衣机顶 | **第 3–7 次访问** | 靠"物理常识"而非视觉编码 |
| **P5 · 隐藏** | **不加任何编码**<br>纯靠探索 | 书架第二层、冰箱顶、沙发底下 | **第 2 周起** | **发现即惊喜**。这是长尾内容的核心 |

> 🎯 **设计意图**：把"可发现的东西"**按时间铺开**。如果所有可交互物件在第一分钟就被发现，第 2 周就没有新东西了；如果都藏起来，第一分钟就流失。**P2→P5 是一个刻意拉长到两周的发现曲线。**

### 4.2 预期学习曲线

| 时间点 | 玩家学会 | 系统支持 |
|---|---|---|
| **第 1 次访问**（1–3 min） | 转视角、点猫/碗、截图 | 三重冗余编码 + 截图按钮常驻 |
| **第 2–3 次** | 抚摸（长按）、喂食 | L1 物件反馈让玩家确认"这个能点" |
| **第 4–7 次** | 家具摆放、开灯开窗 | P3/P4 物件在这一阶段才被注意到 |
| **第 2 周** | **读猫的肢体语言**（耳/尾） | 6 级拒绝的 escalation 让玩家学会"它在忍耐我" |
| **第 3–4 周** | 发现 5 个隐藏锚点中的 1–2 个 | P5 物件 |
| **第 2 月** | **形成"我家猫的作息"心智模型** | 昼夜节律 + 个体性格 |

> 📌 **第 2 月那条是留存的真正开关。** 玩家一旦形成"它下午两点一定在窗台"的预期，他就不是在玩一个游戏，是在**验证一个他熟悉的生命**。

### 4.3 可发现性的量化验收（回应主理人 R4）

**主理人 R4（玩家"看不到可交互物件"）需要一个可执行的验证方案，不能只说"待 playtest"。**

| 指标 | 目标 | 测量方式 |
|---|---|---|
| **首访发现率** | ≥ **80%** 的玩家在第 1 次访问内点过猫或 P2 物件 | 埋点：首会话内的首次有效交互时间戳 |
| **首访流失前的操作次数** | ≥ **3 次**有效输入（含转视角） | 埋点 |
| **P2 物件 3 访内发现率** | ≥ **60%** | 埋点：每个可交互物件的首次点击分布 |
| **"我不知道能点什么"的反馈占比** | ≤ **10%** | 首访后弹一个**极低干扰**的单问（无 UI，用场景内的一张便签）："它今天怎么样？/ 有点不知道做什么 / 挺好" |

> **若首访发现率 < 80%**，按顺序排查：<br>① 饱和度差是否真的做到了 12–15%（美术侧 measurable）<br>② 猫碗的位置是否真的在猫的动线上<br>③ 保底事件（猫走向窗台）是否触发<br>④ 最后才考虑加视觉提示——**且必须是场景内的（便签/指纹），不是 UI**

## 5. 召唤式 HUD 规格

### 5.1 唤出方式

| 平台 | 唤出手势 | 判定阈值 |
|---|---|---|
| **桌面** | 鼠标移到屏幕**下缘 8% 区域**停留 0.4s<br>或 按 `Tab`<br>或 按 `H` | — |
| **移动 · 竖屏** | 从屏幕**下缘上滑**，位移 < 80px，松手前停顿 > 0.3s | 见 §5.2 冲突处理 |
| **移动 · 横屏** | **左下角或右下角**各一个 90×90px 角区，点按 | 横屏下下缘中部不可达（见 §8.3） |

### 5.2 手势冲突处理

**「上滑停顿」vs「拖拽转视角」** 的区分：

```
判定顺序（在 pointerup 时统一判定，不在 move 时判定）：

  位移 ≥ 80px                    → 转视角
  位移 < 80px 且 停顿 > 0.3s      → 召唤 HUD
  位移 < 80px 且 停顿 ≤ 0.3s      → 无效输入（给物件层反馈）
  位移 < 10px 且 时长 < 0.4s      → 点按（交互/唤猫）
```

**「下缘上滑」vs 系统手势**（UX-R3，见 §9）：

| 冲突 | 缓解 |
|---|---|
| iOS Home Indicator（底部横条） | 召唤热区**上移到距底边 24px 以上** |
| Android 三键/手势导航条 | 同上；并在设置中提供「召唤方式」切换 |
| 两者都不可靠时 | **提供替代手势**：双击屏幕空白处 = 召唤（与"双击=截图"冲突 → 改为**长按空白处 1.5s**） |

### 5.3 唤出内容

> **只有一条**，从下缘升起，56px 高。视觉是"从场景里长出来的纸条"，不是"浮在屏幕上的层"（美术 §6.0）。

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│                    （主游戏画面）                          │
│                                                          │
│                                                     📸   │  ← 常驻（0.35 透明度）
├──────────────────────────────────────────────────────────┤
│  🌤  19:30            相册 (2)    音量    设置           │  ← 召唤条（56px）
└──────────────────────────────────────────────────────────┘
```

| 元素 | 内容 | 备注 |
|---|---|---|
| 时刻 | 手写体 14px，如「19:30」 | MVP 无天气（U12 已定仅"晴"），Standard 加天气图标 |
| 相册 | 数字 = 未读日记数 | **不是红点 badge**——是手写数字，像便签上的计数 |
| 音量 | 默认静音（U8） | |
| 设置 | 齿轮 | 最不起眼（美术 §6.1 已定） |

**明确不包含**：关系值、需求条、任务、成就、连续登录。**永久隐藏，永不以任何形式出现。**

### 5.4 停留与淡出

| 项 | 规格 |
|---|---|
| **停留** | 唤出后 **4.0s** 无操作自动淡出 ⚙ |
| **延长** | 玩家进入任一入口（相册/设置）→ 淡出计时改为"离开该入口后 2.0s" |
| **淡出动画** | 仅 `opacity` + `transform: translateY`，**0.5s ease-out** |
| **性能约束** | 只用 `transform / opacity`，**不触发 layout / paint**（美术 §6.4 已定） |

## 6. 交互反馈规格（无震屏 / 无色闪 / 无顿帧）

> **问题**：禁用震屏、色闪、顿帧，且默认静音。玩家凭什么知道"我点到了"？
> **回答**：把"我点到了"这个单一问题**拆成四个不同的问题**，分别回答。

### 6.1 四层反馈

| 层 | 回答的问题 | 具体做法 | 时长 | **是否必给** |
|---|---|---|---|---|
| **L1 · 物件层** | **我点到这个东西了吗？** | 物件产生一个**物理上合理**的微变化：<br>• 杯子被碰得晃 2° 后回弹<br>• 书页翻动 1/4<br>• 抱枕凹陷 3mm 后缓慢回弹<br>• 猫碗被推得转 5° | 0.4–1.2s | ✅ **必给（100%）** |
| **L2 · 声音层** | 我的动作发生了吗？ | 极轻的物件音（陶瓷叮、布料沙沙），音量 **−18dB 以下** | 0.2–0.5s | ❌ 可选（默认关，U8） |
| **L3 · 猫层** | **它收到了吗？** | **Ear-ack**：耳朵朝玩家转 15–25°，0.4s 后转回。骨骼驱动，**0 morph 成本** | 0.4s | ⚠️ **70% 概率**（P = 0.85 − IND/300） |
| **L4 · 世界层** | **这件事有意义吗？** | 场景出现**持久痕迹**：猫毛多一根、碗里的食物少一点、日历翻页、水杯多一圈水印 | **永久** | ✅ 必给（若有对应痕迹） |

### 6.2 🔑 关键裁决：L1 必给，L3 抽签

> 这是本文档最重要的一条设计决策，它同时解决了两个互相矛盾的需求。

```
如果每次点都有 Ear-ack：
    玩家会学到"点了就有反应" → 猫变成一台响应输入的机器 → 猫性崩塌

如果点了连物件都不动：
    玩家无法区分"它不理我"和"我没点到" → 以为卡了 → 关页面

解法：分层。
    L1（物件层）= 确认「输入命中」，必给 —— 这是 UI 的责任
    L3（猫层）  = 确认「它收到了」，抽签 —— 这是猫的权利
```

**玩家的正确心智模型**（我们希望他学到的）：

> "我确定我点到了（因为杯子晃了），但它不理我（耳朵都没动）。"

**这一句话就是支柱三的完整表达。**

### 6.3 保底如何接入反馈层

| 情况 | 反馈 |
|---|---|
| 连续 4 次无反应（系统 GDD §4.3.2 硬保底） | 第 5 次**必定**给 L3（Ear-ack）或更强的反应 |
| L1 反馈的降级 | 输入被吞掉（冷却/预算/热盒禁用）时，L1 反馈强度降至 40%（更轻的晃动），但**仍然给** |

### 6.4 与美术 §6.3 情绪反馈语言的对应

| 情绪事件 | 美术 §6.3 定义 | 本文档补充 |
|---|---|---|
| 接受（蹭手） | 慢动作 0.5× + 暖光 emissive 渐隐 1s | — |
| **拒绝** | 转身 0.4s + 左下手写"哦"字（0.8s 淡入淡出） | ⚠️ **我建议修改**：见 §6.5 |
| 无反应 | 什么都不发生 | ⚠️ **我建议修改**：改为 L1 必给 + Ear-ack 70%，见 §6.2 |

### 6.5 ⚠️ 对美术 §6.3「拒绝」反馈的修改建议

**美术原方案**：拒绝时屏幕左下出现一个手写「哦」字（0.8s 淡入淡出）。

**我的修改建议：删掉这个「哦」字。**

| 理由 | 说明 |
|---|---|
| 1 | **它违反原则 1（场景即界面）**。「哦」是一个**屏幕上浮现的文字**，它是 UI，不是场景。玩家会从"它被我惹烦了"切换到"系统提示我互动失败" |
| 2 | **它把拒绝变成了一个事件**。拒绝应该是**猫的态度**，不是一个反馈。加一个"哦"字等于给拒绝加了 UI 确认，玩家会开始**计数**而不是**感受** |
| 3 | **它破坏拒绝的可读性梯度**。我们已经有 6 级拒绝（R1–R6），每级都是肢体语言。加一个统一的"哦"字会让 R1（无视）和 R5（拍击）看起来一样严重 |
| 4 | **"哦"这个字本身有歧义**。它可能被读作调侃（"哦，它不理我"），也可能被读作冷漠。**我们想要的情绪是"略带遗憾"，不是"被调侃"** |

**替代方案**：拒绝的反馈**全部由猫的肢体语言承担**（R1–R6，系统 GDD §4.4），配以 **L1 必给的物件层反馈**。玩家的确认感来自 L1，情绪来自猫。

**唯一例外**：R5（拍击）可以配一个极轻的声音（猫的警告声，非 UI 音效），因为 R5 是"最后警告"，需要玩家立刻意识到"我做过头了"。

> **需与林绘澄确认。** 这是我对美术圣经的一处修改建议，不是单方面推翻。

## 7. 截图与分享流程（A11 · MVP 核心 KPI）

### 7.1 三个入口

| 入口 | 平台 | 说明 |
|---|---|---|
| **相机按钮**（右下，常驻 0.35） | 双端 | 主要入口 |

### 7.2 完整流程

```
① 触发（0–0.15s）
   所有 HUD 淡出（含相机按钮本身）→ 场景进入「纯净态」
   ⚙ 移动端：此期间禁用第二次输入 0.3s（技术约束：截图 hitch 10–40ms）

② 快门反馈（0.15–0.35s）
   屏幕 5% 黑场 0.1s（美术 §7 已定）+ 可选快门音（默认关）
   ⚠️ 不是闪白——是「微暗」，符合美术 §6.3

③ 捕获（0.35s）
   canvas.toBlob（技术 Q6 已定：禁用 preserveDrawingBuffer）
   移动端禁用连拍（技术 §9.4 约束 6）

④ 确认（0.35–1.2s）⭐ 关键
   右下角出现一张「拍立得」从边缘吐出 40%
   静止 0.8s 后被「吸回」，同时存入相册
   → 这是「截图成功」的确认，且它本身是场景内的物件语言，不是 toast

⑤ 相册
   点击书架上的相册物件 → 翻阅（MVP 上限 20 张）
```

### 7.3 截图种子的引导（☀ 提示图标）

美术 §6.3 已定义：高截图价值状态出现时，**屏幕最边缘 4% 出现一个 ☀ 小图标**，1s 淡出。

**触发条件由策划定义**（这是美术留给我的）：

| 条件 | 说明 |
|---|---|
| **A · 窗台剪影** | 时段 = 昏（16–20）且 猫处于 `WATCH_WINDOW` 且 锚点 = 窗台类 |
| **B · 怪异睡姿** | 猫处于 `SLEEP_DEEP` 且 姿态 = `Sleep_BellyUp`（或 Standard 的其他怪异睡姿） |
| **C · 蹭手瞬间** | 猫执行 `Headbonk` |
| **D · 光比** | 场景当前光比 > 3:1（斜射光最强时） |

**频率限制**（防止干扰与"截图疲劳"）：

```
同一会话最多提示 3 次 ⚙
同一天最多提示 5 次 ⚙
同一条件 24 小时内不重复提示
可在设置中关闭
```

### 8.2 触摸目标尺寸

| 目标 | 最小尺寸 | 说明 |
|---|---|---|
| **猫（抚摸）** | 屏幕占比 ≥ **4%**<br>（1280×720 下约 180×110px 等效热盒） | 猫实际屏占约 100×60px，**热盒必须放大 1.8×**（用包围盒 raycast，非精确 mesh） |
| **可交互物件** | ≥ **44×44 px**（iOS HIG）<br>≥ **48×48 dp**（Android） | 等距微缩下物件可能小于此 → 用**不可见的放大热盒** |
| **相机按钮** | 触摸区 **48×48 px**（视觉 28×28） | 视觉与热区分离 |
| **下缘召唤区** | 全宽 × **60px** 高（上移到距底边 ≥24px） | 整条边都是热区 |
| **横屏召唤角区** | 90×90 px × 2（左下 + 右下） | 见 §8.3 |

### 8.3 单手可达性

| 姿态 | 拇指自然弧覆盖 | 结论 |
|---|---|---|
| **竖屏** | 屏幕下 **55%** | ✅ 相机按钮（右下）可达<br>✅ 召唤区（下缘）可达<br>❌ **相册物件（书架上）不可达** |
| **横屏（正）** | 左右下角 | ✅ 相机按钮可达<br>❌ **下缘中部不可达** |

**两个裁决**：

| # | 问题 | 裁决 |
|---|---|---|
| **M-1** | 竖屏下书架上的相册不可达 | **相册入口在 HUD 召唤条里也有一个**（不只能靠点书架物件）。另外增加**从右上缘下滑的镜像召唤手势**（左右手对称） |
| **M-2** | 横屏下下缘中部不可达 | **召唤热区改为左下角 + 右下角各一个 90×90px 角区**，下缘中部不设热区（同时避免了与拖拽的冲突） |

### 8.4 其他移动端要点

| 项 | 规格 |
|---|---|
| **CSS 防护**（可访问性兜底，非可选项） | `user-select: none; -webkit-touch-callout: none; touch-action: none`（canvas） |
| **竖屏** | 不强制旋转。改为提示条 + **视野收紧档**（相机 FOV 略窄，构图仍成立） |
| **触觉反馈** | 抚摸成功时 10ms 极轻震动（Standard 层）；**拒绝时不震动** |
| **首屏** | 不请求任何权限 |
| **离线** | Service Worker 缓存，离线时仍可打开看猫、不能看新日记 |

## 9. UX 风险登记（8 条）

| # | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| **UX-R1** | **玩家 30 秒内不知道可以点什么，直接关页面** | 🚨 **高** | ① 三重冗余编码（美术 §5.2）② 第一分钟保底事件（猫自己走向窗台，带走视线）③ 空碗放在猫的动线上 ④ L1 物件反馈必给（玩家一试就知道点到了）⑤ §4.3 的量化验收（首访发现率 ≥80%） |
| **UX-R2** | **"无反应"被读成"卡了/没点到"，玩家放弃** | 🚨 **高** | ① **L1 物件层反馈 100% 必给**（核心缓解）② 连续 4 次无反应硬保底 ③ Ear-ack 70% 概率 ④ 全局输入预算防止抖动 |
| **UX-R3** | **移动端下缘上滑与系统手势冲突**（iOS Home Indicator / Android 导航条） | 🚨 **高** | ① 热区上移到距底边 ≥24px ② 提供「长按空白 1.5s」替代手势 ③ 设置里可切换召唤方式 ④ **真机测试覆盖 iPhone SE/13/15 + 主流 Android** |
| **UX-R4** | **首次加载 > 5s，玩家以为没内容** | ⚠️ **中** | ① 1.2s 淡入遮盖（前 1.2s 无感知）② >3s 出现「……」③ 流式加载 P0 阶段 1s 内可见猫（技术 §4.2） |
| **UX-R5** | **玩家不知道"怎么回去看日记"，离线内容被浪费** | ⚠️ **中** | ① 相册物件吐出一半照片（场景内提示）② **痕迹先行**（沙发上的坑先勾起好奇）③ 重逢反应 ④ M-1 裁决：HUD 召唤条里也有相册入口 |
| **UX-R6** | **截图提示图标（☀）变成干扰** | ⚠️ **中** | ① 频率限制（会话 ≤3 / 天 ≤5 / 同条件 24h 不重复）② 位置在屏幕最边缘 4% ③ 可在设置关闭 |
| **UX-R7** | **竖屏下热盒重叠**（微缩场景物件密集） | 🟡 **低** | ① 热盒优先级：**猫 > 大件家具 > 小件** ② 重叠时取**屏幕深度最近**者 ③ 提供"热盒显示"调试开关（DEV only） |
| **UX-R8** | **长按被浏览器识别为"保存图片/选中文本"** | 🟡 **低** | CSS 三件套（§8.4）。**这是可访问性兜底，不是可选项** |

## 10. 可访问性 UX 考量（对接美术 §9）

### 10.1 与美术可访问性规格的对接表

| 美术 §9 项 | 本 UX 文档的对接 |
|---|---|
| **§9.1 定级 Standard**（色盲 + 低视力 + 动效降级，不含屏幕阅读） | 本 UX 文档遵循此定级。**MVP 不做屏幕阅读器支持** |
| **§9.2 规则 5**：可交互物件通过饱和度+形态+位置三通道 | 本 UX 文档 §4.1 在此基础上**加了时间维度**（P1–P5 分级）。**验收要求：关闭饱和度通道后，可发现性下降应 < 25%**（见 §10.2） |
| **§9.3 可独立关闭的视觉项** | 截图提示图标（☀）**需加入此表**，设为可关闭 |
| **§9.4 文字对比度**（已达标 13.5:1 / 8.2:1） | 本 UX 文档新增的文案（重逢提示、路径 C 提示）需同样达标 |
| **§9.5 动效降级** | 见 §10.3 |

### 10.2 色盲玩家的可发现性验收

| 项 | 规格 |
|---|---|
| **问题** | 美术 §5.2 的三重编码中，「饱和度」这一通道对色盲玩家失效 |
| **评估** | 剩余 2/3 通道（形态、位置）仍然有效。**理论损失 ≤ 33%** |
| **验收标准** | **关闭饱和度通道后，首访发现率下降 < 25%**（即色盲玩家发现率 ≥ 60%）。需专门招募色盲玩家做 playtest |
| **若不达标** | 加强「形态」通道：给可交互物件增加更明显的"被人动过"的痕迹（指纹、书页折角、杯沿水渍），以及**轻微的几何不规则**（美术 §1.2「软」的原则已允许） |

### 10.3 动效降级（"减少动效"模式）下的调整

| 项 | 规格 |
|---|---|
| 相机阻尼 | 关闭（瞬移） |
| 猫的过渡动画 | 0.5× 速度 |
| 灰尘漂浮 / 猫毛飘落 | 停止 |
| 阳光阴影 | 5 分钟更新一次（而非每帧） |
| **Ear-ack（本 UX 新增）** | **保留，但简化为 0.2s**（它是核心反馈通道，不能关） |
| **L1 物件反馈（本 UX 新增）** | **保留，时长减半**（同上，不能关） |
| **截图提示图标（☀）** | 改为**静态显示 2s**（不做淡入淡出） |
| **HUD 召唤/淡出动画** | 改为**瞬显瞬隐**（0s） |

> 🚨 **两条不能关**：L1 物件反馈与 Ear-ack。它们是"我点到了"的唯一保证，对**所有**玩家都是必需的，对动效敏感玩家更不能被剥夺。降级只能改时长，不能取消。

### 10.4 运动障碍

| 项 | 方案 |
|---|---|
| **长按（抚摸/梳理）** | 提供「**简化交互**」开关：点按猫身 = 抚摸（无需长按）；连点两次 = 梳理 |
| **拖拽（摆放家具）** | 提供两步替代：**选中物件 → 点目标位置** |
| **双指（缩放/拖拽）** | 提供单指替代：HUD 召唤条里有「视角：远/中/近」三段选择 |
| **原则** | **所有多点/长按/拖拽操作都必须有一个点按替代方案** |

### 10.5 键盘支持（桌面）

| 键 | 操作 |
|---|---|
| 方向键 | 转视角 |
| `Space` | 抚摸 |
| `S` | 截图 |
| `Tab` / `H` | 召唤 HUD |
| `Esc` | 关闭当前浮层 |

> **桌面键盘支持是 MVP 的 P1，不是 P0。** 理由：核心用户以触屏为主的碎片访问为主，键盘是加分项。但 HUD 召唤的 `Tab`/`H` 是 P0（它是可访问性的最低保障）。

### 10.6 认知可访问性

| 项 | 说明 |
|---|---|
| **天然友好** | 无倒计时、无失败、无文字墙、无弹窗、无多层级菜单 → 对认知障碍玩家天然友好 |
| **唯一风险** | **"无引导"** 可能让部分玩家（尤其是认知障碍或年长玩家）产生"我不知道在干什么"的焦虑 |
| **缓解** | ① 第一分钟保底事件（猫自己动，给一个可追随的焦点）② 路径 C 与 HUD 的文案**一律短句、具体、无抽象词** ③ 设置里提供「提示」开关：开启后，可交互物件在玩家 60s 无操作时**轻微呼吸一次**（幅度 2%，非高亮） |
