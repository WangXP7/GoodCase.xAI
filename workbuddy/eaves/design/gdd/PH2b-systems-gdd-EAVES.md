## 1. 系统 0 · 低压力引导系统《今日不同》（M-5 专项）

### 1.1 支柱闸门校验

**服务哪根设计支柱**：**四根全中，且是唯一一个四根全中的系统。**

- **支柱一（同住感）—主**：本系统的全部哲学建立在"**同住的人才会注意到屋里的变化**"上。任务的执行者看清单；室友才会发现"咦，今天窗帘不一样了"。
- **支柱二（时间双层刻度）—次**：「今日不同」**以真实日为生成单位**，与游戏内的 ×12 加速时钟**刻意不同步**。这创造了第二条时间刻度——**屋子按玩家的日历变化，猫按游戏的时钟生活**。
- **支柱三（猫性）—次**：猫对约一半的「今日不同」有反应，对另一半完全无视。**这又是一次三态**。玩家会学到"它对纸团有反应，对新书没反应"。
- **支柱四（低摩擦陪伴）—次**：不宣告、不计数、不奖励、不惩罚错过 → 打开 5 秒就能走，什么都不损失。

### 1.2 系统概述

**一句话定义**：每个真实日，屋里有概率出现**一处**与昨天不同的地方；它可能只是一件小事，也可能被猫注意到；系统永不告诉玩家它存在，也永不记录玩家是否发现过它。

> **它的存在理由只有一条**：
> 本作没有任务、没有榜单、没有连续登录、没有进度条。**第 5 天的玩家已经摸过猫、喂过食、截过图——新奇感耗尽。**
> 此时他打开游戏的唯一理由是"我想看看今天有什么不一样"。**如果屋子从不变化，这个理由不成立，他就静悄悄地走了。**

### 1.3 对候选方向「今天窗外有片新落叶」的裁决：**部分采纳，推翻两个隐含前提**

主理人给的候选方向是"今天窗外有片新落叶"式引导，不带数字、不带进度。

**我的裁决：采纳其核心，推翻它的两个隐含前提。**

| | 候选方向的隐含前提 | 我的裁决 | 理由 |
|---|---|---|---|
| **①** | **每天都有一片新落叶** | ❌ **推翻** | 若每天一定有，玩家第 8 天进屋时会**自动扫描窗户**。他从"看看今天怎么样"变成"找找今天有什么"——**它是伪装的任务，而且更糟，因为它没有任务清单的诚实**。必须引入**不确定性**与**强度分级**（§1.4）。 |
| **②** | **它只是窗外的一片叶子（纯视觉）** | ❌ **推翻** | 纯视觉变化看完就完了，**不产生任何玩法**。玩家看到落叶，然后呢？它不能承载留存。必须加**猫的注意层**（§1.6）——**世界的变化必须被猫看见，才算数**。 |
| **③** | **不带数字、不带进度** | ✅ **完全采纳，且升级为系统的第一铁律** | 这一条是整个候选方向里**唯一正确且不可让步的部分**。它是不成为任务的根本原因。已升格为 §1.8 的「五条不可」。 |

> **一句话总结**：把"装饰性的落叶"变成"**世界在变，而猫有时看见，有时不看见**"。

### 1.4 核心机制详述 · 触发规则与频率

#### 1.4.1 生成单位：真实日，不是游戏日

```
每日种子日界：玩家本地时区 04:00（不是 00:00）
  理由：凌晨 0–4 点打开游戏的玩家，心理上属于"昨天"。
  且这与"夜晚是一天中最长的时段"一致（夜档跨零）。

dailySeed = hash(saveId, dateKey)      // dateKey = 本地日期，04:00 分界
  → 完全确定性，可复现（满足 RUL-9 的 RNG 种子化要求）
  → 玩家改系统时间不能刷（改到未来会得到未来的种子，但离线结算被 clamp）
```

#### 1.4.2 强度分级与频率分布

「今日不同」**不是有/无的二元**，而是四档分布：

| 档 | 名称 | 玩家会看到什么 | 举例 | 猫注意率 |
|---|---|---|---|---|
| **0 档** | **静默日** | 什么都没有。今天很平常。 | — | — |
| **1 档** | **微变** | 需要仔细看才发现 | 书翻了一页 / 沙发压痕位置变了 / 窗外多停了一只鸟 / 日历上的字被划掉一天 | ~25% |
| **2 档** | **可见** | 一眼能看出 | 窗台上落了一片叶子 / 地上多了一个纸团 / 光斑的形状不一样了 / 抱枕换了个方向 | ~55% |
| **3 档** | **事件** | 猫本身处于一个罕见状态 | 它跳上了冰箱顶 / 它以一个完全违反解剖学的姿势睡着 / 它把杯子推倒了 | 100%（它自己就是事件） |

**基础分布** ⚙：

```
P(0 档) = 0.25   P(1 档) = 0.50   P(2 档) = 0.20   P(3 档) = 0.05
```

#### 1.4.3 ⭐ 关键设计：密度随天数递减（屋子的变化率必须随时间下降）

> **这一条是本系统最重要的设计决策，也是它区别于所有"每日内容"机制的地方。**

```
静默率（0 档概率）随玩家天数变化 ⚙：

  D0–D1   : 100%   ← 刻意静默。屋子本身就是新的，不需要额外变化
  D2–D7   :  10%   ← M-5 死亡谷。这是唯一需要系统托举的窗口
  D8–D30  :  25%   ← 基线（= 基础分布）
  D31–D90 :  35%
  D90+    :  45%   ← 退居背景噪声
```

**为什么必须递减**：

1. **前期**：玩家还没建立"这个屋子会自己变"的信念。**必须先证明它。** 所以 D2–D7 密度最高——这是对 M-5 死亡谷的精准投放。
2. **后期**：**"家"的语义是恒常。** 一个玩到第 90 天还天天换样的屋子，不是家，是**展厅**。
   玩家第 90 天打开游戏，想看的不是"今天又换了什么"，而是"**它还在那儿，还是老样子**"。
3. **反直觉但关键**：**降低后期密度不是削弱，是保护。** 若后期还在高频变化，玩家会产生"我得每天来看，不然错过了"的焦虑——**那就变成了 FOMO，本系统的全部努力付之一炬。**

> 🎯 **这一条同时回答了主理人的"第 1/7/30/90 天分别给玩家什么"（见 §1.10）。**

#### 1.4.4 3 档「事件」的额外规则

3 档是唯一的"猫本身就是内容"的档位，它**不适用槽位抽取**，直接从「罕见状态池」抽取：

| 事件 | 触发条件（附加） | 截图价值 |
|---|---|---|
| 怪异睡姿 | `SLEEP_DEEP` 且 `SEC ≥ 50` | ⭐⭐⭐ 锚点 03 |
| 跳上从未去过的高位 | `discoveredAnchors` 中存在未访问的高位锚点 且 `CUR_eff ≥ 55` | ⭐⭐ |
| 推倒桌上的东西 | `PLAY` 且 桌面槽有物件 且 `VIT ≥ 60`（Standard 才有姿态） | ⭐⭐ |
| 盯着一个不存在的东西看 | 随机，`WATCH_WINDOW` 变体 | ⭐ |
| 在完全装不下它的容器里 | 需 Standard 的纸箱类家具 | ⭐⭐⭐ |

**3 档的全年分布**：5% 基础 × 加权 → 玩家平均每 **20 天**遇到一次。它必须稀有，因为它是"今天运气特别好"的时刻，而不是"今天该做的事"。

### 1.5 核心机制详述 · 内容生成方式（三层结构，非点子清单）

> **要求**：不能是"增加随机事件"。下面给出的是**生成器**，它的输出空间远大于任何手工列表。

```
今日不同 = 槽位(Slot) × 变体(Variant) × 修饰(Modifier)
```

> 若不可见，需要美术调整物件位置或相机可达范围。**这是本系统的资产前置依赖。**

#### 1.5.2 第二层 · 变体（Variant）—— 每个槽位的 4–8 种变化

**部分示例**（完整表由美术与策划共同补全，需 0.5 人日，见 ART-6）：

| 槽位 | 变体示例 |
|---|---|
| S01 窗台 | 一片落叶 / 一只飞虫停在玻璃内侧 / 一只玻璃瓶被挪了 3cm / 干花掉了一片花瓣 |
| S03 窗外 | 多停了一只鸟 / 云的形状不同了 / 对面楼的灯亮着 / 树枝上多了个塑料袋 |
| S04 桌上的书 | 翻了一页 / 合上了 / 多了一枚书签 / 被挪到了沙发上 |
| S05 沙发面 | 压痕位置变了 / 多了一根猫毛 / 抱枕倒下了 / 多了一条毯子 |
| S07 碗边地面 | 洒了几粒猫粮 / 多了一小滩水 / 猫碗被推歪了 |
| S10 冰箱顶 | 多了一层灰被擦出一道痕 / 出现了一个小纸团 / 猫的爪印 |

> **变体的设计红线**：
> 1. **绝不能是"新功能"**——它不能解锁任何东西、不能给数值、不能成为可交互物件（除非它本来就是可交互物件的新摆放）。
> 2. **必须有 60% 以上是"生活痕迹"而非"新增物品"**——翻开的书比新到的包裹更符合本作气质。**屋子在生活，不是在进货。**

#### 1.5.3 第三层 · 修饰（Modifier）—— 让同一变体在不同日子读起来不同

| 修饰源 | 作用 | 示例 |
|---|---|---|
| **季节** | 过滤 + 替换变体池 | 冬天不会有"蝴蝶停在窗台"；秋天落叶变体权重 ×3 |
| **天气** | 过滤 + 偏向槽位 | 雨天偏向窗内槽位（S02 水痕、S11 地垫湿了），排除 S03 窗外 |
| **时段** | 影响可见性 | 夜间的 S03 窗外变体多半看不见（改为"对面楼亮着一盏灯"） |
| **猫性格** | 过滤 | `SEC < 25` 的猫不会触发"跳上冰箱顶"（它不敢）；`CUR < 30` 的猫不会触发新物件类 |
| **AFF 阶段** | 过滤 + 语调 | "它把头搁在你常坐的那边"仅在 AFF ≥ 60 时可生成 |
| **最近历史** | 去重（见下） | — |

#### 1.5.4 抽取算法与去重规则

```
1. 取 dailySeed 的随机流（确定性，RUL-9 兼容）

2. 定档：
   静默率 = f(玩家天数)            // §1.4.3 曲线
   if roll < 静默率: 今日无「今日不同」，写 dailyDifference = null，结束

3. 选槽位：
   w(s) = baseWeight(s) × recencyPenalty(s) × modifierFilter(s)
     baseWeight   由槽位显著性决定（高 1.0 / 中 0.7 / 低 0.4）⚙
     recencyPenalty(s) = (s 在最近 7 天内出现过) ? 0.15 : 1.00   ⚙

4. 选变体：
   w(v) = variantWeight(v) × seasonWeatherModifier(v) × recencyPenalty(v)
     recencyPenalty(v) = (v 在最近 30 天内出现过) ? 0.10 : 1.00   ⚙
   附加硬规则：最近 10 条内不得重复同一 (槽位, 变体) 组合

5. 应用修饰：季节 → 天气 → 性格 → AFF 阶段 逐级过滤
   若过滤后候选为空 → 降级为 0 档静默日（不是硬塞一个不合适的）

6. 判定猫是否注意（§1.6）

7. 写入存档：
   environment.dailyDifference = {
     dateKey, tier, slotId, variantId, catNotices, permanent, appliedAt
   }
   保存最近 10 条历史用于去重
```

> **去重的第一性原则**：宁可静默，不要重复。
> 玩家第 12 天看到"窗台上又落了一片叶子"，他会立刻意识到**这是一个循环播放的列表**，幻觉瞬间破灭。
> **一次尴尬的重复，比十次静默日的伤害更大。**

### 1.6 核心机制详述 · 第二层：猫的注意（把世界变化翻译成猫的行为）

> **这是「今日不同」从装饰变成内容的唯一路径。**

```
猫注意到「今日不同」的概率：

  P(notice) = clamp( salience × 0.6 + CUR_eff/250 + (1 − IND/200) × 0.2 , 0.05, 0.85 )   ⚙

    1 档微变 → salience = 0.25
    2 档可见 → salience = 0.55
    3 档事件 → 不适用（猫自己就是事件）

  示例（CUR_eff = 45, IND = 60）：
    1 档：0.25×0.6 + 0.18 + 0.7×0.2 = 0.15+0.18+0.14 = 0.47
    2 档：0.55×0.6 + 0.18 + 0.14   = 0.33+0.18+0.14 = 0.65

  示例（CUR_eff = 20 胆小猫, IND = 60）：
    1 档：0.15 + 0.08 + 0.14 = 0.37
    2 档：0.33 + 0.08 + 0.14 = 0.55
```

**若命中，猫的反应按性格分流**：

| 条件 | 猫的行为 | 玩家读到 |
|---|---|---|
| `CUR_eff ≥ 50` 且 `SEC ≥ 45` | `EXPLORE` → 走过去闻、可能拨弄 | "它发现了" |
| `CUR_eff ≥ 50` 且 `SEC < 45` | `WATCH` → 远距离盯着，数分钟不动 | "它想看又不敢" |
| `SEC < 30` | 不起反应，且若物件在动线上会**绕路走** | "它怕那个东西" |
| `CUR_eff < 50` | **完全无视**（Ear-ack 按既有 70% 规则） | "它对那东西没兴趣" |

**若未命中**：什么都不发生。**这是合法的，且必须真实存在。**

> 🚨 **设计红线**：猫**绝不**因为「今日不同」而给玩家任何数值奖励。
> **唯一的例外**：若「今日不同」产生的是**可交互的新物件**（如一个纸团），猫去探索它 → 触发现有的 `CUR +8`（新物件规则，前半段 GDD §3.3.1 ③ 已定义）。
> **这不是新奖励，是既有规则的自然应用。**

**「想看又不敢」是最有价值的一条**：它会在**玩家不在时**偷偷去查（前半段 GDD §3.3.2 组合 8 已定义此行为）→ **这是离线日记的最佳素材**。具体接口见 §1.14。

### 1.7 核心机制详述 · 第三层：痕迹留存（永久的部分累积成家的历史）

「今日不同」按**持久性**分两类：

| 类型 | 占比 ⚙ | 举例 | 命运 |
|---|---|---|---|
| **瞬时** | 55% | 光斑形状、云、鸟、对面楼的灯、猫的姿势 | 当天结束时消失，**不留记录** |
| **永久** | 45% | 落叶、纸团、被推倒的杯子、翻开的书、沙发上的新压痕 | 留在场景里，成为家的一部分 |

**永久物件的命运分三支**：

```
① 被清理：玩家「收拾」→ 消失（Standard 动词，MVP 用「摆放」的长按变体，见 §9 R-7）
② 被猫接管：猫把它当玩具/垫子 → 升级为可交互物件，进 discoveredAnchors
③ 自然留存：既不被清理也不被接管 → 累积，最多 6 件 ⚙
             超出后，最旧的一件在玩家不在线时被"收走"（叙事上：被收拾了）
```

> ⚠️ **为什么允许自动收走地上物件，却不允许自动删玩家的截图**（见 §6.3）：
> **系统有权丢弃世界的噪声，无权丢弃玩家的作品。** 这是两个完全不同的伦理位阶。

**累积的永久物件 = 「家的历史」的可视化**：
第 90 天的玩家看着屋里——沙发上有三个深浅不一的压痕、书架第二层有个它够不着的位置、窗台上有一片没被吹走的叶子——**这些是他三个月生活的物证**。这是 §1.10 第 90 天答案的物质基础。

### 1.8 ⭐ 为什么它不违背四根支柱：**五条不可**

> 主理人说："任何引导都有变成任务的倾向，要说清边界。"
> **边界就是下面五条。任何一条被打破，这个机制就变成了它要解决的问题本身。**

| # | 不可 | 具体含义 | 违反后会变成什么 |
|---|---|---|---|
| **1** | **不可宣告** | 系统**永不**以任何形式告知"今天有一个不同"。无图标、无提示、无红点、无日记预告、无加载时的暗示文案。 | 每日任务的提示 |
| **2** | **不可计数** | 存档里**只存"生成了什么"，绝不存"玩家发现了几个"**。<br>**实现层硬约束：数据模型中不存在 `discoveredCount` / `foundList` 字段。** | 收集进度 x/50 |
| **3** | **不可奖励** | 发现它不给任何数值。不涨 AFF、不涨 SEC、不给道具。<br>唯一例外是 §1.6 的既有 `CUR +8` 规则（猫对新物件的反应，不是对玩家的奖励）。 | 每日签到奖励 |
| **4** | **不可要求** | 玩家看不见、不点、不理，什么都不会发生。**不存在任何"你有未查看的内容"状态。** | 未完成的任务 |
| **5** | **不可惩罚错过** | 昨天有一个，你没来？那就没看到。**它不等你、不积压、不提示"你错过了一个"。** | FOMO |

**与四根支柱的逐条对应**：

| 支柱 | 本系统如何服务它 | 若违反五条不可会怎样 |
|---|---|---|
| **一 · 同住感** | 玩家是**发现者**，不是执行者。任务说"你该做这件事"；「今日不同」说"屋里有一件小事发生了，你可能会看到，也可能不会。看到的人会觉得自己运气好。"——**前者是义务，后者是运气。** | 玩家从"室友"降级为"任务执行者"，支柱一塌陷 |
| **二 · 时间双层刻度** | 生成单位是**真实日**（与游戏内 ×12 时钟不同步）。玩家的第一层刻度（我的日历）与猫的第二层刻度（它的时钟）在此交汇。 | 变成"游戏内每日事件"，与游戏时钟合并，双层刻度消失 |
| **三 · 猫性** | 猫对约一半的它有反应，对另一半完全无视。**这又是一次三态。** 玩家学到"它对纸团有反应，对新书没反应"——这是"读猫"的又一个维度。 | 若猫每次都必然反应，猫变成"变化探测器"，猫性崩塌 |
| **四 · 低摩擦陪伴** | 不宣告、不计数、不奖励 → **打开 5 秒就能走，什么都不损失**。 | 产生"我得扫一眼屋子再走"的义务感，摩擦产生 |

### 1.10 ⭐ 第 1 / 7 / 30 / 90 天分别给玩家什么

> **这是主理人明确要求回答的问题。**

| 天数 | 玩家的处境 | 系统给他什么 | 谁是主力 |
|---|---|---|---|
| **第 1 天** | 一切都是新的。屋子本身、猫本身、光照本身，就已经是全部内容 | **不需要「今日不同」。系统刻意静默（100%）。**<br>他要做的是推门进屋、看见晨光、看见猫、试着伸手 | **首帧与首分钟**（UX §3.2）。<br>「今日不同」在此刻若插进来，是**对首次体验的干扰** |
| **第 5 天**<br>（M-5 死亡谷） | 摸过、喂过、截过图。新奇感耗尽。还没形成任何习惯 | **「今日不同」全功率运行（静默率仅 10%）。**<br>他学到的不是"今天有什么"，而是**"这个屋子是会自己变的"**——这个信念一旦建立，回访动机就有了着落 | **系统 0 承担主力。**<br>同时 D7 左右猫的性格开始可辨（沙盘：躲避极差 32pp），**"它是什么脾气"开始成为第二个钩子** |
| **第 30 天** | 已经相信屋子会变。开始认得猫的习惯 | 主力从"世界在变"转移到三件事：<br>① **猫的习惯**（它偏爱的位置、它的作息）<br>② **家的历史**（压痕、猫毛、日历、那片没被吹走的叶子）<br>③ **关系阶段**（AFF 49–54 进入"信任"：它在你附近睡、会慢眨） | **系统 1 + 系统 3**。<br>「今日不同」退居背景（静默率回到 25%） |
| **第 90 天** | **系统已经不需要给他任何东西了** | 留存靠**牵挂 + 表达 + 真实世界的季节**：<br>① **牵挂**：AFF 74–80"亲近"，它主动蹭你、等你<br>② **表达**：相册里 40+ 张截图 = "我和它的三个月"<br>③ **季节**（Standard）：窗外从夏入秋 | **玩家自己**。<br>「今日不同」的角色降为**"防止屋子完全静止"的底层噪声**（静默率 45%）——<br>**它的存在感应低到玩家意识不到，但拿掉它屋子就"死"了** |

> 📌 **这张表的核心论点**：
> **留存的接力棒必须从"系统给内容"传给"玩家自己有理由"。**
> 第 1 天给内容，第 5 天给变化，第 30 天给关系，第 90 天——**给他自己**。
> 「今日不同」的作用不是永远提供内容，而是**在第 5 天到第 30 天之间，把玩家扶到"他自己会回来"的那条线上**。

#### 1.11.2 ⭐ A/B 验证设计（唯一可信的判据）

```
组 A（对照）：关闭「今日不同」——屋内零自发变化
组 B（实验）：按本文档运行

样本：每组 ≥ 300 名真实玩家，观察 14 天
主判据：D14 留存差
辅助判据：M5-K4（时长）、M5-K5（截图率）
```

**判定规则**：

| 结果 | 判定 | 处置 |
|---|---|---|
| B 组 D14 留存提升 **≥ 5pp** | ✅ **机制有效** | 进入调参阶段 |
| 提升 **2–5pp** | 🟡 **弱有效** | 优化槽位显著性与 3 档事件权重；**不提高频率** |
| 提升 **< 2pp** | ❌ **机制无效** | **换方向，而不是加强它** |

> 🚨 **这是本系统最重要的一条验收条款**：
> **如果机制无效，正确的处置是换方向，不是加强它。**
> 因为"加强"的手段无非是提高频率、提高显著性、加提示——**而这三件事恰恰会把「今日不同」变成任务。**
> **一个失败的「今日不同」，加强后是一个成功摧毁支柱一的任务系统。这是比无效更糟的结果。**

#### 1.11.3 ⚠️ 任务化的早期信号（反直觉的失败判据）

> **若 playtest 中出现下列表述，机制判定为"开始任务化"，处置是削弱而非加强。**

| 信号 | 玩家可能会说 | 处置 |
|---|---|---|
| **扫描行为** | "我每天进来先扫一遍窗台" | 降低 2 档可见频率；把高显著性槽位（S01/S03）权重下调 |
| **计数行为** | "我已经找到 7 个了" | **立刻停用手写数字类的任何暗示**；检查是否有隐藏的计数 UI |
| **补偿心理** | "昨天没上线，不知道错过了什么" | 提高静默率（让玩家无法建立"每天都有"的预期） |
| **目标化** | "今天的目标是找到它" | 降低 3 档事件频率（它太稀有了就会变成"大奖"） |

## 2. 系统 1 · 房间与家具系统（P1）

### 2.1 支柱闸门校验

**服务哪根设计支柱**：**支柱一 · 同住感（主）** + **支柱四 · 家的诗意（次）**。

- **支柱一**：概念文档 §3.2 把"布置的猫性适配"定为**全游戏的心流锚点**——"它把'整理房间'变成了'为它布置一个家'"。**本系统就是这个决策点的完整机制化。**
- **支柱四**：痕迹（压痕、猫毛、水印、日历）是"家的诗意"的物质承载。
- **间接服务支柱三**：猫对家具的**偏好与拒绝**（它用/它不用/它躲）是猫性的表达通道。
- **不服务支柱二（时间）**：房间不随时间变化（那是系统 2 与系统 0 的职责）。**明确切割，防止职责蔓延。**

### 2.2 系统概述

**一句话定义**：定义屋里的空间如何被划分成"猫可停留的位置（锚点）"、玩家如何通过摆放家具改变这些锚点的属性、以及猫如何在这些锚点之间按性格做选择。

**范围锁定**（RUL-2）：**客厅 + 厨房角落**。MVP 内置 **8 件可移动家具**（概念文档 MVP 不做清单：❌ 家具商店/解锁，仅做 6–8 个内置家具）。

### 2.3 设计目标（可验证）

| # | 目标 | 验证方式 | 状态 |
|---|---|---|---|
| **G-F1** | **玩家在 3 次访问内能说出至少 1 条猫的位置偏好** | 回访访谈："它一般喜欢待在哪儿？"能说出具体位置的比例 ≥ 50% | 待 playtest |
| **G-F2** | **不存在"最优摆放"** | 不存在任何单一摆放方案能在全部 4 时段 × 3 天气 × 4 季节下都是最优 | ✅ 设计保证（偏好随 Light(a,t) 漂移，见 §2.4.3） |
| **G-F3** | **玩家摆错不会有失败态** | 任何摆放都不会导致猫"无处可去"或任何数值归零 | ✅ 设计保证（`REST` 恒有权重，见 E-F2） |

### 2.4 核心机制详述

#### 2.4.1 锚点（Anchor）—— 猫可停留的位置

**定义**：锚点是场景中的一个**命名位置**，带一组属性。猫的状态机在需要更换位置时，从锚点集合中选择目标。

**锚点属性表**

| 属性 | 类型 | 范围 | 说明 |
|---|---|---|---|
| `id` | string | — | 如 `windowsill_sun` / `sofa_center` / `fridge_top` |
| `type` | enum | 软面/半软/硬面/高位开阔/高位封闭/低位封闭/功能 | 决定基础权重与性格修正 |
| `sunExposure` | 0–1 | 动态 | **由系统 2 提供**，随 slot × 天气 × 季节变化 |
| `shelterDegree` | 0–1 | 静态 | 遮蔽程度（床底 0.9 / 柜内 0.8 / 桌下 0.6 / 开阔 0.0） |
| `heightTier` | 0–3 | 静态 | 0 地面 / 1 椅面 / 2 台面 / 3 柜顶 |
| `softness` | 0–1 | 静态 | 沙发 0.9 / 地毯 0.5 / 瓷砖 0.05 |
| `thermal` | −1..+1 | 静态+季节 | 厨房瓷砖夏 −0.7 / 毛毯冬 +0.8 |
| `distToPlayer` | 米 | 动态 | 玩家视点（相机焦点）到锚点的距离 |
| `freshness` | 0–1 | 动态 | 新放置 → 1.0，7 天线性衰减 |
| `visitCount` | int | 累积 | 猫的到访次数，驱动熟悉度与压痕 |
| `discovered` | bool | 累积 | 见系统 3 |

**MVP 锚点总数**：**14 个**（需美术按场景布局最终确认，见 ART-7）。

| 区域 | 锚点 |
|---|---|
| 客厅 | 沙发中央、沙发左角、沙发右角、地毯中央、茶几下、书架第二层、书架顶、窗台（日照）、椅面 |

#### 2.4.3 ⭐ 猫的锚点偏好公式（本系统的核心）

```
U(a) = Base(a) × Light(a,t) × Comfort(a) × Height(a) × Shelter(a) × Social(a) × Novelty(a) × Familiar(a)

仲裁：与系统 1（前半段 GDD §3.3.3）完全一致——
      sharp = raw^1.60 / Σ raw^1.60
      p(a)  = 0.92 × sharp(a) + 0.08 / |候选|
      加权随机抽取
```

> **为什么必须复用同一套 sharp/surprise 机制**：
> 锚点选择和行为选择是同一个问题的两面。若用两套仲裁，猫会表现出"行为有性格、位置没性格"的分裂感。
> **8% 的惊喜配额在这里同样重要**——它保证"它今天居然睡在纸箱里"这种事会发生。

**表 2.4.3-A · 锚点类型基础权重 `Base(a)`**

| 锚点类型 | Base | 说明 |
|---|---|---|
| 软面（沙发坐垫 / 抱枕 / 毛毯） | **1.20** | 猫的最爱 |
| 半软（地毯 / 椅垫 / 纸箱） | 1.00 | 基准 |
| 硬面（地板 / 桌面 / 瓷砖） | 0.70 | **夏季偏好反转**（见 Thermal） |
| 高位开阔（书架顶 / 冰箱顶 / 洗衣机顶） | 0.85 | 需 SEC 支持 |
| 高位封闭（书架第二层 / 柜内） | 0.60 | 低 SEC 的避难所 |
| 低位封闭（床底 / 沙发底 / 茶几下） | 0.55 | 极低 SEC 专用 |
| 功能（碗 / 盆） | — | **不参与仲裁**，由生理需求直接驱动 |

**表 2.4.3-B · 七个修正项**

| 项 | 公式 | 范围 | 说明 |
|---|---|---|---|
| `Light(a,t)` | `1 + k_light × (sunExposure(a,t) − 0.5)`<br>`k_light = 0.9 + VIT/200` ⚙ | 0.55 – 1.45 | **阳光位。阴雨天 sunExposure 普遍偏低 → 该项趋于 1，晒太阳锚点自动失效** |
| `Comfort(a)` | `softness(a)^0.6 × (0.8 + SEC/500)` ⚙ | 0.50 – 1.30 | 不安全的猫更需要"能陷进去"的地方 |
| `Height(a)` | `1 + (IND/100 − 0.5) × (SEC/100) × 2 × (heightTier(a) − 1)` ⚙ | 0.40 – 1.80 | **高独立 + 高安全 → 高位开阔**；低 SEC 无论 IND 都下压 |
| `Shelter(a)` | `(1 − SEC/140) × shelterDegree(a) + 1` ⚙ | 1.00 – 1.70 | SEC 越低越爱遮蔽 |
| `Social(a)` | `1 + (AFF_eff/100 − 0.5) × INDterm × distTerm(a)`<br>`INDterm = (IND < 50) ? +1.0 : −0.4` ⚙<br>`distTerm = clamp(1.2 − dist/4, −0.5, 1)` | 0.70 – 1.40 | **高 AFF + 低 IND → 贴近玩家；高 IND → 反向（傲娇：在附近但不贴着）** |
| `Novelty(a)` | `1 + freshness(a) × CUR_eff/100` ⚙ | 1.00 – 1.50 | 新家具 / 新物件；`freshness` 7 天线性衰减 |
| `Familiar(a)` | `1 + min(visitCount(a), 40)/200` ⚙ | 1.00 – 1.20 | **老位置加成**——解释"它总睡同一个坑" |

**示意演算**（3 个锚点 × 2 只猫，仅为验证公式能产生区分，非沙盘实测）

| | 雪团（IND85 SEC35 CUR70） | 年糕（IND25 SEC60 CUR45） |
|---|---|---|
| **窗台日照位** | `1.00×1.32×0.75×1.51×1.49×1.13×1.35×1.08 = ` **2.95** | `1.00×1.32×0.82×0.62×1.29×1.24×1.22×1.08 = ` **1.47** |
| **沙发中央** | `1.20×1.00×0.98×0.68×1.00×1.06×1.00×1.15 = ` **0.98** | `1.20×1.00×1.02×1.13×1.00×1.31×1.00×1.15 = ` **2.09** |
| **冰箱顶** | `0.85×1.00×0.62×1.51×1.00×0.87×1.00×1.02 = ` **0.70** | `0.85×1.00×0.65×0.62×1.00×1.16×1.00×1.02 = ` **0.41** |

#### 2.4.4 摆放 → 锚点 → 猫：教学闭环

> **这是概念文档 §3.2「决策点 1 · 布置的猫性适配」的机制化。**

```
玩家放软垫在窗台
   → 生成新锚点 {type: 软面, sunExposure: 0.9, heightTier: 2}
   → 该锚点 U 值跃升（Light × Comfort 双高）
   → 猫开始去那儿
   → 玩家学到："它喜欢有太阳的软地方"        ← 正向反馈

玩家把书架移到窗前
   → 遮挡 → 窗前区域所有锚点 sunExposure 降至 < 0.2
   → 猫不再去窗台
   → 玩家看到"它不来了"
   → 玩家自己移开书架                        ← 负向反馈（但无失败态、无提示）

玩家把软垫放在角落（无光）
   → 新锚点 U 值低
   → 猫不去，或偶尔去
   → 玩家学到："位置很重要"                  ← 中性反馈
```

> 🚨 **关键：系统永不告诉玩家"你放错了"。**
> **猫的行为是唯一的反馈通道。** 这是支柱一（同住感）与"不教的四件事"（UX §3.3）的共同要求。
> 玩家学会的不是"最优摆放"，而是"**它喜欢什么**"——**这是关系知识，不是系统知识。**

#### 2.4.5 痕迹系统（与美术圣经 §5.3 对接）

| 痕迹 | 累积规则 | 上限 | 可清理 | 清理方式 |
|---|---|---|---|---|
| **地毯猫毛** | +2 根 / 游戏日；**春秋换毛季 ×1.5** ⚙ | 24 根 | ✅ | 「梳理」动作清零 |
| **沙发压痕** | `visitCount(sofa_center)` 达 20 / 60 / 150 时各升 1 档，共 **3 档** | 3 档 | ❌ | 永久（家的证据） |
| **桌面水印** | 玩家在茶几放置杯子后 +1 | 5 | ✅ | 可擦，但下次还会有 |
| **墙上日历** | 每真实日 +1 | — | ❌ | 自己走 |
| **地上物件** | 系统 0 产生的永久物件，每件占 1 格 | 6 件 ⚙ | ✅ | 「收拾」动作 |

**痕迹的设计原则**：

1. **不清理也可以** —— 概念文档 MVP 不做清单明确："不清理也可以，是'家'的证据"。
2. **清理不产生任何数值收益** —— 若清理给 AFF，玩家会开始"打扫"，那是对本作气质的背叛。
   **唯一的例外**：「梳理」是既有的互动动词（前半段 GDD §4.3.1），它的收益来自**猫**而非**清洁**。
3. **痕迹必须有上限** —— 无限累积会让画面变脏，也会在长线产生性能问题。

## 3. 系统 2 · 光照 / 天气 / 季节系统（P1 · 受 RUL-1 强约束）

### 3.1 支柱闸门校验

**服务哪根设计支柱**：**支柱二 · 时间的双层刻度（主，与时间系统共担）** + **支柱四 · 家的诗意（次）**。

- **支柱二**：主理人裁决令 RUL-1 的理由写得很清楚——「支柱二的实质内容是'光会移动'」。**本系统是"光会移动"的唯一技术落地。**
- **支柱四**：黄昏、雨天的窗、季节的窗外——这些是"家的诗意"的视觉主载体（概念文档 §6 锚点 01/02/05）。
- **间接服务支柱三**：天气改变猫的行为（见 §3.6.3），这是猫性的额外表达通道。
- **不服务支柱一**：光照不因玩家行为改变（除开关灯）。**这是刻意的**——玩家改变不了太阳，正如改变不了一只猫的本性。

### 3.2 系统概述

**一句话定义**：在 RUL-1 的硬约束下（4 套 lightmap、季节与天气一律不走 lightmap），用**主光 + 全屏 LUT + 窗外景物 + 少量可换道具**这四层，表达出"时间在走、季节在换、天气在变"。

**MVP 范围**（U12）：**晴 + 无季节基线**。
**但**：MVP 实现的是**这套系统的一个特例配置**（`weather = "sunny"` 常量、`season = "late_spring"` 常量），**不是它的缺失**。Standard 加入季节/天气时**不需要重做任何光照管线**——这是本系统的核心架构承诺。

### 3.3 设计目标（可验证）

| # | 目标 | 验证方式 | 状态 |
|---|---|---|---|
| **G-L1** | **一次 5 分钟会话能看到时间在走** | 光斑位移 ≥ 半个猫身、色温变化 ≥ 300K、猫完成 ≥1 次状态转移 | 依赖 ×12（RUL-4） |
| **G-L2** | **时段切换不可见为"切换"** | 玩家在访谈中不会提到"画面跳变了一下" | 待 playtest |
| **G-L3** | **季节不增加 lightmap 套数** | lightmap 索引基数恒 = 4（或降级后 = 2） | ✅ **设计证明**（§3.4） |
| **G-L4** | **天气有玩法影响，不只是视觉** | 每种天气至少改变 1 个猫的行为权重 ≥ 15% | ✅ 设计保证（§3.6.3） |

### 3.4 核心机制详述 · 四时段与淡入（RUL-1 落地）

#### 3.4.1 四时段的边界与观感

> **与前半段 GDD §5.4.4 一致**（晨 05–11 / 午 11–16 / 昏 16–20 / 夜 20–05），本文档补充**淡入的观感描述**与**季节对边界的影响**。

| 时段 | 游戏内时间 | lightmap 锚点时刻 | 主光色温 | **淡入观感描述（玩家应该感到什么）** |
|---|---|---|---|---|
| **晨** `slot_morning` | 05:00 – 11:00 | 08:00 | 4500K 暖白 | **"光是从右边慢慢爬进来的。"** 光斑在地板上从窗根向屋子中央推移，边缘从锐利逐渐变柔和；灰尘光柱由细变粗；猫毛的轮廓从半透明变得清晰。**这是本作的招牌画面**（锚点 01） |
| **午** `slot_noon` | 11:00 – 16:00 | 13:00 | 5500K 中性白 | **"光停在头顶上，屋子里很安静。"** 光斑收缩到窗正下方，投影短而淡；灰尘光柱几乎消失（顶光无斜射）；整屋亮度最高、对比最低。**这是"暂停"的时刻**（美术 §2.3） |
| **昏** `slot_dusk` | 16:00 – 20:00 | 18:00 | 3000K 深暖 | **"影子开始长，屋子开始变 orange。"** 光斑从窗下拉长成一条斜带，长度是正午的 3–4 倍；窗框的影子投到对面的墙上；灰尘光柱重新出现且最浓。**截图黄金档**（锚点 02） |
| **夜** `slot_night` | 20:00 – 05:00 | 23:00 | 2700K 极暖 + 窗外蓝 | **"外面蓝下去了，屋里还剩一盏灯。"** 自然光退到只剩窗边的微弱蓝调；室内灯成为主光源；猫的轮廓靠 rim light 维持。**窗内外形成冷暖对比** |

#### 3.4.2 ⭐ 淡入的两个时间尺度（解决 RUL-1 与前半段 GDD 的表述冲突）

> **冲突**：RUL-1 说"时段间 **0.8s** 交叉淡入"；前半段 GDD §5.4.4 说"时段边界 **±45 游戏分钟** = crossfade 窗口"。
> **二者不是同一件事。以下是裁决后的统一表述（同时列入 §9 修订建议 R-2）。**

```
┌─────────────────────────────────────────────────────────────────┐
│  过渡窗（Transition Window）· 45 游戏分钟                        │
│  = 主光 direction / color / intensity 的连续插值区间             │
│    · 这是玩家"感知到"的时间过渡——光在慢慢变                      │
│    · 边界前 22.5 分钟开始，边界后 22.5 分钟结束                   │
│    · ×12 加速下 = 225 真实秒 ≈ 3.75 分钟                         │
│                                                                  │
│         ├────────────── 45 游戏分钟 ──────────────┤             │
│  ───────┼────────────────────┬───────────────────┼──────►       │
│      窗开始              过渡窗中点            窗结束            │
│      (边界−22.5min)      (= slot 边界)      (边界+22.5min)      │
│                              │                                   │
│                              ▼                                   │
│              ┌───────────────────────────────┐                  │
│              │  lightmap 交叉淡入 · 0.8 秒    │                  │
│              │  = 4 套 lightmap 之间的混合     │                  │
│              │    这是一次离散的技术操作，      │                  │
│              │    发生在过渡窗中点，此时       │                  │
│              │    两幅 lightmap 的视觉差最小   │                  │
│              └───────────────────────────────┘                  │
└─────────────────────────────────────────────────────────────────┘
```

**为什么这样安排**：

1. **0.8s 是"不硬切"的最低要求**（RUL-1 明文）。它足够慢，能被读成"光在变"而非"画面闪了一下"（符合 UX 原则 5 静默优先：无 < 0.1s 的瞬时反馈）。
2. **45 游戏分钟是"感知"的窗口**。如果 lightmap 在 0.8s 内切完而主光不去配合，玩家会看到"影子瞬间跳一格"。**主光的连续插值把这一次离散切换掩盖掉。**
3. **在中点切换**是因为此时两幅 lightmap 所代表的光照状态差异最小（过渡窗两端分别是前后两个 slot 的"纯态"）。

**边界情况**：若玩家**恰好在过渡窗中点进入游戏**（存档的 `timeOfDayGameMin` 落在中点 ±0.5 分钟内），**不播放 0.8s 淡入**，直接呈现正确的混合态。理由：进入游戏就看到一次淡入，会被读成"加载完成动画"。

#### 3.4.3 slot 与昼夜节律表的关系（重要接口澄清）

> ⚠️ **前半段 GDD 有两套不同的时间分档，程序不得复用同一枚举**（已列入 §9 修订建议 R-3）。

| 表 | 档数 | 用途 | 是否随季节变化 |
|---|---|---|---|
| `timeSlot`（本系统） | **4**（晨/午/昏/夜） | **lightmap 索引 + 主光锚点** | ✅ **会**（昼长变化，见 §3.5.2） |
| `circadianBand`（系统 1 表 3.3.3-C） | **5**（深夜/晨/午/昏/夜） | **猫的行为节律权重** | ❌ 不会（固定钟点） |

**为什么两套都要存在**：

- `timeSlot` 是**光学**概念——它由太阳的方位决定，会随季节/纬度漂移。
- `circadianBand` 是**生物**概念——猫的作息锚定的是"一天中的第几个小时"，它对季节的反应是**行为层面的**（冬天猫睡更多），不是"重新定义早晨"层面的。

> 若复用同一枚举，冬季的 `slot_morning` 从 05:00 变成 06:20 后，猫的晨间进食高峰也会跟着漂移——**这是错的**。猫的晨间高峰是它的生物钟，不是太阳的。

### 3.5 核心机制详述 · 季节

#### 3.5.1 几季，每季改变什么（RUL-1 约束内）

**4 季**。每季只能改变以下 5 类（**全部不含 lightmap**）：

| # | 类别 | 是否走 lightmap | 具体内容 |
|---|---|---|---|
| **①** | **主光色温 / 强度** | ❌ 否 | 季节色温偏移（对接美术 §2.4「室内副色偏移」） |
| **②** | **全屏 LUT** | ❌ 否 | 季节色调（春微绿 / 夏高明度 / 秋暖 / 冬低饱和冷调） |
| **③** | **窗外景物** | ❌ 否 | 4 套树模型（美术 §5.3 已预算 4 套 C 档树） |
| **④** | **少量可换道具** | ❌ 否 | 花瓶里的花 / 电扇 / 玻璃杯冷凝水珠 / 落叶 / 围巾厚毯 / 毛毯暖炉 / 窗玻璃水雾（美术 §2.4 已列） |
| **⑤** | **⭐ 昼长 → slot 边界** | ❌ 否 | **只改变 4 个 slot 的时刻边界，不改变 lightmap 内容**（见 §3.5.2） |

> ⭐ **第 ⑤ 类是季节最有玩法价值的影响，且成本为零。**
> 冬天下午 5:40 天就黑了，夏天晚上 8 点还有光——**这是玩家能真切感知的季节差异，而且它不需要任何新资产。**

#### 3.5.2 昼长与 slot 边界（季节的玩法核心）

```
slot 边界 = f(season)：
    夜→晨 = 日出 − 0:40        （黎明前，窗外开始亮）
    晨→午 = 日出 + 0.42 × 昼长
    午→昏 = 日出 + 0.72 × 昼长
    昏→夜 = 日落 + 0:40        （入夜，室内灯亮起）
    夜→晨 = 同上（循环）

    ⚙ 系数 0.42 / 0.72 可调，判据是"晨→午 应稳定落在 11:00 前后"
```

| 季节 | 日出 | 日落 | 昼长 | 夜→晨 | 晨→午 | 午→昏 | 昏→夜 | **夜档时长** |
|---|---|---|---|---|---|---|---|---|
| **春** | 05:40 | 18:50 | 13:10 | 05:00 | 11:12 | 15:09 | 19:30 | 09:30 |
| **夏** | 04:50 | 19:30 | 14:40 | 04:10 | 11:00 | 15:24 | 20:10 | **08:00** |
| **秋** | 06:10 | 17:50 | 11:40 | 05:30 | 11:04 | 14:34 | 18:30 | 11:00 |
| **冬** | 07:00 | 17:00 | 10:00 | 06:20 | 11:12 | 14:12 | 17:40 | **12:40** |
| **MVP 基线**<br>（春末初夏） | 05:20 | 19:00 | 13:40 | 04:40 | 11:05 | 15:10 | 19:40 | 09:00 |

**三条性质**（这是我选这组系数的原因）：

1. **晨→午 在四季都稳定在 11:00–11:12** —— 上午的节奏是恒定的。**只有早晚在变，而"早晚在变"正是人类感知季节的方式。**
2. **午→昏 从冬 14:12 到夏 15:24**（差 1h12m）—— 下午的长短是季节最明显的体感。
3. **昏→夜 从冬 17:40 到夏 20:10**（差 2h30m）—— **黄昏（截图黄金档）在夏天比冬天长 1h18m。**

**玩法后果**：

| 后果 | 说明 |
|---|---|
| **冬天的截图窗口更窄** | 昏档冬季 14:12–17:40（3h28m）vs 夏季 15:24–20:10（4h46m）。**冬天的黄昏更珍贵** |
| **冬天的夜行为更多** | 夜档 12h40m vs 夏季 8h00m，猫的夜行为占比上升 |
| **夏天的晨光更早** | 晨档 04:10 起，早起的玩家能看到晨光（锚点 01） |
| **室内灯时长** | 冬 17:40 亮 / 夏 20:10 亮 —— 差 2.5 小时，玩家会注意到"灯亮得早了" |

|---|---|---|---|
| 春 | ×1.2 | ×1.0 | |
| 夏 | ×1.6 | ×0.9 | 夏季雷雨多 |
| 秋 | ×1.0 | ×1.1 | |
| 冬 | ×0.5 | **×1.5** | 冬季少雨多阴 |

#### 3.6.3 ⭐ 天气的玩法影响（Task 明确要求：不只是视觉）

| 天气 | 猫的行为影响 | 玩家的机会 |
|---|---|---|
| **晴** | 基准。`sunExposure` 高的锚点 `Light(a,t)` 项生效（×1.45 上限） | 截图黄金档（晨/昏） |
| **阴** | `sunExposure` 全域压到 ≤0.3 → **晒太阳锚点失效**；<br>**`EXPLORE` +15%** ⚙（光不刺眼，胆小猫敢出来）；<br>`ENE` 恢复 +3% ⚙ | **柔和无影光适合拍细节**（爪垫、胡须、猫毛） |
| **雨** | **`WATCH_WINDOW` ×1.8** ⚙（猫会看雨）<br>`PLAY` −20% ⚙（没精神）<br>**`SEC` +0.5 / 游戏小时** ⚙（雨声是白噪音，猫更安心——这是真实的）<br>`SLEEP_DEEP` +10% ⚙ | **⭐ 锚点 05「雨天的窗」** —— 概念文档五大视觉锚点之一 |

> 📌 **`SEC` +0.5/游戏小时（雨）是本系统最反直觉也最有价值的一条**：
> 它把"天气"从**环境**变成了**恩惠**。玩家会开始期待雨天——"雨天它会更放松"。
> 而它完全符合真实养猫经验（很多猫在雨天睡得特别沉）。

#### 3.6.4 天气与「今日不同」的耦合

雨天时，「今日不同」的槽位池**偏向窗内**（S02 窗玻璃水痕、S11 地垫湿了），**排除 S03 窗外**（看不清）。
这保证了雨天的内容是可读的，而不是一堆看不见的远处细节。

### 3.7 ⭐ lightmap 套数守恒证明（Task 强制要求）

#### 3.7.1 变量分解

> **命题**：季节 × 天气 **不增加** lightmap 套数。

**证明思路**：把所有视觉变量分解到它所属的渲染层级，看 lightmap 层被哪些变量索引。

| 视觉变量 | 取值 | 落在哪个层级 | **是否索引 lightmap** |
|---|---|---|---|
| 时段 slot | 晨 / 午 / 昏 / 夜 | **lightmap** | ✅ **是** |
| 季节 | 春 / 夏 / 秋 / 冬 | 主光（色温/强度）、LUT、窗外模型、可换道具、**slot 边界时刻** | ❌ 否 |
| 天气 | 晴 / 阴 / 雨 | 主光（强度/色温）、LUT、窗材质 | ❌ 否 |
| 室内灯开关 | 开 / 关 | 实时点光 | ❌ 否 |
| 玩家摆放家具 | 连续 | 实时遮挡（若技术允许）／**否则不影响** | ❌ 否 |
| 猫的位置 | 连续 | 实时 | ❌ 否 |

**结论**：

```
lightmap 索引 = f(slot)
             = f(单一变量，基数 4)

∴ |lightmap| = 4，与 |season| × |weather| = 4 × 3 = 12 无关。

若 RUL-1 ② 的降级路径触发：|lightmap| = 2（昼/夜），同样与季节/天气无关。
```

#### 3.7.2 画面构成模型（策划层，不涉实现）

```
最终画面
  = lightmap(slot)                          ← 基数 4（或降级后 2）
  × 主光(direction: slot, color/intensity: slot × season × weather)
  × LUT(season × weather)
  + 室内灯(实时，玩家可控)
  + 窗外景物(season)
  + 可换道具(season)
```

#### 3.7.3 🚨 硬闸门：新增任何效果的检查表

> **任何人在任何阶段提出一个新的季节/天气/节日效果，必须先过这个闸门。**

| # | 检查项 | 若"是" |
|---|---|---|
| 1 | 它是否改变了**间接光的分布**（即：光从哪个方向来、打到哪里、反弹多少）？ | 🔴 **必须重新评审**。它很可能需要新 lightmap |
| 2 | 它是否改变了**太阳相对窗户的方位**？ | 🔴 同上 |
| 3 | 它只改变**主光的颜色 / 强度 / 方向插值**？ | 🟢 放行 |
| 4 | 它只改变**全屏色调**（LUT）？ | 🟢 放行 |
| 5 | 它只改变**窗外景物 / 可换道具 / 窗材质**？ | 🟢 放行 |

#### 3.7.4 闸门的一次实际应用：**雪**（主动范围决策）

| 效果 | 过闸门的结果 | 裁决 |
|---|---|---|
| 雪 · 窗外飘雪 | 检查 5 → 🟢 放行 | ✅ Standard 可做 |
| 雪 · **窗台与地面的积雪** | 检查 1 → 🔴 **积雪是强反照率表面，会显著改变室内的间接光反弹** | ❌ **记入 Epic，不进 Standard** |
| 雪 · 窗玻璃水雾 | 检查 5 → 🟢 放行（与雨共用窗材质） | ✅ Standard 可做 |

> **这是一个主动的、有依据的范围决策，不是拍脑袋砍功能。**
> 若将来有人提出"加雪景吧"，本文档给出的回答是：**可以做飘雪与窗雾，不能做地面积雪**——因为后者会打破 RUL-1，代价是一整套 lightmap。

| **E-L1** | **玩家恰好在过渡窗中点进入游戏** | **不播放 0.8s 淡入**，直接呈现正确的混合态（§3.4.2）。进入时看到一次淡入会被读成"加载动画" |
| **E-L2** | **×12 加速下，一次会话跨过整个过渡窗**（45 游戏分钟 ÷ 12 = 225 真实秒） | 正常。玩家会在 3.75 分钟内看到一次完整的时段过渡——**这是特性不是 bug**（前半段 GDD E3-6 已定）。<br>**但**：若玩家在此期间的相机是静止的且未看向窗，他会错过。**不补偿、不提示** |
| **E-L3** | **季节过渡第 4 天，玩家整天在线**（窗外树无法 swap） | 延迟到该玩家下次进入时执行。**绝不在玩家眼前换树。**<br>若玩家连续 7 天不关标签页 → 在第 7 天过渡结束时强制执行（此时已是过渡期末尾，视觉差异最小） |
| **E-L4** | **玩家在过渡期内改系统时间跨季节** | 离线结算 clamp 到 30 天（前半段 GDD §5.7④）。季节按 `saveDate` 推算而非连续累积，改时间无法"快进"到某个季节获得额外内容 |
| **E-L5** | **雨天连续 10 天（马尔可夫链的极端尾巴）** | 允许。但**第 6 天起，雨的转移概率每日 ×0.85 递减** ⚙，确保不出现"永远在下雨"。<br>理由：连续阴雨会让画面长期灰暗，且 `SEC` 持续上升会让猫变得"过于放松"，抹平性格差异 |
| **E-L6** | **南半球玩家的季节是反的** | 按时区与地区信息推断；推断失败默认北半球；**设置项提供手动翻转**（Q-2 / B-9） |
| **E-L7** | **玩家手动把「季节」设为「固定春末」，但已玩到秋天** | 立即生效，7 天过渡回春末。**不回滚任何已生成的日记或痕迹**——那些是历史，历史不因设置改变 |

## 4. 系统 3 · 成长与解锁系统（P1 · 无 FOMO 红线最高风险区）

### 4.1 支柱闸门校验

**服务哪根设计支柱**：**支柱一 · 同住感（主）** + **支柱四 · 家的诗意（次）**。

- **支柱一**：关系的深化是"同住"的必然结果。室友相处三个月，关系会变——这是支柱一的长线表达。
- **支柱四**：家的历史（痕迹、锚点发现、相册）是"诗意"的累积。
- **🚨 刻意不服务支柱二（时间）与支柱三（猫性）**：
  - **不服务支柱二**：成长**不按时间表推进**。没有"玩 30 天解锁 X"。成长由 `AFF` 驱动，而 `AFF` 由**玩家做了什么**驱动，不是由**过了多久**驱动。
  - **不服务支柱三**：**性格是基因锁定的**（前半段 GDD §3.3.1 ②：`IND` 不可被玩家改变）。成长改变的是**关系的表达**，不是**它是谁**。

> **这个"刻意不服务"是本系统最重要的设计声明。**
> 成长系统最容易犯的错，就是把它做成"时间表"——而时间表就是进度条，进度条就是 FOMO。

### 4.2 系统概述

**一句话定义**：关系的深化如何改变猫的行为曲目、猫如何逐步发现屋里的位置、屋里如何逐步积累历史——**并且这一切都不被宣告、不被计数、不被奖励。**

**核心裁决 G-1**：

> 🚨 **本系统不解锁"内容"，解锁"可能性"。**
> 没有任何物件有"解锁条件"字段。物件只有 `{id, spawnSource, spawnCondition}`——**它没有 `unlockRequirement`**。
> **项目的数据模型里不允许出现"解锁"这个概念。**

### 4.3 设计目标（可验证）

| # | 目标 | 验证方式 | 状态 |
|---|---|---|---|
| **G-G1** | **关系成长不可速成** | 不存在任何输入序列能让 `AFF` 在 90 天内达到 100 | ✅ 沙盘已验证（前半段 §6.4：最快 ~180 天） |
| **G-G2** | **成长永不回退** | 即使 `AFF` 因暖机模型下降，**已获得的行为曲目永不丢失** | ✅ 设计保证（裁决 G-2） |
| **G-G3** | **成长不被宣告** | 阶段切换无提示、无动画、无音效、无日记卡片 | ✅ 设计保证（裁决 G-3） |
| **G-G4** | **无任何进度可见** | 玩家在任何时候都看不到"x/y"、"百分之多少"、"还剩多少" | ✅ 设计保证（系统 4 UI-R5） |
| **G-G5** | **长线不空窗** | D30–D90 之间每 ≤20 天有一次可感知的行为变化 | ⚠️ 需新增亚档（见 §4.4.2 与风险 B-5） |
| **G-G6** | **成长不是唯一回访理由** | 每周 1 次的低频玩家在 D365 也能进入"信任"（有进展，不封顶） | ✅ 沙盘已验证（前半段 §6.4：41） |

### 4.4 核心机制详述

#### 4.4.1 关系阶段 → 行为曲目（唯一的"解锁"轴）

> 阶段定义沿用前半段 GDD §3.3.1 ①（陌生 0–20 / 习惯 20–40 / 信任 40–60 / 亲近 60–80 / 羁绊 80–100）。

| 阶段 | AFF | **新增的行为曲目（累积，不回退）** | 玩家感知 |
|---|---|---|---|
| **陌生** | 0–20 | 无。会躲 | "它怕我" |
| **习惯** | 20–40 | 允许同处一室；偶尔看你；`Ear-ack` 概率提升 | "它不躲了" |
| **信任** | 40–60 | 在你附近睡；**慢眨**；允许梳理；`Headbonk` 极小概率 | "它愿意靠近了" |
| **亲近** | 60–80 | **主动蹭你（Headbonk）**；叫你；睡在有你气味的地方 | "它主动来找我了" |
| **羁绊** | 80–100 | 跟着你移动；**踩你正在看的东西**；睡在你的位置 | "它离不开我了" |

**裁决 G-2 · 成长永不回退**：

```
即使 AFF 因暖机模型下降（warmth < 15 时 AFF −0.25/日），
已获得的行为曲目永不丢失。

理由：回退会让玩家感到"我失去了什么"——那是惩罚，直接违反 U4 与情绪禁区。
     一只学会了慢眨的猫，不会因为你有两周没来就"忘记怎么慢眨"。

实现：行为曲目存为 cat.behaviorRepertoire: string[]，单调递增。
     阶段判定用 AFF 实时计算，但曲目用集合取并集。
```

**裁决 G-3 · 阶段切换无任何宣告**：

```
阶段切换时：
  ✗ 无提示文字
  ✗ 无动画
  ✗ 无音效
  ✗ 无日记卡片
  ✗ 无"新行为已解锁"的任何形式

玩家发现的方式只有一个：他看见猫做了一件以前没做过的事。
```

> **唯一需要讨论的例外**：美术圣经 §9.3 列了「慢眨信任提示」这一可关闭项，默认开。
> **我的建议**：把它从**宣告性**改为**解释性**——
> - ❌ 宣告性："你的猫学会了慢眨！"（预告/宣告，违反 G-3）
> - ✅ 解释性：在玩家**已经观察到慢眨之后**，用一个极轻的场景内语言告诉他"猫慢眨 = 它信任你"（解释一个他已经看见的现象）
>
> **这是待拍板项 Q-4，需与林绘澄确认（ART-8）。**

#### 4.4.2 ⭐ 阶段内亚档（解决 G-G5 的 D30–D90 空窗）

> **问题**：沙盘显示每日玩家 D30 的 AFF 是 49–54（信任），D60 是 64–69（亲近）。
> **中间 30 天里，阶段没变，玩家感受不到任何变化。** 这是 M-5 的长线版本。

**解法**：每个阶段（20 点跨度）内分 **3 个亚档**，每亚档约 6.7 点。

```
亚档 = floor((AFF − stageBase) / 6.67)   // 0 / 1 / 2
```

**亚档不改变曲目，只调整行为权重**：

| 阶段 | 亚档 0 | 亚档 1 | 亚档 2 |
|---|---|---|---|
| **信任** 40–60 | 在你 1.5m 内睡 | 在你 1.0m 内睡；慢眨频率 ×1 | 在你 0.6m 内睡；慢眨频率 ×2；`SEEK_ATTENTION` ×1.3 |
| **亲近** 60–80 | Headbonk 每月 1–2 次 | Headbonk 每周 1–2 次；开始"等你" | Headbonk 每天 0–1 次；睡在有你气味的地方成为默认偏好 |
| **羁绊** 80–100 | 跟到隔壁视野 | 跟到视野边缘 | 踩你正在看的东西 |

> **为什么用"权重微调"而不是"新增行为"**：
> 新增行为会让阶段变得像"等级"，玩家会开始期待下一个等级。
> **权重微调制造的是"它最近好像更黏我了"这种模糊的、连续的、说不清的感觉——而这正是真实关系的样子。**

#### 4.4.3 锚点发现（Anchor Discovery）

| 项 | 规格 |
|---|---|
| 触发 | 猫首次抵达某锚点（`visitCount` 从 0 → 1） |
| 数值 | `CUR +10`（一次性，既有规则） |
| 玩家感知 | **无**。不提示、不计数、不显示 "3/14" |
| 价值 | ① 日记的地点锚池变宽 ② 猫的行为分布变宽 ③ 玩家的心智模型变复杂 |
| **未发现锚点的合法性** | **是特性不是 bug**。一只 `SEC` 太低的猫**永远不敢上冰箱顶**——那个锚点在它的存档里永远是 `discovered: false`。**这就是猫性** |
| 初始已发现 | 3 个（地毯中央、沙发一角、窗台）——玩家第一次打开游戏时猫就已经认识这三个地方 |
| 隐藏锚点（UX §4.1 P5 层） | 书架第二层、冰箱顶、茶几下、洗衣机顶、柜后 —— 需 `CUR_eff` 与 `SEC` 双高才可能被发现 |

#### 4.4.4 物件"发生"的三条来源（**没有一条叫"解锁"**）

| # | 来源 | 举例 | 是否与"玩了多少天"挂钩 |
|---|---|---|---|
| **①** | **「今日不同」系统**（系统 0） | 落叶、纸团、翻开的书 | ❌ 否（由 `dailySeed` 决定） |
| **②** | **玩家行为引出** | 把书翻开 → 书签出现；把抱枕放沙发上 → 抱枕上的猫毛 | ❌ 否（由玩家行为决定） |
| **③** | **猫的行为引出** | 猫第一次跳上冰箱顶 → 那里出现爪印；猫在某处睡够 60 次 → 压痕升档 | ❌ 否（由猫的行为决定） |

> 🚨 **三条来源里没有一条是"玩满 X 天"。**
> 这是本系统与"每日登录奖励"的分界线——**内容的出现由世界与角色驱动，不由日历驱动。**

### 4.7 边缘情况（6 条 · 硬性要求）

| # | 边缘情况 | 处理规则 |
|---|---|---|
| **E-G1** | **猫永远发现不了某个锚点（SEC 太低）** | **特性，不是 bug。** 该锚点在存档里永远 `discovered: false`。<br>**不补偿、不降低门槛、不提示。** 一只不敢上冰箱顶的猫，就是不敢上冰箱顶 |
| **E-G2** | **玩家移走家具，导致已发现锚点失效** | 锚点标记 `dormant: true`，但**保留在 `discoveredAnchors` 中**（它记得那个位置）。<br>家具放回后，`dormant` 解除，`visitCount` 保留 |
| **E-G3** | **AFF 因暖机模型下降，阶段回退** | **行为曲目不回退**（G-2）。<br>阶段判定本身会回退（它是 `f(AFF)`），但**曲目集合取并集**。<br>玩家可能观察到"它最近没那么黏了"（这是真实的），但**它不会忘记怎么慢眨** |

## 5. 系统 4 · UI / HUD 系统（P2 · 与 UX 规格严格一致）

### 5.1 支柱闸门校验

**服务哪根设计支柱**：**不以"提供什么"服务任何支柱，以"不提供什么"服务支柱一与支柱四。**

- **支柱一的守门人**：UI 每多一个常驻元素，"这是一个家"的信念就弱一分。**UI 系统的 KPI 是退场。**
- **支柱四的守门人**："随时来、随时走"要求零摩擦进入与退出。任何挽留、确认、总结都是对它的敌意（UX 原则 4）。
- **不服务支柱二、支柱三**：时间与猫性**全部**编码在场景内，UI 不参与。

> **本系统的验收标准是回忆性的**：
> 玩家关掉游戏后回想，**说不出任何 UI 元素的名字**。他记得的是"墙上的钟""沙发的坑""它尾巴的方向"（UX §1 原则 1）。

### 5.2 系统概述

**一句话定义**：把 UX 规格（PH4-DESIGN-003）的五条原则翻译成**可实现的状态、参数与数据结构**，并给出 UI 元素的增删改规则。

**本文档与 UX 规格的分工**：

| UX 规格 | 本文档 |
|---|---|
| 说明**为什么**（原则、论证、体验目标） | 说明**是什么**（元素清单、状态机、参数、规则） |
| 面向设计与评审 | 面向实现与验收 |

#### 5.4.1 ⭐ UI 增删改规则（硬约束）

```

        count(elements where persistent == true) == 1
        违反此条的任何提交不得合入。

UI-R2 · 新增常驻元素必须指定被移除者
        新增任何 persistent 元素时，必须同时指定一个既有的 persistent 元素被移除，

        判定标准：它是否有世界坐标、能否被相机绕行 / 被其他物件遮挡？
```

## 6. 系统 5 · 元系统（存档 / 截图 / 设置 / 多标签页）（P2）

### 6.1 支柱闸门校验

**服务哪根设计支柱**：**支柱四 · 低摩擦陪伴（主）**，同时是**全部四根支柱的信任基础**。

- **支柱四**："随时来、随时走、随时再来"的前提是——**随时被打断不会丢东西**。RUL-8 把存档安全定为零容忍项，正是因为它一旦失守，玩家投入的唯一载体就没了。
- **信任基础**：一个养了 60 天的猫因为切后台丢失，**比任何画面缺陷都更致命，且不可挽回**（RUL-8 原文）。
- **不服务支柱一、二、三**：元系统不产生任何玩法内容。

### 6.2 系统概述

**一句话定义**：存档的持久化与安全、截图的存储与导出、设置项的完整清单、多标签页的会话仲裁。

**与前半段 GDD §5.5–§5.7 的分工**：前半段定义了**存档的字段结构与写入时机**；本节补充**容量管理、版本迁移、导出/导入、以及截图与设置**。**不重复前半段。**

#### 6.4.1 容量预算

| 数据 | 估算 | 上限策略 |

| 存档主体（不含截图） | ~8 KB | — |

#### 6.4.2 版本迁移链（RUL-8 相关）

```
迁移原则（前半段 E3-8 已定，本节补充实施细则）：

  1. 迁移函数必须单调递增：migrate_v2_to_v3, v3_to_v4 ...
  2. 迁移函数只增字段，不删字段。删除留到"字段被废弃满 2 个版本"后
  3. 迁移前先做一次完整性校验；校验失败的存档**不迁移**，保留原样并走异常恢复
  4. 迁移成功后，旧版本存档保留一个备份槽（slotArchive），保留 7 天
  5. 迁移失败 → 进入异常恢复路径，**绝不静默重置**

★ 硬规则：迁移函数不得修改任何"玩家的情感资产"：
     cat.name / cat.genes / discoveredAnchors / repertoire / 相册截图
     这五项在任何迁移中都必须逐字节保留。
```

| 项 | 规格 |

| 触发 | 设置页 → 导出存档码（U-11 场景的常驻入口） |

### 6.7 核心机制详述 · 多标签页会话仲裁

> 前半段 E2-7 已定"第二个标签页进入只读模式"。本节补充**锁的生命周期**（前半段未定义）。

```
锁结构（写入 IndexedDB，不用 localStorage）：
  sessionLock = { tabId, acquiredAt, heartbeatAt }

获取：进入时，若无锁 或 锁的 heartbeatAt 距今 > 30s → 抢占
心跳：持有者每 10s 更新 heartbeatAt
释放：visibilitychange→hidden / pagehide / 正常卸载
超时：30s 无心跳 → 视为已释放（覆盖崩溃场景）

只读模式（第二个及之后的标签页）：
  ✓ 可看、可转视角、可截图
  ✗ 不可互动、不可摆放、不可改设置
  ✗ 不跑 tick（不模拟猫）
  提示：极轻，场景内语言（一次性便签）

恢复：
  持有者释放后，只读页在下次心跳检测（≤ 10s）内
  → 重新读档并重渲染
  → ★ 不重载页面（见下）
  → 提示"它还在"（极轻，可关闭）
```

> ⚠️ **对前半段 E3-7 的修订建议**：
> E3-7 写的是"提示'它长大了'，重新加载"。
> **我建议改为「静默重新读档并重渲染，不重载页面」**。理由有二：
> ① B 页在整个只读期间**未做任何模拟**，无状态可失，重载是纯粹的浪费；
> ② "它长大了"是**宣告性**的——它替玩家判断了"这是一个值得注意的变化"，违反系统 3 的裁决 G-3。
> 已列入 §9 修订建议 **R-5**。
