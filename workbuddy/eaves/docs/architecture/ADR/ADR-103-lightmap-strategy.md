## 1. 背景

### 1.1 RUL-1 的原文

> **采纳方案 B · 四时段淡入（晨 / 午 / 昏 / 夜）**
> ① 4 套 lightmap，时段间 **0.8s 交叉淡入淡出，禁止硬切**
> ② 程基岩在 Phase 3 核算 4 套 2048² lightmap 在中端移动端的实际显存占用，**若超过预算 60% 则降为 2 套（昼 / 夜）+ Color Grading LUT 补足中间态**
> ③ 季节与天气**一律不走 lightmap**，只允许改实时主光色温/强度 + 全屏 LUT
>
> 理由：支柱二「时间的双层刻度」的实质内容是"**光会移动**"。方案 A（1 套）让阴影永久静止，等于把支柱抽空。

### 1.2 需要本 ADR 解决的三件事

1. **4 套 lightmap 的显存核算** → 是否触发降级？（RUL-1 ② 强制要求给出具体数字）
2. **0.8 s 交叉淡入怎么实现** → Three.js 内置材质只支持单一 `lightMap` sampler
3. **季节/天气如何在零 lightmap 成本下表达**（RUL-1 ③）

### 1.3 一处文档冲突（已澄清）

GDD 前半段 §5.4.4 写「降级为方案 A（**1 套** + LUT）」，与 RUL-1 的「**2 套**（昼/夜）」互斥。GDD PH2b §9 的 **R-1** 已识别为硬冲突。

> ✅ **本 ADR 按 RUL-1 执行：降级路径 = 2 套（昼/夜）+ LUT。1 套不可接受**（理由见 §5.2）。

## 2. 决策

### 2.1 总览

```
最终画面
  = lightmap(slot)                                    ← 基数 4（降级后 2），索引只接受 slot 一个参数
  × 主光(direction: slot 过渡窗插值;
         color/intensity: slot × season × weather)
  × 色彩分级(season × weather)                        ← 参数化，12 组常量，384 B
  + 室内灯(实时 Point/Spot，玩家可控)
  + 窗外景物(season，4 套 C 档树)
  + 可换道具(season)
```

### 2.2 lightmap 资产规格

| 项 | 规格 |
|---|---|
| 文件 | `lm_morning.ktx2` / `lm_noon.ktx2` / `lm_dusk.ktx2` / `lm_night.ktx2` |
| 分辨率 | **2048²（恒定）** |
| 编码 | **UASTC LDR 4×4 + KTX2 zstd 超压缩**；Android 兼容档回退 ETC1S |
| 单套显存 | **4.0 MiB**（UASTC→ASTC 4×4 / ETC2 EAC，8 bpp）｜ Android ETC1S 路径 **2.0 MiB** |
| 单套下载 | **0.6–1.4 MB**（zstd 后约 2.0–2.8 bpp） |
| **mipmap** | **关闭**（正交 3 档 zoom，采样频率恒定；省 33% 显存） |
| UV | **UV1**（第二套 UV），全场景唯一展开，不重叠 |

### 2.3 驻留策略（关键优化）

| 状态 | 驻留套数 | 显存（ASTC） |
|---|---|---|
| **稳态** | 2 套（当前 slot + 下一时段 slot） | **8.0 MiB** |
| crossfade 瞬态（0.8 s） | 3 套（+ 目标） | 12.0 MiB |
| 异常路径（跨多时段进入） | 4 套 | 16.0 MiB（之后回落 2 套） |

> crossfade 只需要"当前 + 目标"两套在场。第三套（下一时段）是预取，第四套按需加载。
> 异常路径（玩家改系统时间跨多时段）会有一次 ~30–80 ms 的贴图上传 hitch，但此时本来就在离线结算遮罩内。

### 2.4 交叉淡入的驱动（落实 GDD PH2b §3.4.2）

```
过渡窗（Transition Window）= 45 游戏分钟
  ├─ 边界 −22.5 游戏分钟：主光开始插值
  ├─ 边界（进度 0.5）：★ lightmap 0.8 s crossfade 在此触发
  └─ 边界 +22.5 游戏分钟：主光插值结束
```

| 项 | 值 | 说明 |
|---|---|---|
| 过渡窗 | 45 游戏分钟 | ×12 下 = 225 真实秒 = 3.75 分钟 |
| **crossfade 时长** | **0.8 s（真实秒）** | **RUL-1 明文，不可调**。占过渡窗的 0.36% |
| 插值曲线 | `smoothstep(0, 1, t / 0.8)` | 不是线性，避免起止的"速度突变"被察觉 |
| 触发条件 | 过渡进度跨过 0.5 **且** `crossfadeDone == false` | 保证每次过渡只播一次 |
| 完成后 | `slot = to`，`lightMapA ← lightMapB`，`lightMapMix ← 0` | |

**边界情况 E-L1**：玩家恰好在中点 ±0.5 游戏分钟进入 → **不播放淡入**，直接设 `lightMapMix` 为按进度计算的正确静态混合值。理由：进入就看到一次淡入会被读成"加载完成动画"。

### 2.5 交叉淡入的 shader 实现（**核心技术决策**）

Three.js 的 `MeshStandardMaterial.lightMap` 只支持**单一 sampler**。两条路：

| 方案 | Draw call 影响 | 判定 |
|---|---|---|
| 双 mesh 叠加 alpha blend | A 档 5 件 + B/C batch 5 = **+10~12**；且 alpha blend 在 fill rate 上是一整遍额外 overdraw | ❌ **否决** |
| **`onBeforeCompile` 注入双 sampler** | **0** | ✅ **采纳** |

```glsl
// 注入 uniform
uniform sampler2D lightMapA;
uniform sampler2D lightMapB;
uniform float     lightMapMix;    // 0 → A, 1 → B

// 替换 <lights_fragment_maps> 中的 lightmap 采样段
vec4 lmSample = mix(texture2D(lightMapA, vLightMapUv),
                    texture2D(lightMapB, vLightMapUv),
                    lightMapMix);
vec3 lightMapIrradiance = lmSample.rgb * lightMapIntensity;
```

**四个必须注意的实现细节**

| # | 细节 | 为什么 |
|---|---|---|
| **C-1** | **只编译 1 个 program 变体**（A/B sampler 恒在 shader 中） | crossfade 只改 uniform → **零 shader 重编译**。直接消解风险 T-4 |
| **C-2** | **稳态下 `lightMapB` 指向 1×1 白色纹理，`lightMapMix = 0`** | 稳态只有 1 次有效采样 + 1 次 1×1 采样（近乎免费）。**稳态零额外成本** |
| **C-3** | 必须定义 `material.customProgramCacheKey` | 否则 Three.js 可能与其他 standard material 共享 program，导致 uniform 丢失 |
| **C-4** | 注入锚定 `<lights_fragment_maps>` chunk 名 | r→r 升级时若改名会**静默失效**。必须 Spike 验证 + 升级回归（风险 T-5） |

**成本**

| 状态 | 中端移动 1600×900 | 桌面 2560×1440 |
|---|---|---|
| 稳态（B = 1×1） | **≈ 0 ms** | ≈ 0 ms |
| crossfade 进行中（0.8 s 内） | **+0.3–0.6 ms/帧** | +0.8–1.5 ms/帧 |

### 2.6 季节与天气（零 lightmap 成本）

| 变量 | 通道 | 资产成本 |
|---|---|---|
| 季节色温 | 主光 `color` 偏移（春 ±0 / 夏 +200K / 秋 −100K / 冬 −300K） | 0 |
| 季节色调 | 色彩分级参数（4 组） | 0 |
| 季节窗外 | 4 套 C 档树（各 ~1.5k tris, ~80 KB glb） | 320 KB 总计，按需加载 |
| 季节可换道具 | ~12 件小道具（各 ≤800 tris） | ~200 KB |
| **季节昼长** | **改变 4 个 slot 的时刻边界**（查表 + 7 天线性插值） | **0** |
| 天气强度/色温 | 主光 `intensity` ×(1.00/0.55/0.35)，`colorTemp` +(0/+300/+200 K) | 0 |
| 天气投影 | `weather === 'sunny'` 才开 shadow map | 阴/雨天**反而省 0.5–1.0 ms** |
| 雨天窗户 | 玻璃水珠 shader（美术 §5.3 已预算 2 人日） | 已计入 |
| **色彩分级总组数** | 4 季 × 3 天气 = **12 组常量 × 8 float** | **384 B** |

**架构强制**：`LightmapManager.setSlot(slot: TimeSlot)` **只接受一个参数**。任何试图传入 `season` 或 `weather` 的改动都会被 TypeScript 拒绝。这是 GDD PH2b A-L1（"lightmap 套数恒 = 4"）的代码级保证。

## 3. 备选方案

### 3.1 备选 A · 1 套 lightmap（Phase 1 我的原建议 / 美术圣经 §5.4.2 的隐含方向）

| 维度 | 评价 |
|---|---|
| 优点 | 显存 4.0 MiB（4.2%）；下载 1 套 |
| 缺点 | **阴影永久静止**。RUL-1 原文：「方案 A 让阴影永久静止，等于把支柱抽空」 |
| 判定 | ❌ **已被 RUL-1 否决**。我 Phase 1 的建议在此被裁决推翻，**本 ADR 服从裁决** |

### 3.2 备选 B · 48 套 lightmap（4 时段 × 4 季 × 3 天气，美术圣经原方案）

| 维度 | 评价 |
|---|---|
| 优点 | 每个组合都是精确烘焙 |
| 缺点 | 48 × 4.0 MiB = **192 MiB 显存**（中端红线 96 MiB 的 **200%**）；下载 ~50 MB |
| 判定 | ❌ **否决**。RUL-1 已裁 |

### 3.3 备选 C · 全实时 GI（无 lightmap）

| 维度 | 评价 |
|---|---|
| 优点 | 季节/天气/时段全部自动正确；无限套数 |
| 缺点 | WebGL2 移动端无实时 GI 方案；`LightProbe` + 手动打点的覆盖质量远不如烘焙；半兰伯特 + 环境探针的间接光质量会明显劣化 |
| 判定 | ❌ **否决**。RUL-1 已判"方案 C 在当前技术评估下不可行" |

### 3.4 备选 D · 2 套（昼/夜）+ LUT（RUL-1 的降级路径）

| 维度 | 评价 |
|---|---|
| 优点 | 显存 8.0 MiB（8.3%）；**保住昼夜的阴影差异** |
| 缺点 | 晨与昏共用昼套 → 晨/昏的间接光软阴影形状不再变化 |
| 判定 | ⏸ **保留为降级路径，不激活**（见 §4 核算与 §5） |

### 3.5 备选 E · lightmap crossfade 用两个 mesh 叠加

| 维度 | 评价 |
|---|---|
| 优点 | 无需 shader 注入，规避 T-5 风险 |
| 缺点 | **+10~12 draw call**（移动端从 28 → ~40）；alpha blend 一整遍额外 overdraw；每个受光物件都要复制一份几何 |
| 判定 | ❌ **否决**。draw call 与 fill rate 双重代价 |

### 3.6 备选 F · 用 `texture.array`（Texture2DArray）存 4 套，shader 内索引

| 维度 | 评价 |
|---|---|
| 优点 | 一次绑定，索引切换零成本；无需 A/B 双 sampler |
| 缺点 | **4 套必须同时驻留**（16.0 MiB 常驻，无驻留置换优化）；crossfade 需要 2 次 array 采样（成本与双 sampler 相同）；`KTX2Loader` 对 array 纹理支持需手工组装 |
| 判定 | ⏸ **备选**。若驻留置换的复杂度在实测中成为问题，可切换到此方案（代价：稳态显存从 8.0 涨到 16.0 MiB，仍在 16.7% 预算内） |

## 4. 🚨 显存核算（RUL-1 ② 的强制交付项）

### 4.1 降级判据的明确定义

> **降级判据** ＝（4 套 lightmap 全部常驻 GPU 时的显存占用）÷（中端移动**纹理内存工程红线**）> 60%

**中端移动纹理内存红线 = 96 MiB**（不是 Phase 1 写的 128 MiB）。修正理由：Phase 1 的 128 MiB 是"GPU 侧纹理分配理论上限"，**工程红线必须扣除 Render Target 占用**：

| Render Target（中端移动 1600×900） | 占用 |
|---|---|
| 主 framebuffer（RGBA8 + D24S8，7 B/px） | 9.61 MiB |
| Shadow map 1024² D32 | 4.00 MiB |
| 后处理 1/4 降采样 ping-pong × 2 | 0.69 MiB |
| 日记离屏 RT 512² RGBA8（常驻） | 1.00 MiB |
| SMAA / 边缘缓存 | 0.50 MiB |
| **RT 合计** | **15.80 MiB** |

→ 96 MiB（纹理）+ 15.8 MiB（RT）= 111.8 MiB GPU 侧总量，为驱动内部缓冲与 iOS 内存压力留 16 MiB 余量。
→ **红线 96 MiB，降级阈值 57.6 MiB。**

### 4.2 核算结果

| 编码路径 | 单套 | **4 套总显存** | 占 96 MiB | **是否触发降级** |
|---|---|---|---|---|
| **UASTC → ASTC 4×4（iOS 主路径）** | 4.0 MiB | **16.0 MiB** | **16.7%** | ❌ **否** |
| **UASTC → ETC2 EAC（Android 高质）** | 4.0 MiB | **16.0 MiB** | **16.7%** | ❌ **否** |
| **ETC1S → ETC1（Android 兼容路径）** | 2.0 MiB | **8.0 MiB** | **8.3%** | ❌ **否** |
| ⚠️ 未压缩 RGBA8（无 KTX2 支持回退） | 16.0 MiB | **64.0 MiB** | **66.7%** | ✅ **触发** |
| ⚠️ 4096² ASTC 4×4（若分辨率上探） | 16.0 MiB | **64.0 MiB** | **66.7%** | ✅ **触发** |
| ⚠️ 2048² RGBA8 + mipmap | 21.3 MiB | **85.3 MiB** | **88.9%** | ✅ **触发** |

### 4.3 完整纹理预算（中端移动）

| 项 | 显存 |
|---|---|
| 猫 albedo 1024² ASTC 4×4 | 1.33 MiB |
| 猫 normal 1024² ASTC 4×4 | 1.33 MiB |
| 猫 ORM/SSS mask 512² | 0.33 MiB |
| 环境 Atlas albedo 2048² ETC2 | 4.00 MiB |
| 环境 Atlas normal 2048² ASTC | 4.00 MiB |
| C 档 Atlas albedo 1024² | 1.33 MiB |
| **lightmap 稳态驻留 2 套** | **8.00 MiB** |
| lightmap crossfade 瞬态第 3 套 | 4.00 MiB |
| 3D LUT 32³ RGBA8 | 0.14 MiB |
| 窗外天空 512² equirect | 1.33 MiB |
| 痕迹/UI 图集 512² | 0.33 MiB |

### 4.4 ✅ 核算结论

> ## **不触发降级。按 RUL-1 主路径执行：4 套 2048² lightmap。**
>
> 占用 **16.0 MiB / 96 MiB = 16.7%**，距 60% 阈值（57.6 MiB）有 **3.6 倍余量**。
> 稳态实际只驻留 2 套（**8.0 MiB = 8.3%**），因为 crossfade 只需"当前 + 目标"两套在场。
>
> 以上为**架构核算值**。Phase 3 Spike 必须实测回填，偏差 > 20% 立项修订。

### 4.5 敏感性分析

| 触发条件 | 我的处置 |
|---|---|
| 设备不支持 KTX2 / ASTC / ETC2（2026 年 < 2%） | **回退路径强制** lightmap 降为 **2 套 + 1024² + RGB565** = 2 × 2.0 = **4.0 MiB**。分辨率与套数同时降，回退路径反而不触发降级 |
| 分辨率上探到 4096² | **架构硬约束拒绝**。需要改这条约束必须主理人重开 RUL-1 |
| mipmap 被误开（应关闭） | CI 断言 `lightmap.generateMipmaps === false` |
| 未来有人提"给每个季节加 1 套 lightmap" | **被 GDD PH2b §3.7.3 硬闸门拦截**（检查项 1 → 🔴 必须重新评审）+ 架构侧 `setSlot(slot)` 单参数签名二次拦截 |

## 5. 降级路径（保留但不激活）

### 5.1 降级配置

| slot | 复用的 lightmap |
|---|---|
| `slot_morning` | `lm_day` |
| `slot_noon` | `lm_day` |
| `slot_dusk` | `lm_day` |
| `slot_night` | `lm_night` |

- crossfade 只在 **昼 ↔ 夜** 之间发生（每 24 游戏小时 2 次，而非 4 次）
- LUT 补足：`lm_day` 之上叠加「晨」「昏」两组色彩分级参数（4 组 slot 参数，**0 资产成本**）

### 5.2 降级后的表现损失量化（主理人问的第 2 点）

| 维度 | 结论 |
|---|---|
| **仍然保留** | 主光 direction/color/intensity 实时插值 → **光斑位置与颜色仍在动**，G-L1（5 分钟看到时间在走）**仍然达成** |
| **仍然保留** | 昼夜的阴影差异 → 支柱二的核心（"光会移动"）**不倒** |
| **损失 1** | 晨（斜入 30–45°）与昏（极长投影）共用昼套 → **窗框投影的软边、灰尘光柱的入射角、地面反弹光的分布在晨与昏之间是相同的** |
| **损失 2** | 光色变化幅度变窄 → 由 LUT 补回约 **60–70%**（LUT 能改色温与对比，改不了光的空间分布） |
| **可察觉性** | **ΔE ≈ 6–10（CIEDE2000）**，人眼可辨阈值约 ΔE 2.3 → **能看出来，但不是"跳变"**，被 0.8 s crossfade + 45 游戏分钟主光插值掩盖 |
| **最坏场景** | 连续在"晨 → 昏"之间横跳的玩家会发现"早晨和傍晚，屋里影子的软边是一样的"。**需要对比才能发现** |
| **对比：若降为 1 套** | 昼夜无差别 → **支柱二直接被抽空**。1 套不可接受 |

> **我的判断**：降级到 2 套是**可接受的中等损失**，远小于 1 套。**RUL-1 定 2 套而非 1 套是对的**。
>
> 📌 **确认 GDD PH2b §9 R-1 硬冲突**：前半段 §5.4.4 的"降级为 1 套"是错的，**以 RUL-1 的 2 套为准**。请文策渊在 v1.1 回填时同步改写 §5.4.4 的"策划侧补偿方案"表——该表按 1 套写（"阴影不再分四档变化"），按 2 套应改为**"阴影不再区分晨/昏，但仍区分昼夜"**。

## 6. 理由

### 6.1 为什么选 UASTC 而非 ETC1S

| 编码 | 显存/套 | 质量 | 判定 |
|---|---|---|---|
| **UASTC → ASTC 4×4** | 4.0 MiB | 高 | ✅ **采纳** |
| ETC1S → ETC1 | 2.0 MiB | **低频渐变上可能出现 banding** | ⏸ Android 兼容档 |

**lightmap 是低频渐变数据，banding 是它最致命的缺陷**——玩家在昏时段的暖色渐变上看到色带，直接破坏"家的诗意"。

代价是显存翻倍（8 → 16 MiB），但 **16.7% 仍远低于 60% 阈值**，这个代价完全付得起。

> ⚠️ **iOS 的特殊注意**：Basis 的 ETC1S **不能**转码到 ASTC（只能转 ETC1/ETC2/BC1/BC3/PVRTC1）。而 **PVRTC1 4bpp 在低频渐变上会产生严重色带**。因此 iOS 上要么走 UASTC→ASTC，要么 ETC1S→ETC2（8 bpp，显存同样是 4.0 MiB 但质量不如 ASTC）。**选 UASTC→ASTC。**

### 6.2 为什么是 shader 注入而非双 mesh

见 §3.5。**+10~12 draw call 在移动端是从 28 到 ~40 的 43% 增幅**，且 alpha blend 的 overdraw 在 fill rate 上是致命的。shader 注入是唯一可行路径——这也是 ADR-101 选 Three.js（保留 `onBeforeCompile`）而非更高级别框架的原因。

### 6.3 为什么 crossfade 只编译 1 个 program 变体

若 crossfade 用 `#define` 切换（有 crossfade / 无 crossfade 两套 shader），则每次时段切换都会触发一次 shader 重编译（中端移动 200–800 ms 卡顿）。

**A/B 双 sampler 恒在 + 只改 uniform** 让重编译次数为 **0**，直接消解风险 T-4。代价是稳态多一次纹理 fetch——通过把 B 指向 1×1 白纹理降到近乎免费。

### 6.4 为什么稳态只驻留 2 套

crossfade 的数学只需要"当前 + 目标"两套在场。第 3 套（下一时段）是预取，第 4 套按需。**这把稳态显存从 4 套（16.0 MiB）降到 2 套（8.0 MiB），而视觉完全等价。**

### 6.5 为什么色彩分级必须在 ACES 之后

`ACESFilmicToneMapping` 在 Three.js 内置材质的 shader 末尾执行。若色彩分级在 ACES 之前，它会被 ACES 再压一遍，导致：
- 冬天想要的"低饱和冷调"被 ACES 的对比曲线拉回
- 美术在 DCC 里调好的 LUT 与运行时不一致

**管线顺序**：`scene → [ACES 内置] → RT → tilt-shift → 色彩分级 → vignette → screen`
