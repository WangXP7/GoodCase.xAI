## 1. 背景

美术圣经 §8.4 已定义三档（H 高端 / M 中端 / L 低端），但**没有给出触发策略**（Phase 1 Q5 已指出："触发策略需细化"）。同时：

- **`WEBGL_debug_renderer_info` 在现代浏览器中已被限制/伪造**，GPU 字符串不能作为分档的唯一依据
- 用户可在设置中**手动覆盖**（美术 §8.4）
- 降级必须**可回退**（性能富余时升档），否则旗舰机用户被永久锁在中档

本 ADR 定义：探测什么、怎么分档、怎么降级、怎么回退。

## 2. 决策

### 2.1 能力探测矩阵（一次性探测，结果冻结）

```ts
interface Capability {
  webgl2: boolean;                  // ★ 硬红线，false → 拒绝进入
  maxTextureSize: number;           // gl.MAX_TEXTURE_SIZE
  astc: boolean;                    // WEBGL_compressed_texture_astc
  etc2: boolean;                    // WebGL2 core（ES3 必需）
  etc1: boolean;                    // WEBGL_compressed_texture_etc1
  pvrtc: boolean;                   // WEBGL_compressed_texture_pvrtc
  s3tc: boolean;                    // 桌面
  bptc: boolean;                    // 桌面高端
  halfFloatLinear: boolean;         // OES_texture_half_float_linear（morph texture 需要）
  floatBlend: boolean;              // EXT_float_blend
  maxTextureUnits: number;          // gl.MAX_TEXTURE_IMAGE_UNITS
  maxVertexUniforms: number;        // 影响骨骼数上限
  maxVaryings: number;
  rendererString: string | null;    // ★ 弱提示，不作分档依据
  deviceMemoryGB: number | null;    // navigator.deviceMemory（不可靠，仅参考）
  hardwareConcurrency: number;
}
```

> ⚠️ **`rendererString` 只作弱提示**：Chrome 从 2021 年起对 `WEBGL_debug_renderer_info` 做了限制（部分平台返回通用字符串），Safari 更早就屏蔽了。**分档的真实依据是 §2.3 的 benchmark。**

### 2.3 分档触发链（四步）

```
① 能力探测（§2.1）→ 初分档
     ├─ 无 WebGL2                              → 拒绝进入（升级提示页）
     ├─ maxTextureSize < 2048                  → 强制 L
     ├─ 无 ASTC 且无 ETC2                      → 强制 L（走 ADR-105 回退路径）
     ├─ hardwareConcurrency ≥ 8 且 deviceMemory ≥ 6  → 初分 H
     ├─ hardwareConcurrency ≥ 4 且 deviceMemory ≥ 3  → 初分 M
     └─ 其余                                    → 初分 L

② 首帧后 1 s benchmark
     渲染 N 帧（N = 60），采集中位帧时间 medianFrameMs
     ├─ medianFrameMs ≤ 0.55 × 预算   → 升一档（上限 H）
     ├─ medianFrameMs ≤ 0.85 × 预算   → 维持
     ├─ medianFrameMs ≤ 1.20 × 预算   → 降一档
     └─ medianFrameMs >  1.20 × 预算  → 降两档

③ 运行时连续监测
     滑动窗口 3 s 的帧时间 P95
     ├─ P95 > 1.2 × 预算 持续 3 s  → 降一档（冷却 30 s）
     └─ P95 < 0.5 × 预算 持续 60 s → 升一档（冷却 120 s，且只在 H/M 间升降）

④ 用户手动覆盖（设置项「画质：自动 / 高 / 中 / 低」）
     手动设置后，②③ 自动调整停止（尊重用户选择）
```

### 2.4 降级动作清单（按代价从低到高执行）

| 序 | 动作 | 省下 | 视觉代价 |
|---|---|---|---|
| 1 | 关闭灰尘/猫毛 VFX | 0.2 ms | 轻微（"活着的感觉"减弱） |
| 2 | DPR 1.25 → 1.0 | **~36% 像素量** | 中等（边缘锯齿增加） |
| 3 | 关 tilt-shift（保留 vignette） | 0.24 ms | 中等（微缩感减弱） |
| 4 | 关实时阴影 → blob shadow | 0.8–1.5 ms | 中等（接触阴影变假） |
| 5 | lightmap 2048² → 1024² | 6.0 MiB 显存 | 轻微（间接光糊一点） |
| 6 | 关 AA（SMAA） | 0.4 ms | 中等 |
| 7 | **锁 30 fps**（L 档） | — | 无（本作"慢"的调性下可接受） |
| 8 | 降动态光数（3 → 2） | 材质重编译一次 | 轻微 |
| 9 | 三角面预算收紧（LOD1 提前切换） | — | 中等 |

> **执行顺序很重要**：先降 DPR（省最多、代价最小），最后才降帧率。这符合 Phase 1 §3.3 的判断——**移动端真正的瓶颈是 fill rate，不是三角面**。

### 2.5 降级必须"可逆但有阻尼"

| 方向 | 触发条件 | 冷却 |
|---|---|---|
| 降档 | P95 > 1.2 × 预算 持续 **3 s** | 30 s |
| 升档 | P95 < 0.5 × 预算 持续 **60 s** | 120 s |

**升档比降档保守 20 倍**——宁可让旗舰机用户停在中档，也不要反复横跳（横跳的视觉抖动比一直停在中档更糟）。

**只有 H ↔ M 之间会自动升降；L 档一旦进入，只能由用户手动升回**（L 档设备通常没有升档空间，反复尝试会伤害体验）。

## 3. 备选方案

### 3.1 备选 A · 纯 UA / GPU 字符串分档（美术 §8.4 的原文表述）

| 维度 | 评价 |
|---|---|
| 优点 | 零成本、即时生效 |
| 缺点 | **`WEBGL_debug_renderer_info` 已被 Chrome 限制、Safari 屏蔽**；UA 可被伪造；新设备不在列表里会被误判为 L |
| 判定 | ❌ **否决作为唯一依据**，保留为初分的弱提示 |

### 3.2 备选 B · 纯运行时 benchmark 分档

| 维度 | 评价 |
|---|---|
| 优点 | 反映真实性能 |
| 缺点 | **首帧就必须用一个档位渲染**（鸡生蛋问题）；benchmark 期间的卡顿会被玩家看到 |
| 判定 | ⏸ **部分采纳**。benchmark 放在首帧**之后**，且首帧一律用 M 档 |

### 3.3 备选 C · 只有两档（高 / 低）

| 维度 | 评价 |
|---|---|
| 优点 | 简单 |
| 缺点 | 中端机（iPhone 11 / Snap 7 系）是本作的**主力设备群**，两档会让它们要么过热要么画质过差 |
| 判定 | ❌ **否决**。三档是必要的 |

### 3.4 备选 D · 无自动降级，只有用户手动设置

| 维度 | 评价 |
|---|---|
| 优点 | 完全可预测，无横跳 |
| 缺点 | 大多数玩家不会去设置页；中端机用户会在不知情的情况下忍受 25 fps |
| 判定 | ❌ **否决**作为唯一机制；**手动覆盖保留为最高优先级**（尊重用户） |

### 3.5 备选 E · 用 `navigator.deviceMemory` / `hardwareConcurrency` 作为主依据

| 维度 | 评价 |
|---|---|
| 优点 | 无需 benchmark，即时 |
| 缺点 | iOS Safari **不暴露 `deviceMemory`**；`hardwareConcurrency` 只反映核心数不反映 GPU；这两个值都不能区分"旗舰 GPU + 低内存"与"中端 GPU + 大内存" |
| 判定 | ⏸ **只用于初分**，最终以 benchmark 为准 |

## 4. 理由

### 4.1 为什么 DPR 是第一个降级杠杆

Phase 1 §3.3 已论证：**移动端真正的瓶颈是 fill rate，不是三角面。**

```
DPR 1.25 → 1.0：像素量减少 1 - (1.0/1.25)² = 36%
帧率提升通常 30–60%
```

而它对三角面、draw call 零影响，视觉代价只是"锯齿变明显"——在正交等距 + 暖光 + 软材质的画面上，锯齿的观感伤害远小于掉帧。

### 4.2 为什么升档比降档保守 20 倍

档位横跳会造成：
- 材质重编译（动态光数变化）→ 200–800 ms 卡顿
- DPR 变化 → 画面尺寸跳变
- lightmap 分辨率切换 → 贴图重新上传

**一次横跳的成本，远大于"旗舰机停在中档"的损失。** 所以升档要求 60 s 稳定 + 120 s 冷却。

### 4.3 为什么 L 档不做自动升回

L 档设备（iPhone SE2 / Snap 6 系）通常**没有升档空间**。自动升回会导致：升档 → 3 s 后掉帧 → 降档 → 60 s 后再升档 → … 的振荡。

**L 档一旦进入，只由用户手动升回。** 这是有意的非对称设计。

### 4.4 为什么 `maxTextureSize < 2048` 直接强制 L

lightmap 是 2048²（ADR-103）。若设备 `MAX_TEXTURE_SIZE < 2048`，lightmap 无法上传，画面会全黑。

**这是能力红线，不是性能判断。** 必须在探测阶段就拦截并强制走回退路径（lightmap 降为 1024²）。

### 4.5 为什么 `halfFloatLinear` 需要探测

Three.js r172 的 morph texture 用 `HalfFloatType`。若设备不支持 `OES_texture_half_float_linear`，morph 采样会回退到 nearest，导致**表情抖动**。

虽然 WebGL2 core 已包含 half float 纹理，但**线性过滤**是独立扩展。必须探测，不支持时强制 L 档并提示（或关闭 morph 的线性过滤，接受抖动）。

## 5. 影响

### 5.1 正面

| 项 | 说明 |
|---|---|
| 覆盖 | 从旗舰到入门机全谱覆盖，且降级可逆 |
| 主力设备（中端） | 有专属档位，不会过热也不会画质过差 |
| 用户主权 | 手动覆盖是最高优先级，自动调整立即停止 |
| 稳定 | 升档阻尼 20×，避免横跳 |

### 5.2 负面 / 代价

| 项 | 说明 | 缓解 |
|---|---|---|
| **benchmark 期（1 s）玩家会看到卡顿** | 首帧用 M 档渲染，1 s 后调整 | benchmark 放在 loading 遮罩内完成 |
| **档位切换时的 hitch** | 材质重编译 + 贴图重传 200–800 ms | 切换时展示"正在调整画质"的极简提示（0.5 s 内消失） |
| **探测矩阵维护成本** | ~150 LOC + 每次浏览器更新需复核 | 单元测试覆盖 6 种模拟能力组合 |
| **L 档不自动升回可能让部分设备"永远低画质"** | 有意设计 | 设置项可手动升 |

### 5.3 对下游的约束

| 对象 | 约束 |
|---|---|
| **美术** | **不接受"Retina 全分辨率"**——DPR 由程序控制（H 1.5 / M 1.25 / L 1.0）（AR-9） |
| **美术** | 所有可关闭的视觉项（tilt-shift / 灰尘 / 猫毛 / 阴影）都必须有"关闭后仍然成立"的设计 |
| **策划** | L 档下粒子数为 0，任何依赖粒子的情感反馈必须有非粒子替代通道 |
| **QA** | 三档 × 3 台真机 = 9 组回归用例 |

## 6. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| **A106-R1** | 能力探测在某些 Android WebView 上抛异常 | 🟠 P1 | 全 `try/catch` 包裹；探测失败默认降一档（保守） |
| **A106-R2** | benchmark 在低端机上本身就慢，导致误判为更低档 | 🟡 P2 | benchmark 用最简场景（空场景 + 1 个 quad），测的是"填充能力"而非"游戏负载" |
| **A106-R3** | 档位切换的 hitch（200–800 ms）被玩家读成"卡死" | 🟠 P1 | 只在 loading 或明确提示时切换；运行时切换加 0.5 s 提示 |
| **A106-R4** | `halfFloatLinear` 不支持 → morph 抖动 | 🟡 P2 | 探测后强制 L 档；或在 shader 里对 morph 做手动双线性插值（备用方案，+0.2 ms） |
| **A106-R5** | 用户手动设为"高"但设备跑不动，玩家怪游戏优化差 | 🟡 P2 | 手动设置时给一次极轻提示；检测到持续掉帧时**询问**（不自动降） |
| **A106-R6** | iOS 内存 kill 与档位无关（即便 L 档也可能被 kill） | 🔴 P0 | 见 ADR-102 / 架构 T-2；纹理红线 64 MiB（L 档）是主要防线 |
