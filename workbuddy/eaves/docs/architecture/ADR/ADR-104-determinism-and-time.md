## 1. 背景

### 1.1 RUL-9 的原文

> **MVP 不实现回放功能，但架构层必须做好两件事**：① 全局 RNG 种子化 ② 逻辑固定步长（与渲染帧率解耦）
>
> 理由：这两件事本身就是好架构（对养成游戏的确定性模拟有独立价值），且成本几乎为零。做了它们，将来加回放不必返工；不做，将来要重写。这是"**现在免费、以后昂贵**"的典型。

### 1.2 RUL-4 的三段式时间

```
① 进入时刻锚定：  gameMinutes₀ = 本地真实时刻（含时区）
② 会话内加速：    gameMinutes += dt_real × 12      ⚙ TIME_SCALE = 12
③ 离线推进：      1:1，离线 8 小时 = 游戏内 8 小时
附加：单次会话最多推进 6 游戏小时；设置项「真实 / 加速」，默认加速
```

### 1.3 需要本 ADR 解决的问题

1. 固定步长的**步长值**取多少？（1/60 还是 1/30？）
2. 分层 tick（0.5/4/1/1÷60 Hz）与固定步长**如何共存**？—— 这是 TECH-1 的实质
3. RNG 如何**分多路**？哪些流需要持久化？
4. 游戏时钟与真实时钟的**边界**在哪里？哪些计时用真实秒、哪些用游戏分钟？

---

## 2. 决策

### 2.1 固定步长

| 参数 | 值 | 理由 |
|---|---|---|
| **`STEP_SECONDS`** | **1/30 s（33.33 ms）** | 最快的 tick 层是 4 Hz（0.25 s），1/30 足够；且移动端 30 fps 档下每帧恰好 1 步，零抖动 |
| `MAX_CATCHUP` | **5 步** | 追帧上限 166 ms，超出直接丢弃时间（宁可慢放不要雪崩） |
| `frameMs` clamp | **[0, 250 ms]** | 覆盖"切后台 3 小时回来"这类 dt 爆炸 |
| 渲染插值 | `alpha = accumulator / STEP_MS` | **仅用于连续量**（位移、相机、尾巴骨骼）；**离散量**（状态、morph 目标）不插值 |

```ts
function frame(nowMs: number) {
  let frameMs = clamp(clock.tick(nowMs), 0, 250);
  accumulator += frameMs * timeScale;               // ×12（RUL-4）
  let steps = 0;
  while (accumulator >= STEP_MS && steps < MAX_CATCHUP) {
    simulation.step(STEP_SECONDS);                  // 固定 dt = 1/30 s
    tickScheduler.advance(STEP_SECONDS);            // 分层 tick 在此调度
    accumulator -= STEP_MS;
    steps++;
  }
  if (steps === MAX_CATCHUP) accumulator = 0;       // 防 spiral of death
  presentation.update(accumulator / STEP_MS, frameMs);
  renderer.render(scene, camera);
}
```

### 2.2 分层 tick 在固定步长之上调度（**TECH-1 的实质**）

> **这是本 ADR 最关键的一条**：分层 tick **不是**固定步长的替代品，而是叠加在固定步长时间轴上的**低频调度器**。

```ts
// core/tick-scheduler.ts
interface TickLayer { period: number; nextDueAt: number; run: () => void }

advance(dt: number) {                 // dt 恒为 STEP_SECONDS
  this.simTime += dt;
  for (const layer of this.layers) {
    while (layer.nextDueAt <= this.simTime) {
      layer.run();
      layer.nextDueAt += layer.period;   // ★ 不是 = simTime + period（防漂移）
    }
  }
}
```

**权威 tick 表**（合并 GDD §3.5 与 §5.3.1，落实 R-8）

| 层 | 周期常量名 | 周期 | 频率 | 每帧摊销 @60fps |
|---|---|---|---|---|
| 微表情 | `MICRO_PERIOD_S` | 0.25 s | 4 Hz | 0.0067 ms |
| 生理需求 | `NEEDS_PERIOD_S` | 1.0 s | 1 Hz | 0.0003 ms |
| 行为决策 | `BEHAVIOR_PERIOD_S` | 2.0 s | 0.5 Hz | 0.0050 ms |
| 性格结算 | **`PERSONALITY_PERIOD_S = 60`** | **60 s** | 1/60 Hz | 0.000014 ms |
| 自动存档 | `AUTOSAVE_PERIOD_S` | 30 s | 1/30 Hz | 0.0003 ms |
| | | | **合计** | **≈ 0.012 ms/帧（帧预算 0.07%）** |

> 📌 **命名修正**：GDD 写的是「性格 **1/60 Hz**」。这个写法极易被实现者误读为 **60 Hz**（每帧跑一次）。**代码常量必须是 `PERSONALITY_PERIOD_S = 60`，文档统一写"周期 60 s（= 1/60 Hz）"**。这是最危险的一类歧义。

### 2.3 我对 GDD tick 表的 3 处修正

| # | GDD 原方案 | 修正 | 理由 |
|---|---|---|---|
| **①** | 「性格 1/60 Hz」 | 常量命名 `PERSONALITY_PERIOD_S = 60`，文档双写 | 防误读为 60 Hz |
| **②** | 「光照色温 每 5 游戏分钟」占一个 tick 层 | **移出 tick 表**，改为游戏分钟整数边界**事件**驱动 | 它本来就是 `time` 模块的派生行为；占一个 tick 槽会引入"两层调度器对不齐"的隐患 |
| **③** | tick 表用于在线推进 | **离线结算禁止复用 tick 表** | 30 天 × 86400 s ÷ 1 s = **260 万次**需求 tick ≈ 52 秒。必须走闭合解 |

**修正 ③ 的展开**（架构 §9.2）：

| 量 | 算法 | 复杂度 |
|---|---|---|
| `HNG`/`HYD`/`TOI` | 闭合解 `v' = clamp(v − rate × gameHours, 0, 100)` | O(1) |
| `warmth` / `AFF` / `CUR` | 闭合解（线性 + clamp + 地板） | O(1) |
| **`ENE`** | **粗粒度模拟，15 游戏分钟步长** | 30 天 = 2880 步 ≈ 58 ms，分 4 帧 |
| 日记生成 | GDD §5.6.2 的 7 步算法 | O(n)，n ≤ 5 |

> `ENE` 为什么不能闭合解：`ENE_rec = (2.0 + VIT×0.04) × (0.6 + VIT/125)` 点/分，猫在 30 天里经历数百次睡/醒循环，这是非线性分段函数。15 分钟步长的误差 vs 1 分钟：< 0.5 点，可忽略。

### 2.4 RNG：PCG32 + 四路独立流

| 流 | 用途 | 持久化 | 为什么 |
|---|---|---|---|
| `rng.core` | 行为决策抽取、三态判定、保底触发 | ✅ | 决定可观测状态 |
| `rng.journal` | 离线日记的行为/地点/评论抽取 | ✅ | 决定可观测内容 |
| `rng.genesis` | 猫的基因生成（一次性） | ✅ | 猫生下来就定了 |
| `rng.cosmetic` | 微表情抖动、猫毛位置、灰尘漂浮 | ❌ **不持久化** | 不影响任何可存档状态；省 8 字节/存档；让回放更宽松 |

**算法选择**：

| 算法 | 周期 | 状态 | 判定 |
|---|---|---|---|
| `Math.random()` | 不可种子化 | — | ❌ **CI 禁止出现在业务代码** |
| `Mulberry32` | 2³² | 1×uint32 | ❌ 90 天约 10⁶ 次抽取，虽未触周期但余量不足 |
| **PCG32** | **2⁶⁴** | **2×uint32** | ✅ **采纳**（~40 LOC） |

**存档字段**：`rng: { core: [u32, u32], journal: [u32, u32], genesis: [u32, u32] }`（24 字节）

**CI 强制**：ESLint `no-restricted-properties` 禁止业务代码出现 `Math.random`（`debug/` 豁免）。

### 2.5 两个时钟的分离

| 时钟 | 来源 | 用途 | 受 ×12 影响 |
|---|---|---|---|
| **真实时钟** | `performance.now()`（单调） | 帧驱动、动画缓动、**0.8 s crossfade**、冷却计时、自动存档间隔、UI 动效 | ❌ |
| **游戏时钟** | `realMs × timeScale` 积分 | 时段判定、需求衰减、昼夜节律、离线结算、状态最小驻留 | ✅ |

> ⚠️ **0.8 s crossfade 用真实秒**（RUL-1 原文是墙钟时间）。×12 下它等于 9.6 游戏分钟，而过渡窗是 45 游戏分钟 = 225 真实秒 → crossfade 占过渡窗的 **0.36%**。与 GDD PH2b §3.4.2 图示一致。
>
> ⚠️ **状态最小驻留用游戏分钟**（`stateEnteredAtGameMin`），不用 epoch。理由：×12 加速下驻留必须在游戏时间上正确；且 epoch 与 `monotonicMs` 混存会在时区切换后算错（架构 §4.3 修正 S-1）。

### 2.6 防作弊（GDD §5.7 落地）

| # | 手段 | 实现 |
|---|---|---|
| ① | 单调时钟优先 | `performance.now()` 累计在线时长 |
| ② | 双时间戳 | 存 `savedAtEpoch`（`Date.now()`）与 `monotonicMs`（`performance.timeOrigin + performance.now()`），**取较大者** |
| ③ | 回拨检测 | `now < lastSavedAt` → **冻结本次离线结算**（不回滚、不产生日记、不推进需求），仅 `console.info`，**不弹提示**（GDD E3-2） |
| ④ | 前进 clamp | `> 30 天` → clamp 到 30 天（T6 封顶） |
| ⑤ | 时区记录 | `tzOffsetMin` 变化 → 保守按 T1 处理 |
| ⑥ | 校验和 | CRC32（ADR-102） |
| ⑦ | 明确不做 | 不加密、不混淆、不防 DevTools |

## 3. 备选方案

### 3.1 备选 A · 可变步长（dt = 帧时间）

| 维度 | 评价 |
|---|---|
| 优点 | 实现最简 |
| 缺点 | **逻辑结果依赖帧率**——同一局在 60 fps 与 30 fps 下会走出不同的猫。直接违反 RUL-9 的"与渲染帧率解耦" |
| 判定 | ❌ **否决** |

### 3.2 备选 B · 固定步长 1/60 s

| 维度 | 评价 |
|---|---|
| 优点 | 精度更高；与 60 fps 天然对齐 |
| 缺点 | **移动端 30 fps 档下每帧要跑 2 步**，CPU 成本翻倍（虽然绝对量很小）；且 `MAX_CATCHUP` 的追帧时间减半（83 ms），更容易触发慢放 |
| 判定 | ❌ **否决**。最快的 tick 层是 4 Hz，1/60 的精度是浪费 |

### 3.3 备选 C · 固定步长 1/10 s

| 维度 | 评价 |
|---|---|
| 优点 | 更省 CPU |
| 缺点 | 快于 4 Hz（0.25 s）的动画会失真；离线结算的 ENE 粗粒度步长会被迫对齐到 1/10 s（精度过高，步数变多） |
| 判定 | ❌ **否决**。1/30 是"够用且有余量"的甜点 |

### 3.4 备选 D · 单路全局 RNG

| 维度 | 评价 |
|---|---|
| 优点 | 实现最简，存档只存 8 字节 |
| 缺点 | **"日记生成消耗了 3 个随机数"会让"行为决策的抽取结果"漂移**。这意味着：玩家翻不翻日记会改变猫的行为——**不可接受** |
| 判定 | ❌ **否决**。分路是刚需 |

### 3.5 备选 E · RNG 用 `Math.seedrandom` / 第三方库

| 维度 | 评价 |
|---|---|
| 优点 | 零实现成本 |
| 缺点 | 引入运行时依赖；`seedrandom` 的算法（ARC4）质量与速度都不如 PCG32；且需要保存字符串状态 |
| 判定 | ❌ **否决**。PCG32 只要 40 LOC |

### 3.6 备选 F · 时间锚定用 UTC 而非本地时区

| 维度 | 评价 |
|---|---|
| 优点 | 跨时区行为一致，无需 `tzOffsetMin` 检测 |
| 缺点 | **RUL-4 的核心价值是"我晚上打开，屋里就是晚上"**——这必须用**本地**时刻。UTC 锚定会让北京玩家在 UTC+8 的晚上 8 点看到正午 |
| 判定 | ❌ **否决**。GDD §5.7 ⑤ 的时区检测是必要的代价 |

## 4. 理由

### 4.1 为什么 1/30 而不是 1/60

| 论据 | 说明 |
|---|---|
| tick 频率的下限 | 最快的分层 tick 是 4 Hz（0.25 s = 7.5 个 1/30 步）。1/60 的精度在这之上没有可观测收益 |
| 移动端 30 fps 档 | 1/30 步长下每帧恰好 1 步，零抖动；1/60 下每帧 2 步，追帧预算减半 |
| CPU | 1/30 的模拟层调用次数是 1/60 的一半。虽然绝对量都很小（0.012 ms/帧），但没有理由付这个钱 |

### 4.2 为什么 `nextDueAt += period` 而不是 `= simTime + period`

后者会让 tick **漂移**——每次执行都丢失 `(simTime - nextDueAt)` 的余量，长时间运行后 4 Hz 的 tick 会变成 3.9 Hz。**累加式**保持长期频率精确，这是确定性模拟的必要条件。

### 4.3 为什么 `cosmetic` 流不持久化

| 论据 | 说明 |
|---|---|
| 不污染存档 | 省 8 字节（小），但更重要的是**减少"必须逐字节保留"的字段** |
| 回放可以更宽松 | 未来做回放时，视觉抖动不必逐帧复现，只需"看起来像" |
| 无观测差异 | 微表情抖动、猫毛位置、灰尘漂浮都不写入任何可存档字段 |

**风险**：如果将来某个"cosmetic"用途变成了影响状态的（例如"猫毛位置影响锚点偏好"），必须立即移到 `core` 流。**代码注释里写死这条警告。**

### 4.4 为什么离线结算必须走闭合解

30 天离线若按 1 Hz 逐 tick 跑：

```
30 天 × 86400 s ÷ 1 s = 2,592,000 次需求 tick
每次 0.02 ms → 51,840 ms ≈ 52 秒
```

中端移动上 52 秒的白屏是不可接受的。而 `HNG`/`HYD`/`TOI` 的衰减是**线性 + clamp**，数学上有闭式解，结果与逐 tick 积分**完全等价**（浮点误差 < 0.01 点）。

**这不仅是性能优化，是可行性问题。**

### 4.5 为什么 RUL-9 值得做（即便 MVP 不做回放）

| 收益 | 说明 |
|---|---|
| **可测试性** | 种子化 RNG + 固定步长让整个模拟层可以在 Vitest 里 headless 跑确定性测试。GDD 的沙盘（Python）可以直接移植为 JS 的回归测试 |
| **数值验证** | 策划的沙盘结论（"D30 进入信任"等）可以在 CI 里自动验证 |
| **回放的期权** | 将来加回放只需存 Intent 序列 + RNG 流，不必重写模拟层 |
| **成本** | PCG32 40 LOC + 固定步长 150 LOC ≈ **2.5 人日** |

## 5. 影响

### 5.1 正面

| 项 | 说明 |
|---|---|
| 帧率无关 | 60 / 30 / 20 fps 下逻辑结果完全一致 |
| 可测试 | 模拟层可在 Vitest 中 headless 跑，GDD 沙盘可自动化回归 |
| 回放期权 | RUL-9 兑现，将来加回放不返工 |
| 离线结算 | 从 52 秒降到 **< 110 ms**（中端移动，分帧） |
| tick 开销 | **0.012 ms/帧（帧预算 0.07%）**，比"全部每帧"省 98.4% |

### 5.2 负面 / 代价

| 项 | 说明 | 缓解 |
|---|---|---|
| **渲染插值增加复杂度** | 表现层要区分"连续量插值"与"离散量不插值" | 约定：`CatExpressionTarget` 的数值插值，状态/事件不插值 |
| **`simulation/` 必须零 three 依赖** | 否则 headless 测试跑不起来 | ESLint CI 阻断（架构 D-1） |
| **离线结算不能用 tick** | 需要额外写一套闭合解 + 粗粒度模拟 | 契约测试：对同一段离线时长，闭合解 vs 逐 tick 积分的结果误差 < 0.01 点 |
| **RNG 分路增加心智负担** | 开发者要判断"这个随机用途属于哪一路" | 代码注释 + code review checklist |

### 5.3 对下游的约束

| 对象 | 约束 |
|---|---|
| **全体** | 业务代码**禁止** `Math.random`（ESLint 阻断，`debug/` 豁免） |
| **全体** | 新增需要随机性的功能，必须声明它属于哪一路 RNG 流 |
| **策划** | 离线回填的数值规则必须是**线性 + clamp**，否则无法闭式求解（若加入非线性项需提前告知程序） |
| **策划** | `timeSlot`（4 档）与 `circadianBand`（5 档）是两个枚举（GDD R-3） |
| **美术** | 0.8 s crossfade 是**真实秒**，不是游戏时间 |

## 6. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| **A104-R1** | 某个"cosmetic"用途后来变成影响状态的，导致回放不可复现 | 🟡 P2 | 代码注释警告；code review 检查 `rng.cosmetic` 的每次调用 |
| **A104-R2** | 闭合解与逐 tick 积分的结果漂移（策划后期加入非线性规则） | 🟠 P1 | 契约测试：两者误差 < 0.01 点，CI 阻断 |
| **A104-R3** | `MAX_CATCHUP` 触发导致时间"变慢"，玩家察觉 | 🟡 P2 | 追帧上限 166 ms 是 5 帧的余量；只有极端卡顿时触发 |
| **A104-R4** | 浮点累积误差导致长时间运行后 `gameMinutes` 漂移 | 🟡 P2 | `gameMinutes` 用 `double`（JS number）累加，30 天精度损失 < 1 ms |
| **A104-R5** | 时间作弊（改系统时间） | 🟡 P2 | GDD §5.7 七条；**明确不做加密/混淆**（GDD §5.7 ⑦） |
| **A104-R6** | 离线 30 天的 ENE 模拟在低端机上超预算（58 ms → ~120 ms） | 🟠 P1 | 分帧执行，每帧 ≤ 16 ms（风险 T-6） |
