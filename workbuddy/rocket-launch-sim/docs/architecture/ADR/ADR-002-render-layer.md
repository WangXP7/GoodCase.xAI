# ADR-002 · 渲染层选型

- **状态**：已接受（Accepted）
- **日期**：Phase 3
- **决策者**：程基岩（技术/引擎）
- **关联**：ARCH-1 §6 · 美术圣经 §5 · GDD S7

## 背景（Context）

需要渲染：9 段天空色带、程序化环境（网格/状态灯/剪影）、箭体、火焰、`zoom rails` 相机，以及**信息密度极高**的 HUD（5 读数 + 5 动词 + Ω 双模态指示器 + 结算面板）。目标平台 = TapTap **桌面浏览器**，需 1920×1080 基准自适应。原型阶段无最终美术资产。

## 决策（Decision）

**使用 Phaser 3.80.1，渲染层基于其 `Graphics` 程序化绘制（底层 WebGL，自动回退 Canvas）。**
- 场景分 `WorldScene` / `HudScene` 两层。
- 静态几何**绘制一次**（面板框/角标/刻度/标签），每帧只更新 1 个动态 `Graphics` + 动态文本。
- 不引入任何位图美术资产（原型阶段）。

## 备选方案（Alternatives）

| 方案 | 优点 | 为何不选 |
|---|---|---|
| **纯 Canvas2D 手写** | 零依赖、包体最小 | 需自造场景/输入/缩放/时间循环/Sprite 管理；HUD 的复杂原点定位与相机分层要重写；开发成本远高于收益 |
| **纯 WebGL 手写** | 性能上限最高 | 对"程序化色块图形"属过度工程；着色器/批处理调试成本高；原型阶段收益为负 |
| **DOM + CSS 做 HUD** | HUD 排版简单、矢量清晰 | 与游戏世界分层/缩放同步麻烦；每帧跨 DOM 边界更新文本触发重排，性能不可控；Ω 指示器的动态填充动画不便 |
| **PixiJS** | 渲染性能优秀 | 与 Phaser 同量级；Phaser 额外自带场景/输入/缩放/时间循环，省更多胶水 |

## 后果（Consequences）

**正向**
- 场景管理、输入、`Scale.FIT`、时间循环开箱即用，开发聚焦"玩法闭环"。
- `Graphics` 程序化图形 → 无需等美术资产即可验证玩法。
- 静态合批 + 单动态 Graphics → draw call 远低于 90 红线。

**负向 / 代价**
- **包体**：`phaser.min.js` 1.18 MB，逼近首屏 1.2 MB 红线（见 ARCH-1 §6.1）。正式版需自定义构建裁剪或 gzip/brotli 传输。
- 绑定 Phaser API：升级需回归（当前钉死 3.80.1）。

**触发重评的条件**
- 包体成为发布阻塞（首屏 >1.2 MB 且不可压缩）→ 换自定义 Phaser 构建或迁移渲染层（core 不受影响，因 core 与渲染解耦）。
