> - **(A) 位图 / 图集资产**：需要导出的 PNG / WebP 文件（火焰序列、烟、辉光、星图、碎片、图标、字体）。

>
> 这个区分是本规格的核心：**当前 `src/render/` 的美术 100% 是 (B) 程序化生成**（见 §0），如果把本规格写成"假设全部是位图"，会与实际管线完全脱节。§6.0 给出"必须资产化 vs 保留程序化"的二分判断。

> **✅ 火箭帧数压缩 —— 主理人已批准（附条件）**
>
> 美术圣经 §10.3 原给"火箭 60 帧"预算（含三态姿态）。**本规格压缩为 8 个静态部件 sprite**（已写入美术圣经 v1.2 §10.3：60 → 8，合计 270 → 218 帧），三态差异由 `rotation` / `tint` / 尾焰组切换在运行时实现。
>
> **附条件回答 ——"8 帧是否够表达点火→满推力的渐变？"**：
> **够，因为该渐变根本不由箭体帧承担。** 点火→满推力是**火焰长度与形态**的变化（0 → 40% → 100% 满焰，约 0.4s），由**火焰 sprite 序列（30 帧）+ 运行时长度插值**表达；**箭体本身在点火前后不发生形变**（只有 `rotation` 与底部补光 `alpha` 变化）。故箭体只需 8 个静态部件。
>
> **若仍要更多箭体帧**：建议上限 **12–16 帧**（如待机微摆位移、一级/二级各补 2–3 个状态变体），并**从延展层等量砍帧**（延展层的"火箭三态序列 60 帧"本就是备选）—— **绝不能为箭体加帧而砍火焰**（火焰是全作最贵单点，美术 §1 K2）。

## §2 位图资产技术规格（(A) 类逐项）

> **通用规格**：色彩空间 **sRGB**；位深 **8-bit/通道**；`premultipliedAlpha = false`（Phaser 默认）；`trim: true`、`extrude: 0`、`padding: 2`（美术 §6.0 / §10.2）。
> **格式决策树**：含**连续 alpha 渐变**（火焰/烟/辉光）→ **WebP q=82**（PNG-8 只有 1-bit alpha，会锯齿）；**纯色硬边 UI**（图标/角标/数字位图）→ **PNG-8**；**禁止未压缩 PNG-32 作精灵图**（美术 §6.0）。

### 2.1 火焰序列（最高优先级 VFX 资产）

| 项 | 规格 |
|---|---|
| **总帧数** | 3 层 × 5 帧 × 2 组（大气 / 真空）= **30 帧** |
| **画布 / 锚点** | 画布尺寸见 §1.5；**锚点固定在画布顶边中点**（= 喷口挂接点），便于 `setOrigin(0.5, 0)` 贴附 |
| **格式** | WebP q=82（含 alpha） |
| **透明通道** | ✅ 必须（火焰外缘需透明） |
| **混合** | 运行时 `BlendMode.ADD` |
| **帧循环** | 0.083s / 12fps；**三层错拍**：核心 0.083 / 中层 0.091 / 外层 0.077（美术 §4.2） |
| **图层结构** | 单帧内为**层叠**的 3 张独立图（不合成一张），运行时按层叠加 |
| **@2x 决策** | ⚠️ **仅出 @1x**（见 §7.3 纹理内存核算——火焰 @2x 会击穿 48MB 红线） |

**大气组 vs 真空组差异**：真空组外层消失，核心 + 中层改为**羽毛状扩散**（长度 ×1.6、宽度 ×2.4、alpha ×0.7，美术 §4.2）。故需**两套独立序列**。

## §3 导出规范

### 3.1 图层结构（源文件 → 导出）

**火焰 / 烟 / 辉光（半透明特效）**：
```
源（PSD/Aseprite）
├─ 每帧一层（frame_01 … frame_05）          ← 独立导出
├─ 层内：形状层（硬边） + 可选内发光层（烘焙，非实时）
└─ 背景：透明（导出时关闭背景层）
导出：逐帧 PNG-32（源）→ 构建期转 WebP q=82
```
- **禁止**把三层火焰合并进一张图——运行时按层叠加以便错拍与独立缩放。
- **禁止**在源文件上使用图层蒙版柔化边缘——硬边是母题（K2）。

**火箭 / 部件（不透明 + 少量 alpha）**：
```
源
├─ 主体平色层（P1）
├─ 阴影带层（右下 30%，−30% 明度，硬边）        ← 美术 §4.1 三段平铺
├─ 高光线层（1px，+25% 明度）
└─ 细节层（燃料管 / 铆钉点阵 / 环带）
导出：合并为单张 sprite（不透明区外透明）
```
- 光源统一**上方偏左 15°**，投影**向右下、固定 75°**（美术 §4.6）。

**UI / 图标（纯色硬边）**：
```
源
├─ 形状层（硬边几何，圆角仅 {0,2,4,8}）
└─ 描边层（统一 1px，P3 或填充色 60% 明度）
导出：PNG-8（≤256 色 + 1-bit alpha）
```

### 3.2 透明通道处理

| 情形 | 处理 |
|---|---|
| 火焰 / 烟 / 辉光 | **连续 alpha**，导出不得预乘；Phaser 默认非预乘，勿改动 |
| 火箭 / 图标 | **1-bit alpha 或硬边 alpha**，边缘必须干净无半透明灰边（否则缩放出脏边） |
| 图集打包 | `trim: true` 会让透明边被裁掉 → **必须**在图集 JSON 记录 `sourceSize` 与 `pivot`，运行时按 `sourceSize` 还原锚点 |
| 天光 / 补光 | 补光**不烘进贴图**（美术 §4.6 要求随事件变色），走独立 `fx_rimlight_*` 叠层 |

## §4 图集策略

### 4.1 合并规则

| 图集 | 收录 | 最大尺寸 | 打包参数 |
|---|---|---|---|
| `atlas_core_2048_1x` / `_2x` | 火箭 8 部件 + 地面设备 + 环境物件 | **2048 × 2048** | padding 2 / trim true / extrude 0 |
| `atlas_fx_1024_1x` | 烟 3 + 烟环 3 + 碎片 14 + 辉光 2 + 补光 2 + 余烬 1 + 噪点 | **1024 × 1024** | 同上 |
| `atlas_ui_1024_1x` | 图标 16 + 角标 + 数字位图 | **1024 × 1024** | 同上 |
| `sheet_flame_1024x2048_1x` | **火焰 30 帧独立 sheet** | 1024 × 2048 | 火焰因数量大单独打，避免挤占 fx |
| `atlas_env_1x` | 星图 + 天空色带 + 地面弧 + 地球辉光 | 视情况（地面弧太大，建议单独文件） | — |

**合并原则**：
1. **按"同时出现"分组**——同屏出现的资产进同一图集（换图集 = 新增 draw call）。
2. **按"加载阶段"分组**——`boot` / `core` / `orbit` 三阶段，`orbit` 资源（星空 / 地面弧 / 辉光弧）在升空时后台预载（美术 §6.0）。
3. **火焰 / 大尺寸序列不塞进通用图集**——它们会把小图标挤到跨页，浪费面积。

### 4.2 避免浪费（结合 ≤48MB 红线）

1. **`trim: true`** 裁掉透明边——火焰帧可省 30–40% 面积。
2. **@2x 只给"会被降采样"的资产**（火箭，因为 zoom 0.75/0.5）。雾化件（烟 / 辉光）本就是软边，@1x 够用。
3. **地面弧 1920 × 240 宁可不进图集**——它单独一张拉伸，进图集反而撑爆 2048 边长。
4. **色板化成小图拉伸**：天空色带 8×512（<2KB/张）够用（美术 §6.0："天空不需要大图"）。
5. **⚠️ 硬性发现**：**3 张 2048² RGBA8 图集 = 3 × 16.78MB = 50.3MB，单这一项就超过 48MB 红线**（美术 §6.0 / §10.2 未核算到这一层）。**因此"三张 2048 图集 + 全 @2x"的组合不可行**，必须按 §7.3 的重算方案降规格。详见 §7.3。

## §6 资产生产优先级

### 6.0 资产化优先级判断（核心决策 · 现状 100% 程序化）

> 既然当前全部是程序化绘制，"**哪些必须资产化、哪些应保留程序化**"本身就是核心决策。**判断依据四条**：
> **(a) 品质**（程序化能否达到硬边有机形状 / 烘焙色阶 / 连续 alpha）；**(b) 性能**（draw call / 纹理内存）；**(c) 体积与加载**（程序化省体积、零加载）；**(d) 动态响应**（程序化可直接随 sim 状态变色 / 变形，位图需多帧或 tint）。

#### 必须资产化（A）—— 程序化达不到品质，或引擎强绑定 —— **6 大类**

| # | 资产类 | 为何必须资产化 |
|---|---|---|
| 1 | **火焰序列（30 帧）** | 有机锯齿硬边形 + `ADD` + 逐帧错拍；程序化每帧重绘 `Graphics` 违反美术 §10.4「禁止每帧重绘 Graphics」，是性能杀手 |
| 2 | **烟团 / 烟环 / 余烬** | Phaser 粒子发射器**必须有纹理**才能工作；且烟是"扁平硬边椭圆"，需 authored 形状（非程序化柔圆） |
| 3 | **辉光 / 底部补光条** | 需**预烘焙色带化径向渐变**（美术 §4.4 禁实时模糊 / T2 禁无信息脉动）——程序化做不出色带化 glow |
| 4 | **火箭 8 部件（@1x+@2x）** | 需 @2x 抗 zoom {0.75, 0.5} 降采样；程序化在 0.5× 下 1px 描边糊掉，违反 K2 硬边几何 |
| 5 | **字体（woff2）+ 位图数字集** | 遥测可读性是灵魂（概念 A3）；位图数字解决首屏闪白 + 文字 draw call 爆炸（§7.2） |
| 6 | **UI 图标 16 / 地面弧 / 行星辉光弧 / 碎片** | 语义图标需 authored 形状（色盲双通道 T7）；地面弧与辉光弧是**预烘焙色带图**（弯曲 + 辉光，程序化难做且层次多） |

#### 建议保留程序化（B）—— 程序化已足够好，且省体积省生产 —— **7 大类**

| # | 资产类 | 为何保留程序化 | 判据 |
|---|---|---|---|
| 1 | **天空色带（8 条）** | 纯色矩形即最优解：**零加载、零纹理内存、改色零成本**；TileSprite 反而多 2 draw call + 纹理 | 本质是"两色纯填充"，位图化无增益 |
| 2 | **星图** | 单个 `Graphics` 已达标；512² 贴图要额外 1 MB 纹理内存 | 除非要做星点闪烁 / 视差 |
| 3 | **云** | 硬边椭圆 = 图元；程序化 + 视差系数已达标 | 形状简单、需随高度整体下沉 |
| 4 | **地面 / 发射台 / 塔架 / 储罐 / 方舱** | 纯色矩形 + 1–2px 线段，程序化**更锐利**（不受纹理采样影响） | 平色 + 直线，位图化反引入采样模糊 |
| 5 | **HUD 面板 / 角标 / 刻度 / 仪表 / 分段进度条** | 1px 描边 + 分段矩形，程序化锐利且**必须随数值动态变化** | 动态量，位图只能做静态底框 |
| 6 | **示教线 / 参考指针 / 目标线 / 导向线** | 需随 sim 实时变化（参考弹道、目标高度线） | 动态量 |
| 7 | **去饱和覆盖层 / 远山剪影 / 人影** | 单色低 alpha 矩形 / 三角剪影 | 无需 authored 细节 |

#### 判断总纲（一句话）

> **"有有机硬边形状、需烘焙色阶、或被引擎强绑定（粒子必须吃纹理）" → 资产化；**
> **"平色 + 直线 + 需随数值动态变化 + 体积敏感" → 保留程序化。**

**比例结论**：必须资产化 **6 大类 ≈ 107 个位图文件**；建议保留程序化 **7 大类 ≈ 42 个渲染系统**。
**⚠️ 不为"完整"而全量资产化** —— 程序化在网页 2D 的**体积 / 加载 / 动态性**上有真实优势，盲目位图化会同时增加体积、纹理内存与生产工时，却拿不到品质增益。

## §7 性能配合规格（资产侧硬数字）

> 三条红线（美术 §6.0，桌面）：**活跃粒子 ≤ 420 ｜ Draw call ≤ 90 ｜ 纹理内存 ≤ 48MB**。以下为资产侧的具体配合方式。

### 7.1 配合「≤ 420 活跃粒子」

**粒子预算（发射器清单，桌面峰值）**：

| 发射器 | 触发段 | `maxParticles` | 贴图 | 说明 |
|---|---|---|---|---|
| 烟 · 地面横向卷云 | T-0 → T+1.5s | 20 | `fx_smoke_puff_*` | 3 个宽椭圆贴地铺开（美术 §4.3） |
| 烟 · 尾迹 | T+1.2s → 塔架脱离 | 60 | `fx_smoke_puff_*` | 存活 1.2s |
| 余烬 · 失败 | 爆炸 0→0.4s | 30 | `fx_ember` | 仅失败态 |
| **峰值合计** | — | **≤ 110** | — | 远低于 420 红线；**留足 headroom 给烟雾叠加** |
| 火焰 | 全程 | **0** | — | 火焰**不进粒子系统**，走 sprite 序列（T1 反堆砌） |

**熔断要求**（美术 §10.4）：每个 emitter 设 `maxParticles` **+** 全局粒子计数器在 `update()` 做总数熔断——**单靠各 emitter 加不满时仍可能破线**。
**验收判据（T1）**：关掉全部粒子系统后，点火/爆炸仍成立（因为主力是 sprite 序列与硬边形体）。

### 7.2 配合「≤ 90 draw call」

| 手段 | 具体做法 | 预估节省 |
|---|---|---|
| **图集合并** | 火箭 / 图标 / VFX 各进 1 张图集 → 同图集元素批处理 | 把 ~40 个独立纹理降到 4–5 张 |
| **⚠️ 合并云层** | 现实现 12 个独立 `Graphics` 云 = **12 draw call**，应合并进 **1 个** `Graphics` | −11 |
| **⚠️ 遥测文字批处理** | 现 HUD ~30 个 `Text` 对象 = 每串一个新纹理 = **~30 draw call**。**改用位图字体 / 数字图集**渲染数值 | −20 以上 |
| **静态 HUD 合批** | 现 HUD 有 5 面板各带独立角标 `Graphics` + 1 静态 `Graphics`；合并为 1 个 | −5 |
| **星空** | 现为单 `Graphics`（好）；若转 A 版则 1 张 `TileSprite`（更好） | 持平 |
| **天空** | 2 个矩形（同纹理批处理）或 2 个 `TileSprite` | 2 |

**预估 draw call 剖面**：World ≈ 12（合并云后）+ 8 = 20；HUD ≈ 8（合并后）+ 位图字体 3 = 11；合计 **≈ 31**，**桌面 ≤90 / 移动 ≤70 均达标**。**最大隐患是文字对象数量**，务必用位图字体。

### 7.3 配合「≤ 48MB 纹理内存」——含一处必须改规格的硬发现

> **⚠️ 硬发现**：美术圣经 §10.2 要求"出 @1x + @2x，3 张图集"，§6.0 要求纹理 ≤48MB。但**3 张 2048×2048 的 RGBA8 图集单独就是 3 × 16.78MB = 50.3MB**，**在放任何独立纹理（星空/地面弧/火焰）之前就已经破线**。因此**"全 @2x + 三张 2048 图集"的组合在数学上不成立**。

**重算后的推荐分配（桌面 · RGBA8 未压缩 GPU 内存）**：

| # | 资源 | 规格 | 单张 | 张数 | 小计 |
|---|---|---|---|---|---|
| 1 | `atlas_core_2048_2x` | 2048 × 2048 | 16.78 MB | 1 | **16.78 MB** |
| 2 | `sheet_flame_1024x2048_1x` | 1024 × 2048 | 8.39 MB | 1 | **8.39 MB** |
| 3 | `atlas_ui_1024_1x` | 1024 × 1024 | 4.19 MB | 1 | **4.19 MB** |
| 4 | `atlas_fx_1024_1x` | 1024 × 1024 | 4.19 MB | 1 | **4.19 MB** |
| 5 | `sc_arc_ground_g0..g3` | 1920 × 240 | 1.84 MB | 4 | **7.37 MB** |
| 6 | `bg_starmap` | 512 × 512 | 1.05 MB | 1 | **1.05 MB** |
| 7 | 天空色带（若 A 版） | 8 × 512 | 16 KB | 8 | **0.13 MB** |
| 8 | 地球辉光弧 | 1920 × 64 | 0.49 MB | 4 | **1.97 MB** |
| 9 | 噪点 + 位图数字 + 字体（字体走 DOM 不计显存） | — | — | — | **≈ 0.1 MB** |
| | **合计** | | | | **≈ 44.2 MB** ✅ |

**✅ 主理人已批准本重算方案**（火焰仅 @1x + 图集 1×2048 + 2×1024 = 44.2 MB）。以下为**推导算式**——**后续任何人增删资产请复用此式，勿凭感觉估算**：

```
纹理内存(MB) = Σ [ 宽(px) × 高(px) × 4 B/px(RGBA8) ] ÷ 1024²
────────────────────────────────────────────────
单个 2048² 图集 = 2048 × 2048 × 4 = 16,777,216 B = 16.78 MB
单个 1024² 图集 = 1024 × 1024 × 4 =  4,194,304 B =  4.19 MB
单个  512² 贴图 =  512 ×  512 × 4 =  1,048,576 B =  1.05 MB
火焰 30 帧 @1x（每帧 ≤ 256×640）≈ 30 × 0.63 MB ≈ 19 MB  → trim 后打进 1024×2048 sheet = 8.39 MB
火焰 30 帧 @2x（每帧 ≤ 512×1280）≈ 30 × 2.50 MB ≈ 75 MB  ← 单此项即超 48 MB 红线
```

**关键降规格决策（3 条，均已批准）**：
1. **火焰只出 @1x**（美术 §10.2 要求双套）——火焰 30 帧若 @2x 即 ≈ 75 MB，击穿红线。**@1x 火焰在 zoom 0.5 时采样比 0.5 < 1 略糊，但火焰是软边特效，可接受。**
2. **地面弧只出 @1x**（美术 RA-3 已认可）。
3. **三张 2048 图集降为「1×2048 + 2×1024」**，且只有 `atlas_core` 出 @2x。

> ### ⚠️ 红线警告（显式，必读）
> **本方案下，若未来给火焰补 @2x，纹理内存会从 ≈ 44.2 MB 立即跳到 ≈ 100 MB，48 MB 红线当场破裂。**
> **任何"给火焰补 @2x"的提案，必须先解决压缩纹理（KTX2/Basis）或明确削减其他资产，不得直接加。**

> **若坚持全 @2x**：须改用 **KTX2 / Basis 压缩纹理**（WebGL 支持，可将 RGBA8 压 4:1–6:1），需引擎侧确认 Phaser 纹理管线支持（**交程基岩评估**）。否则只能在"@2x 覆盖率"与"48 MB 红线"之间二选一。

### 7.4 配合加载阶段与首屏包（≤1.2MB 首屏）

| 阶段 | 内容 | 预算 |
|---|---|---|
| `boot` | Logo + 进度条 | < 200KB |
| `core` | 火箭 + 发射场 + UI + 火焰 atmo 组 | < 1.0MB |
| `orbit` | 星空 + 地面弧 + 辉光弧 + 火焰 vac 组（**升空时后台预载**） | < 2.3MB |

- 全部位图走 **WebP q=82**（纯色 UI 走 PNG-8）；构建期压缩，源文件不进包。
- 字体 **≤120KB**，`font-display: swap` + 位图数字顶位 → **首屏不因字体阻塞**。
- **首屏包红线口径（主理人已裁决 · 对齐工程侧）**：**以 gzip / brotli 传输体积为准**，**raw 不计红线**（网页实际加载的是压缩后体积）。实测 **gzip 340.5 KB / brotli 273.3 KB，均通过**（raw 1.229 MB 不计入）。
- **由此释放的预算**：位图与音频按 **gzip ≤ 1.2 MB** 核算（当前 Phaser + 自研源码 gzip = 340.5 KB，余量 **≈ 860 KB** 给位图 / 音频 / 字体）。**⚠️ 注意**：WebP / woff2 / 音频本身已是压缩格式，其二次 gzip 增益有限 —— **须按"已压缩体积"直接计入 gzip 口径**，不要按 raw 估。

## §8 生产风险与交接

**纹理内存红线与"双套 @2x + 三张 2048 图集"的原始规划在数学上不相容**（§7.3）。**已通过"火焰仅 @1x + 图集 1×2048+2×1024"裁决缓解**（44.2 MB ✅），但**生产期必须守住"火焰不加 @2x"** —— 这是唯一的红线单点（一加即 ≈100 MB）。
