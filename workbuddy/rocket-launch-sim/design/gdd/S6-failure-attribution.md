## 1. 系统职责与支柱挂靠

### 1.1 一句话职责

> **让每一次爆炸都带着一句话："你错在 X 时刻的 Y 数值上，差了 Z。"** S6 拥有全部失败码、归因数据管线与失败演出时序。

### 1.2 支柱闸门校验

| 支柱 | 本系统如何服务 | 判定 |
|---|---|---|
| **P1 · 过程即内容** | 失败不是"黑屏 + 重来"，而是**有 1.7 s 演出 + 一段可交互的数据复盘**的时间段。玩家在这段时间里仍然在操作（读取、翻页），不是在看动画 | ✅ 挂靠 |
| **P2 · 可解读的深度** | **本系统是 P2 的第二验收点**（第一是 S7 的 Ω）。每一次失败必须给出**带时刻、带数值、带差值**的归因，而非"任务失败" | ✅ 挂靠（主载体） |
| **P3 · 一次发射，六十秒** | 失败支路同样受 3 s 重开硬上限约束（概念 §6.2）。失败演出总长 **1.70 s**，归因面板停留由玩家控制，**"可再次操作"的时间点 ≤ 失败后 3.0 s** | ✅ 挂靠 |
| **P4 · 失败也好看** | **本系统是 P4 的唯一载体。** 爆炸演出、残骸物理、失败数据回放的全部规格在此 | ✅ 挂靠（唯一载体） |

**闸门结论：S6 挂靠全部四根支柱，且是 P4 的唯一载体。**

### 1.3 明确不属于 S6

- 失败码的**产生**（`q > Q_STRUCT` 等判据）→ 由 S1/S3/S4 判定并抛出，S6 只消费
- 失败演出的美术资产实现 → 美术 §6.7
- 成功流程的结算 → S5

## 2. 核心状态与数据结构

### 2.1 失败码枚举

```ts
export const FailureCode = Object.freeze({
  // ── 结构 / 气动 ──
  DESTRUCT_AERO:  'DESTRUCT_AERO',   // 动压超结构极限，气动解体
  DESTRUCT_ALPHA: 'DESTRUCT_ALPHA',  // 攻角 × 动压超限，箭体折断
  TUMBLE:         'TUMBLE',          // 姿态失控翻滚
  SEP_HIGHQ:      'SEP_HIGHQ',       // 高动压分离，级间碰撞

  // ── 轨迹 ──
  IMPACT:         'IMPACT',          // 撞地（含坠海）
  INSUFFICIENT_DV:'INSUFFICIENT_DV', // 燃料耗尽但未达入轨门槛
  ESCAPE_TRAJ:    'ESCAPE_TRAJ',     // 速度超过逃逸速度，甩出引力场

  // ── 序列 / 玩家主动 ──
  SEQUENCE_FAULT: 'SEQUENCE_FAULT',  // 发射序列故障（S2 的 HOLD 超时）
  ABORT:          'ABORT',           // 玩家主动中止（V5）
});
```

### 2.2 归因数据结构

```ts
interface FailureRecord {
  code:         FailureCode;
  t:            number;      // 失败时刻 s
  primary:      string;      // 主因一句话（带数值，见 §3.3）
  evidence:     Evidence[];  // 证据链（2–4 条，每条含时刻 + 量名 + 数值 + 单位）
  fixHint:      string;      // 一句可执行的改进建议（**禁止给最优解**）
  peak:         PeakSnapshot;// 关键极值快照
}

interface Evidence {
  t:     number;   // s
  label: string;   // 量名（中文 + 英文缩写）
  value: number;   // 数值
  unit:  string;   // 单位
  verdict: 'OK' | 'WARN' | 'BAD';   // 该证据的判定
}

interface PeakSnapshot {
  maxQ:      number;   // 峰值动压 Pa
  tMaxQ:     number;   // s
  maxAlpha:  number;   // 峰值攻角 rad
  hMax:      number;   // 最高高度 m
  vMax:      number;   // 最大速度 m/s
  periBest:  number;   // 全程最佳近地点 m
  tPeriBest: number;   // s
  dvLoss:    number;   // Δv 总损失 m/s
}
```

### 2.3 常量

| 常量 | 值 | 量纲 | 说明 |
|---|---|---|---|
| `T_EXPLOSION` | 1.70 | s | 失败演出总时长（美术 §6.7） |
| `T_SILENCE` | 0.60 | s | 演出中的静默段（0.50 → 1.10 s） |
| `T_PANEL` | 1.70 | s | 归因面板弹出时刻（= 演出结束） |
| `T_RETRY_MAX` | 3.00 | s | **从失败到"可再次操作"的硬上限**（P3 红线） |
| `MAX_EVIDENCE` | 4 | 条 | 单次归因的证据条数上限（认知过载红线） |

## 3. 规则与公式

### 3.1 失败检测（S6 消费其他系统抛出的码）

| 失败码 | 判据 | 抛出方 | 检测时机 |
|---|---|---|---|
| `DESTRUCT_AERO` | `q > Q_STRUCT (30 kPa)` | S4 | 每帧 |
| `DESTRUCT_ALPHA` | `\|alpha\| > 0.35 rad` **且** `q > 30 kPa` | S1 §6.5 | 每帧 |
| `TUMBLE` | `\|alpha\| > 1.05 rad (60°)` 持续 1.0 s | S1 | 每帧 |
| `SEP_HIGHQ` | 分离瞬间 `qSep > Q_SEP_SAFE (5 kPa)`（阈值由 S3 拥有；S3 §9-C6 提议上调至 8 kPa，待裁决） | S3 §3.4 | 分离事件 |
| `IMPACT` | `h ≤ 0` 且 `t > 1 s` | S1 §6.6 | 每帧 |
| `INSUFFICIENT_DV` | SECO 或主动关机时 `!isOrbital` | S5 §3.2 | 判定时刻 |
| `ESCAPE_TRAJ` | 判定时 `regime === ESCAPE` | S5 | 判定时刻 |
| `SEQUENCE_FAULT` | S2 的 HOLD 持续 > 3 s | S2 §6.3 | 序列更新 |
| `ABORT` | 玩家按 `Esc`（`phase ∈ {RELEASE, FLIGHT}`） | S2 §3.5 | 输入 |

> **优先级**：同一帧多个码同时满足时，按上表**从上到下**取第一个。`DESTRUCT_*` 优先于 `IMPACT`（解体后才撞地，死因应是解体）。

### 3.2 归因管线（三步）

```
① 采集：PeakSnapshot 在飞行全程逐帧累积（maxQ / maxAlpha / hMax / vMax / periBest ...）
② 选主因：按失败码查「归因模板表」（§3.3），填入实测数值
③ 选证据：从候选证据池中按「最能解释本次失败」排序，取前 MAX_EVIDENCE 条
```

**证据排序规则**（确定性，不含随机）：
1. `verdict === 'BAD'` 的证据优先
2. 同为 BAD 时，按「该证据数值与门槛的相对偏离」降序：`|value − threshold| / threshold`
3. 同分时按时间戳升序（早发生的更能解释根因）

### 3.3 归因模板表（**本系统的核心交付物**）

> 每条模板的 `{占位符}` 由运行时填入实测值。**文案的硬性要求**：必须同时包含 **① 时刻 ② 量名 ③ 实测值 ④ 差多少** 四类信息中的至少三类。

| 失败码 | 主因文案模板 | 改进建议模板 |
|---|---|---|
| `DESTRUCT_AERO` | 你在 **T+{t}s / 高度 {h} km** 承受了 **{q} kPa** 动压，超过结构极限 **30 kPa** 达 **{q−30} kPa**。 | 动压 = ½·空气密度·速度²。爬升更快（更高处空气更稀薄）或提前收油门都能压低峰值。 |
| `DESTRUCT_ALPHA` | 你在 **T+{t}s** 以 **{alphaDeg}°** 攻角、在 **{q} kPa** 动压下飞行——箭体被侧向气流折断了。 | 攻角 = 箭体指向与飞行方向的夹角。让箭体顺着速度矢量走。 |
| `TUMBLE` | 你在 **T+{t}s** 失去姿态控制，箭体以 **{alphaDeg}°** 攻角翻滚了 **1.0 s**。 | 低空空气会自行把箭体摆正，高空不会。别在高空做大角度配平。 |
| `SEP_HIGHQ` | 你在 **T+{t}s / 动压 {qSep} kPa** 时分离——上级撞上了自己的一级。安全分离需低于 **5 kPa**。 | 动压在 **T+40 s** 后降到 5 kPa 以下。别急着按 SHIFT。 |
| `IMPACT` | 火箭在 **T+{t}s** 撞回地面。最高只到 **{hMax} km**，最大水平速度 **{vhMax} m/s**（圆轨道需要 **1512 m/s**）。 | 水平速度不够，重力就会把你拉回来。更早、更彻底地把速度矢量压向水平。 |
| `INSUFFICIENT_DV` | 燃料耗尽于 **T+{t}s**，近地点只有 **{peri} km**，距入轨门槛 **13.5 km** 还差 **{13.5−peri} km**。<br>Δv 总损失 **{dvLoss} m/s**（基准弹道 548 m/s）。 | Δv 损失来自重力、转向和空气阻力三项。检查你的峰值攻角（{maxAlphaDeg}°）与峰值动压（{qMax} kPa）。 |
| `ESCAPE_TRAJ` | 关机速度 **{v} m/s** 已超过逃逸速度 **2138 m/s** —— 你把自己甩出了引力场。 | 目标圆轨道速度是 1512 m/s。你给多了 {v−1512} m/s。 |
| `SEQUENCE_FAULT` | 发射序列在 T-0 挂起超过 3 秒：{blockedItem} 未完成。 | 这是系统故障，不是你的操作问题。重开即可。 |
| `ABORT` | 你在 **T+{t}s / 高度 {h} km** 手动中止了任务。乘员舱已安全弹离。 | — |

### 3.6 3 秒重开红线（P3）

```
t_failure        → 失败发生，演出开始
t_failure + 1.70 → 归因面板弹出，玩家可读取
t_failure + 3.00 → 硬上限：此刻必须已可再次操作（无论玩家是否读完）
```

**实现要求**：
- 归因面板**不阻塞**重开：面板弹出的同时 `R` 键即生效。
- 若玩家在 3.0 s 内未按 `R`，面板**保持显示**（不自动关闭、不自动重开）——**尊重玩家的阅读节奏**，但保证"想快就能快"。
- 演出阶段（0 → 1.70 s）**不可跳过**。理由：这是 P4 的兑现，跳过等于砍掉失败的价值。**但 1.70 s 已远小于 3.0 s 上限。**

### 3.7 中止（ABORT）的特殊处理

`ABORT` 是**玩家主动**的，不是失误。因此：
- **不播放爆炸演出**（火箭没炸，乘员舱弹离了）
- 播放**逃逸塔点火**演出（概念 §4.1 V5：逃逸塔点火、乘员舱弹离、警示灯全亮）
- 归因文案用中性措辞（§3.3 已体现），**不计入失败统计**（S8）
- 演出时长 **1.20 s**（比爆炸短），之后弹归因面板

## 4. 玩家输入映射（键鼠）

| 输入 | 时机 | 行为 |
|---|---|---|
| **`Esc`** | `RELEASE` / `FLIGHT` | 触发 `ABORT`（V5） |
| **`R`** | 归因面板显示后 | 重开，回到 S2 的 `IDLE` |
| **`←` / `→`** | 归因面板显示后 | 在多页归因之间翻页（MVP 内仅 1 页，**预留交互位**） |
| **`Space`** | 归因面板显示后 | 等同于 `R`（重开）——降低"找键"成本，符合 P3 |

### 4.1 输入细则

1. **演出期间锁定输入**（0 → 1.70 s）：`Esc` / `R` / `Space` 全部无效，防止玩家在爆炸中误触重开，把演出砍成 0.2 s。
2. **面板期全键可用**：`R` / `Space` 重开；`Esc` 返回主菜单（MVP 内主菜单极简，等价于重开）。
3. **去抖**：重开键 200 ms 去抖，防连按导致连续跳过两局的归因。
4. **可重映射**：同其他动词（美术 §9.4）。

## 6. 边缘情况（≥3 条，含数值退化与除零防护）

### 6.1 `INSUFFICIENT_DV` 的差值可能为负 / 极小

`13.5 − peri`，若 `peri = 13.4999 km` ⇒ 差值 = `0.0001 km = 0.1 m`。文案显示"还差 0.1 km"会显得荒谬（玩家会觉得系统在嘲讽）。

**防护**：差值小于 100 m 时改用**百分比表述**：
```
gap = H_PASS − periapsis
文案 = (gap > 100) ? `还差 ${(gap/1000).toFixed(2)} km`
     : (gap > 0)   ? `还差 ${gap.toFixed(0)} m —— 就差一点点`
     : `已达标`
```
且 `gap ≤ 0` 时不得走 `INSUFFICIENT_DV` 分支（那是 S5 的判定逻辑，S6 只消费结果）。

### 6.2 `ESCAPE_TRAJ` 的 `apoapsis = Infinity` 显示

`远地点 ∞` 必须走特殊字形。见 S5 §6.7。**S6 的证据链中若含 `∞`，该条证据的 `value` 字段设为 `Number.POSITIVE_INFINITY` 并标记 `renderAs: 'INFINITY'`，由 S7 决定字形。**

### 6.3 归因模板的除零：`(q − 30) / 30` 等相对偏离

若 `q = 0`（真空段失败，如 `INSUFFICIENT_DV`），相对偏离计算 `|0 − 30|/30 = 1` 安全。
但**证据排序**中的 `|value − threshold| / threshold` 在 `threshold = 0` 时除零。

**防护**：
```
rel = (threshold === 0) ? (value === 0 ? 0 : Infinity)
                        : Math.abs(value − threshold) / Math.abs(threshold);
rel = Number.isFinite(rel) ? rel : 0;
```

### 6.4 `PeakSnapshot` 在极短局（T+1 s 内失败）的空值

若玩家在 T+0.5 s 就按 `Esc`（ABORT），`maxQ = 0`、`hMax ≈ 0`、`vMax ≈ 0`。模板填入全零会产生"你在 T+0.5s 撞回地面，最高只到 0.00 km"的荒谬文案。

**防护**：ABORT 的模板**不使用** `hMax` / `vMax` 的对比句式（§3.3 已如此设计）；且所有数值经过 `formatForDisplay()`，对 `|x| < 1e-3` 显示 `0` 而非 `0.000`。

### 6.5 同一失败码连续出现多次（玩家反复犯同一个错）

**不合并、不省略**。每一次都完整播放演出与归因。

**但**：S8 的档案室会记录失败码的分布，若同一码连续 5 次 ⇒ 归因面板追加一行 `这是你连续第 N 次因此失败` 的提示（中性措辞，不含嘲讽）。这是 P2 的延伸服务，不是惩罚。

### 6.6 失败演出的对象清理

爆炸碎片 8–14 个 sprite + 3 个烟环 + 30 个余烬粒子，若在重开时未清理，会累积泄漏。

**防护**：`reset()` 无条件清空所有碎片/粒子池，并把活跃粒子计数器归零（美术 §10.4 要求做全局粒子计数熔断）。

**验收**：连续失败并重开 20 次，活跃粒子总数恒定 ≤ 420（桌面）。

### 6.7 失败发生在大气顶之上（真空解体）

真空中 `q = 0`，因此 `DESTRUCT_AERO` **不可能**在真空触发。真空段的失败只能是 `INSUFFICIENT_DV` / `ESCAPE_TRAJ` / `TUMBLE`。

**真空解体的表现差异**：碎片在真空中**无烟环**（物理正确：真空里没有空气形成烟环）。S6 需检测 `h > ATM_TOP` 并跳过烟环生成。

## 9. 冲突与待裁决项

### C10【中】概念 §6.2 写「失败支路单次循环时长 20–50 秒」，与 P3 的 3 秒重开存在表述冲突

概念 §6.2：「单次循环时长：60–90 秒（成功）／ **20–50 秒（失败）**」。
概念 §6.2 同一节：「重开成本：从失败演出结束到玩家可再次操作，硬上限 **3 秒**」。

**这两句在字面上自相矛盾**：若失败循环是 20–50 s，则"重开成本 3 s"指的只是演出结束到可操作的间隙，而不是循环总长。我按后者理解（3 s 是硬约束，20–50 s 是"玩家愿意读完归因再重开"的典型时长）。

**建议**：把概念 §6.2 的第一句改为「单次循环时长：78–90 秒（成功）／ **5–50 秒（失败，下限受 3 秒重开红线约束，上限由玩家阅读归因的时长决定）**」，消除歧义。

### 补充：MVP 内未实现的失败模式（明确记录，防后期误纳入）

以下真实火箭的失败模式**明确不在 MVP 内**，S6 不得为其预留分支：

- 发动机熄火 / 推力室故障（无随机故障系统）
- 推进剂耗尽导致的泵气蚀
- 热防护失效 / 再入烧毁（无气动加热模型，见 S4 §1.3）
- 结构疲劳累积（无连续应力模型，见 S1 §6.5）
- 发射台爆炸（S2 的 `IGNITION` 段不建模故障）

> **理由**：这些都需要**随机性或连续状态模型**，而 MVP 的失败必须**完全由玩家操作决定**（P2「可归因」的前提）。引入随机故障会直接击穿 P2——玩家无法从"运气不好"中学到任何东西。
