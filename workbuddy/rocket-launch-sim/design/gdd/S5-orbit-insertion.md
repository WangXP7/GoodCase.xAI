## 1. 系统职责与支柱挂靠

### 1.1 一句话职责

> **在飞行结束的那一帧给出一个不可争议的成功/失败判定，并把"你飞得有多好"翻译成三个可比较的数字。**

### 1.2 支柱闸门校验

| 支柱 | 本系统如何服务 | 判定 |
|---|---|---|
| **P1 · 过程即内容** | 入轨判定**不是结算画面上的一个结论**，而是全程逐帧解算、实时可视（S7 的模态 B 双游标）。玩家在飞行中就在"看着近地点爬过目标线" | ✅ 挂靠 |
| **P2 · 可解读的深度** | **本系统是 P2 的验收点。** 判定门槛（近地点 ≥ 13.5 km）与三档评级标准**全部明示给玩家**（概念 §5.1 胜任保障 1：「评级标准明示，不是黑箱」） | ✅ 挂靠（主载体） |
| **P3 · 一次发射，六十秒** | 判定时机决定单局终点。S5 支持**主动提前关机**——这是 60 s 打法的实现前提 | ✅ 挂靠 |
| **P4 · 失败也好看** | 判定的**否定分支**直接产出 S6 的归因数据（差多少 m/s、差多少 km、差在哪个时刻） | ✅ 挂靠 |

**闸门结论：S5 挂靠全部四根支柱。**

### 1.3 明确不属于 S5

- 轨道根数解算算法本身 → `src/core/orbit/OrbitSolver.ts`（规格见 `tests/c1/orbit-solver.ref.mjs`，性能已由 C1 验证：58 ns/次）
- 失败演出的画面实现 → S6
- 跨局趋势与解锁 → S8

## 2. 核心状态与数据结构

### 2.1 判定常量

| 常量 | 值 | 量纲 | 推导 / 依据 |
|---|---|---|---|
| `H` | 15000 | m | 目标轨道高度（RT-1） |
| `H_PASS` | 13500 | m | **入轨门槛** = 0.9·H（RT-1 §4 采用同一门槛） |
| `H_PREC` | 750 | m | **精确入轨容差** = 0.05·H（`\|h_p − H\| ≤ 750 m`） |
| `V_C` | 1512 | m/s | 目标高度圆轨道速度 |
| `V_ESC` | 2138 | m/s | 逃逸速度 |
| `T_SHUTDOWN_HOLD` | 1.0 | s | 主动关机的确认保持时长 |
| `T_SILENCE` | 0.8 | s | 关机后静默时长（美术 §6.6） |

### 2.2 运行时状态

```ts
interface OrbitState {
  // ── 逐帧解算结果（缓存，供 S7 读取）──
  regime:     Regime;      // ELLIPTIC | CIRCULAR | ESCAPE | SUBORBITAL | DEGENERATE
  periapsis:  number;      // 近地点高度 m（可为负，HUD 层才夹紧）
  apoapsis:   number;      // 远地点高度 m（ESCAPE 时为 Infinity）
  e:          number;      // 离心率
  a:          number;      // 半长轴 m
  valid:      boolean;     // 本帧解算是否有效（DEGENERATE ⇒ false，沿用上帧）

  // ── 判定 ──
  judged:       boolean;   // 是否已判定
  tJudge:       number;    // 判定时刻 s
  judgement:    'INCOMPLETE' | 'ORBITAL' | 'PRECISE';
  shutdownHold: number;    // 主动关机的已保持时长 s

  // ── 结算数据 ──
  accuracyM:    number;    // 入轨精度偏差 m = periapsis − H
  dvRemain:     number;    // Δv 余量 m/s（剩余推进剂 Δv）
  dvSpent:      number;    // 已消耗 Δv m/s
  dvLoss:       number;    // Δv 总损失 m/s = dvSpent − v
  fuelRemainKg: number;    // 剩余燃料 kg
  flightTime:   number;    // 局内时长 s
}
```

### 2.3 评级枚举

```ts
export const Judgement = Object.freeze({
  INCOMPLETE: 'INCOMPLETE',   // 未入轨
  ORBITAL:    'ORBITAL',      // 入轨
  PRECISE:    'PRECISE',      // 精确入轨（最高档）
});
```

## 3. 规则与公式

### 3.1 轨道解算调用

**每个物理步（120 Hz）调用一次 `solveOrbit(rx, ry, vx, vy, {mu, R}, out)`，结果缓存；S7 在渲染帧读缓存。**

- 性能：RT-1 实测 58 ns/次 ⇒ 120 Hz 下年占帧预算 **0.0007%**，可忽略。
- **必须复用输出对象**（`out` 参数），避免热路径分配（orbit-solver.ref.mjs 已按此设计）。

### 3.2 入轨判定（三个条件同时满足）

```
isOrbital = (regime === ELLIPTIC || regime === CIRCULAR)
         && periapsis >= H_PASS           // 13.5 km
         && Number.isFinite(apoapsis)     // 排除 ESCAPE（远地点 Infinity）
```

| 条件 | 为什么必须独立存在 |
|---|---|
| `regime ∈ {ELLIPTIC, CIRCULAR}` | 排除 SUBORBITAL（近地点在地下）与 DEGENERATE |
| `periapsis ≥ 13.5 km` | 与 `regime` 冗余但**不可省**：`regime` 只判 `r_p ≥ R`（近地点 ≥ 0 km），而入轨要求近地点 ≥ 13.5 km。**这是两个不同的门** |
| `apoapsis` 有限 | **RT-1 诊断 ③的直接教训**：v1 扫描把 `ESCAPE`（远地点 Infinity）误判为入轨。此条件必须显式保留 |

### 3.3 判定触发时机（三种）

| # | 触发条件 | 行为 |
|---|---|---|
| **① SECO** | `stage === 2 && fuel2 <= 0` | 立即判定 |
| **② 主动关机** | `throttle ≤ 0.30`（节流下限，等效熄火）持续 `T_SHUTDOWN_HOLD = 1.0 s` | 判定。**这是 60 s 打法的实现前提** |
| **③ 失败** | S6 抛出任意失败码 | 不判定，直接走失败流程 |

> **为什么主动关机需要 1.0 s 保持**：节流下限是 0.30（不是 0），所以"收油门到底"不等于关机。1.0 s 的保持窗口防止玩家在末段微调节流时误触发判定。S7 在此期间显示 `SHUTDOWN ...` 进度提示。

**判定后的时序**（对齐美术 §6.6）：
```
t = tJudge          物理冻结，尾焰 0.6 s 熄灭
t + 0.6 → t + 1.4   画面完全静止 0.8 s（静默）
t + 1.4             弹出结算面板
```

### 3.4 三档评级

```
INCOMPLETE : !isOrbital
ORBITAL    : isOrbital && |periapsis − H| >  H_PREC
PRECISE    : isOrbital && |periapsis − H| <= H_PREC      // |h_p − 15000| ≤ 750 m
```

**即：`PRECISE` 要求近地点落在 [14.25, 15.75] km。**

#### 3.4.1 评级门槛的标定依据（用 RT-1 §5 的 7 条弹道交叉验证）

| 路线 | hTurn% | 近地点 (km) | `\|h_p − H\|` (m) | 评级 | 时长 s |
|---|---|---|---|---|---|
| 低抛 A | 35 | 13.51 | 1490 | **ORBITAL** | 81.0 |
| 低抛 B | 40 | 14.22 | 780 | **ORBITAL**（差 30 m） | 81.0 |
| 低抛 C | 45 | 14.73 | 270 | **PRECISE** ✅ | 81.0 |
| **基准** | **50** | **15.09** | **90** | **PRECISE** ✅ | 81.0 |
| 高抛 A | 60 | 15.54 | 540 | **PRECISE** ✅ | 81.0 |
| 高抛 B | 70 | 15.42 | 420 | **PRECISE** ✅ | 81.0 |
| 高抛 C | 85 | 14.69 | 310 | **PRECISE** ✅ | 81.0 |

> **防主导策略校验（设计理论红线）**：
> - `PRECISE` 覆盖 **hTurn ∈ [45%, 85%]** 共 5 条路线，**低抛侧与高抛侧各有代表**，不存在"某一侧全对"的偏向 ✅
> - `ORBITAL` 覆盖两端（35%、40%）。低抛极端打法**能入轨但不精确**——这是合理的取舍：省油（Δv 损失 531 vs 603）换精度，**两个方向各有代价，不是"哪条都行"** ✅
> - **7 条全部入轨**（RT-1 §5 已验证），说明入轨门槛不过紧；**只有 5 条 PRECISE**，说明最高档有真实区分度 ✅

#### 3.4.2 为什么最高档用「精度」而不是「Δv 余量」门控

> **这是一个刻意的反主导策略决策，必须记录。**

若用「Δv 损失 ≤ 560 m/s」作为最高档门控，7 条弹道的结果是：低抛 A/B/C（531/537/543）+ 基准（548）共 4 条达标，高抛 A/B/C（571/589/603）**全部落榜**。

**这会造成主导策略**：低抛侧在全部门槛下都优于高抛侧，玩家的最优解坍缩为"永远尽早倾倒"，概念 §5.1 的自主性保障 2（「低抛与高抛都应可通关，杜绝主导策略」）被直接击穿。

改用**精度**门控后，最优区落在 **hTurn ∈ [45%, 85%]** 的内部区间，两端各有代价，且 Δv 损失仍作为**独立的结算数据**呈现给 Achiever 型玩家（概念 §5.3：「追求最少燃料入轨」）作为自我挑战目标——**它不门控评级，因此不制造主导策略。**

### 3.5 结算三项数据（概念 §5.1 胜任保障 3）

| # | 数据 | 公式 | 单位 | 基准弹道值 |
|---|---|---|---|---|
| 1 | **入轨精度** | `accuracyM = periapsis − H` | m | **+90 m** |
| 2 | **Δv 余量** | `dvRemain = ISP_G0 · ln(m / m_dryPath)`（见 S1 §3.2-⑥） | m/s | **0**（烧满） |
| 3 | **燃料剩余** | `fuelRemainKg = fuel1 + fuel2` | kg | **0** |

> **诚实记录：第 2、3 项在固定构型下单调相关。**
> `dvRemain = 2900 · ln((m_dry + fuelRemain) / m_dry)`，二者一一对应，第 3 项对第 2 项**无额外信息量**。
> 保留两者的唯一理由是概念 §5.1 已向玩家承诺"三项数据"，且 kg 对非硬核玩家比 m/s 更直观。**S7 应把两者并排显示为同一数据卡的两种单位，而不是两个独立卡片**，以控制信息密度。

### 3.6 补充指标（不计入评级，供 Achiever 自我挑战）

| 指标 | 公式 | 基准值 | 说明 |
|---|---|---|---|
| **单局时长** | `tJudge` | 81.0 s | P3 的技能信号 |
| **Δv 总损失** | `dvLoss = dvSpent − v` | 548 m/s | 重力 + 转向 + 气动损失之和 |
| **远地点** | `apoapsis` | 8746 km | 越大说明 Δv 越过剩 |

### 3.7 「60 秒打法」的实现路径（概念 §5.2 的兑现）

**提前关机是缩短单局的唯一手段**，其代价链条如下（基准弹道逐秒数据）：

| 关机时刻 | 近地点 (km) | Δv 余量 (m/s) | 局时 (s) | 评级 |
|---|---|---|---|---|
| T+76 | 11.94 | 229 | 76 | **INCOMPLETE** |
| T+78 | **13.50** | **151** | 78 | **ORBITAL**（刚好过门） |
| T+79 | 14.10 | 101 | 79 | **ORBITAL** |
| T+80 | 14.62 | 51 | 80 | **PRECISE** ✅ |
| T+81 | 15.09 | 0 | 81 | **PRECISE** ✅ |

> **读取方式**：
> - **PRECISE + 最短时间** 的最优解 ≈ **T+80 关机**（80 s，Δv 余量 51 m/s，精度 −380 m）。比基准快 1 s，且仍是最高档。
> - **ORBITAL + 最激进** ≈ **T+78**（78 s，Δv 余量 151 m/s）。快 3 s，但降一档。
> - **再早**：T+76 及以前直接 INCOMPLETE。
>
> **结论**：60 s 打法在本标定下**不可达**——因为二级燃时固定 21 s，且近地点在最后 3 s 才冲过门槛。最快可行是 **78 s**。
>
> ⚠️ **这与概念 §5.2 的「60 s（激进/熟练）」不符。** 见 §9-C2，我建议把 P3 的三档重新标定为 **78 / 81 / 90 s**。

## 4. 玩家输入映射（键鼠）

S5 **不接受直接输入**，但响应两个既有动词的间接效果：

| 动词 | 键位 | 对判定的作用 |
|---|---|---|
| **V2 节流** | `W`/`S` 或 `↑`/`↓` | 降到 `0.30` 并保持 1.0 s ⇒ **主动关机** ⇒ 触发判定。这是玩家唯一能"提前结束"的手段 |
| **V5 中止** | `Esc` | 触发 S6 的 `ABORT`，不进入判定 |

### 4.1 主动关机的输入细则

1. **必须显式确认**：`throttle ≤ 0.30` 持续 1.0 s。期间松开 `S` 键（节流回升）⇒ 计时器清零，不判定。
2. **HUD 反馈**：保持期间显示 `SHUTDOWN ▓▓▓░░ 1.0s` 的倒计时条（美术 §5.4 分段式 8 段），让玩家知道"我在触发关机"。
3. **一级段不允许主动关机**：`stage === 1` 时该逻辑禁用。理由：一级关机后没有二级点火，火箭必然坠落，这不是一个有意义的选择，只会制造误操作。
4. **自动关机优先**：若 `fuel2 <= 0` 先发生，则走 SECO 判定，忽略关机保持计时器。

## 6. 边缘情况（≥3 条，含数值退化与除零防护）

### 6.1 `DEGENERATE` 解算（垂直上升，`h_ang → 0`）

起飞瞬间 `r × v ≈ 0`，`e → 1`，`rp → 0`。`orbit-solver.ref.mjs` 已用 `(a, e)` 标量式规避了 `p/(1−e) = 0/0` 的奇点（见该文件 §3 与反例函数），但 `r = 0`（理论上不可能）仍会触发 `DEGENERATE`。

**防护**：
```
if (regime === DEGENERATE || !Number.isFinite(periapsis) || !Number.isFinite(apoapsis))
    → valid = false，沿用上一帧的 (regime, periapsis, apoapsis)
    → 若从未有过有效值，则 periapsis = −R（−300 km）、apoapsis = NaN
```
S7 的 Ω 计算在 `!valid` 时**跳过模态 B 判定**（见 S7 §6），保持模态 A。

**验收**：起飞前 10 帧内 `periapsis` 不得为 `NaN`，且 Ω 读数不得闪白或闪 `--.-`。

### 6.2 `ESCAPE` 分支（远地点 `Infinity`）

RT-1 诊断 ③的教训：v1 扫描把 `ESCAPE` 误判为入轨。

**防护**：`Number.isFinite(apoapsis)` 是入轨判定的**独立必要条件**（§3.2）。`ESCAPE` 状态在 S7 上必须显示为：
- 远地点读数显示 `∞` 而非数字
- 评级判定为 `INCOMPLETE`
- 若最终判定为 ESCAPE ⇒ 失败码 `ESCAPE_TRAJECTORY`，归因文案："你把自己甩出了引力场 —— 速度 2,214 m/s 已超过逃逸速度 2,138 m/s。收油门。"

**数值背景**：基准弹道 SECO 速度 2087 m/s < 2138 m/s，**不会逃逸**。但玩家若全程满油门 + 高抛 + 早分离，可能超过。这是一个真实存在的失败模式。

### 6.3 `periapsis` 恰好等于门槛值的浮点边界

`periapsis = 13500.0000000001` vs `13499.9999999999` —— 评级在 `PRECISE` / `ORBITAL` / `INCOMPLETE` 之间翻转，玩家会认为系统在随机。

**防护**：判定用**严格不等号 + 1 m 迟滞带**：
```
// 入轨：需超过 13.5 km + 1 m
entersOrbit : periapsis >= H_PASS + 1
// 精确：|Δ| ≤ 750 m（不含迟滞，精度是可连续比较的量，无抖动风险）
```
且**判定在 `tJudge` 时刻一次性冻结**，不再随后续帧变化。

### 6.4 主动关机计时器的竞态

玩家在 `T_SHUTDOWN_HOLD` 计时到 0.95 s 时松手，节流回升到 0.35，下一帧又按回去。

**防护**：计时器在 `throttle > 0.30` 的**任一帧**立即清零（不是衰减），重新开始计时。这杜绝了"抖动着凑满 1 秒"的意外判定。

### 6.5 判定时 `fuel2` 已耗尽但 `stage` 仍为 2 的一帧

S1 的推进逻辑为 `if (stage === 2 && fuel2 > 0)`，耗尽当帧 `thrust = 0`。若 S5 在 S1 之后运行（时序见 §7.3），读到的是**已耗尽**状态 ⇒ 立即判定。这是正确的，但需确保**只判定一次**。

**防护**：`if (!judged && stage === 2 && fuel2 <= 0) judge();` —— `judged` 是一次性闩锁，重开时清零。

### 6.6 近地点在判定后继续变化

判定后物理冻结（`tJudge` 后不再积分），因此近地点不再变化。**但结算面板显示的是 `tJudge` 时刻的值，不是后续演算值。** 必须显式快照：
```
snapshot = { periapsis, apoapsis, dvRemain, fuelRemainKg, flightTime }
```
**验收**：连续 10 次相同弹道，结算数值完全一致（差异 < 1e-6）。

### 6.7 `a < 0`（双曲线分支）的 `apoapsis` 处理

`orbit-solver.ref.mjs` 在 ESCAPE 分支下 `o.aa = Infinity`。S7 显示 `∞` 时**必须走等宽字体的特殊字形**，不得显示 `Infinity` 字符串（会撑破布局）。美术 §5.2 已要求 `tabular-nums`；`∞` 需纳入位图数字集的符号表。

## 9. 冲突与待裁决项

### C2【阻塞级】60 s 打法在本标定下不可达，最快 78 s

见 §3.7 的完整数据：二级燃时固定 21 s，近地点在最后 3 s 才冲过门槛，因此**最快可行局时 = 78 s**，概念 §5.2 的「60 s（激进/熟练）」不可达。

**建议（与 S2 §9-C2 的方案 B 配套）**：把 P3 的三档重新标定为：

| 档 | 值 | 含义 |
|---|---|---|
| **快** | **78 s** | 激进：近地点刚过门槛即关机（Δv 余量 ~151 m/s，评级降为 ORBITAL） |
| **基准** | **81 s** | 两级烧满（RT-1 实测值） |
| **慢** | **90 s** | 保守：一级节流降档拉长燃时，重力损失上升，Δv 余量下降 |

**这不改变 P3 的 60–90 s 窗口**（78/81/90 全部落在区间内），也不需要动任何物理参数。只需改写概念 §5.2 的时长表述。

### C5【低】RT-1 §5 表头「Δv 余量」实为「Δv 总损失」

RT-1 §5 表格的列名为「Δv 余量」，数值为 531–603。核对：`DV_TOTAL (2635) − vEnd (2104~2032) = 531~603`，即**重力 + 转向 + 气动的损失总和**，而非"剩余推进剂可提供的 Δv"。

概念 §7.1 把第 5 读数定义为「Δv 余量」，指的是**后者**（剩余推进剂 Δv，随燃烧从 2635 递减到 0）。

**同名不同义，会在实现阶段造成严重误读。** 建议：
- RT-1 §5 表头改为「**Δv 损失**」
- 本 GDD 与 S1/S7 中的「Δv 余量」一律指 `dvRemain = ISP_G0 · ln(m / m_dryPath)`（剩余推进剂 Δv）
- 「Δv 损失」作为独立指标 `dvLoss = dvSpent − v`，仅出现在结算面板（§3.6）
